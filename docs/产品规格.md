v2.17 补记十四（2026-11-14）：演示厅再去重复——① **删除演示厅「我维护的」汇总区**：四个子区视图最下方不再设汇总区（补记四的汇总区部分、补记十一的相关恢复口径均作废）；本人维护的条目唯一标示就是卡片**绿色外框线**，在其所属子区原位呈现，不再汇总重复展示（理由：本人维护的稿本来就在各自子区里、绿框可认，如拜访目录下我维护的一两套，无需再单列一区重复出现）。② **我的库删除离线缓存面板**：我的库页面不再单设缓存总览面板 / 区块；离线缓存在我的库只以卡内状态 + 单条操作呈现，成规模管理仍在内容页「本地缓存」视图、全局开关与管理员策略仍在设置页（补记三的三层分工不变，只是我的库不再多出一块面板）（见 3.17）。
v2.17 补记十五（2026-11-14）：语言绑定改版——用户否决独立的语言绑定工作台（「打开封面以后，里面有一个语言绑定主页绑定英文，这个实际上是不需要的」）。新口径：**绑定就在打开的内容块里面做**——打开内容块（如封面），在当前版本的页面缩略图处，每页可选目标语言并绑定到该语言的对应页；可选语言来自**设置里维护的内容语言清单**（英语、日语等任意语言，可增删），**双语**是可选形态之一；不再有独立的语言绑定主页 / 工作台。底层不变：绑定仍落到每一页，缺译、译文待更新、来源徽标、补绑定合并、整稿换语言等机制照旧；原工作台的拖拽配对不再是绑定入口，导入时的自动预配确认保留为导入流程的一部分。同日早些时候用户曾确认「自动预配 + 拖拽配对」，本补记 supersede 其交互形态（见 3.12、7.9）。

v2.17 补记二十二（2026-11-14）：条目卡**右上角设「删除」按钮**——删除该索引条目（生成提交；只删条目，不删库中内容块，既有规则不变），删除前走一句式小确认（见 3.10）。
v2.17 补记二十三（2026-11-14）：术语与分色——条目版本策略里的「固定（当前版本）」统一改称「**版本锁定**」；版本锁定与解除锁定（跟随最新）两态**用颜色区分**：锁定 = 橙色、跟随最新 = 绿色，「保持最新」开关与锁定徽标同色语义（见 3.10）。

（五）**讲稿实现口径（§3.16）**：讲稿随版本存储（versions.scripts_json，逐页对齐）；导入 / 发布时由片段备注页正文占位符抽取为初始讲稿。编辑通道 `PUT /v1/versions/:id/scripts`（需发布权限），**只改讲稿、不升版本号、不升内容修订**。导出「添加备注」口径落定：按导出绑定顺序把各版本讲稿写回组装稿对应页的备注页（`set_notes_text` 只写已有备注页正文占位符的页；无备注页的页跳过，不新建）。

## 1. 目标与范围

**产品定位：面向大公司的 PPT 管理器（暂定名「启幕」）。** 给公司在局域网内管理 PPT 内容：内容按“内容位”拆开管理、各自留版本；作者改好后发布到局域网主机；同事在 PowerPoint 里打开文稿时收到更新提示，逐个或全部接受，**在打开的原文件里原地替换**；同一内容位的不同形态（如精简 1 页 / 详细 3 页）长期并存，可随时切换。组织、部门与权限按大公司的形态建模（第 7 节）；局域网版是第一期的部署形态，数据模型为将来扩到多组织 / 云端预留。

本期（局域网版）做：

- 局域网主机集中存储版本，客户端与插件只连局域网、不连外网（AI 翻译调用外部 AI 服务是唯一例外，见 3.13）
- 内容的拆分、版本、发布、更新提示、预览、原地接受更新、形态切换
- 按索引分发的结构更新：从索引导出的文稿，其更新按来源索引的差异计算，含新增模块、删除模块（见 5.7）
- 与 DeckCraft 兼容：DeckCraft 制作的 PPTX 可直接导入管理；本系统导出的 PPTX 能在 DeckCraft 中正常打开；内嵌清单须经得起 DeckCraft 打开—保存的往返（见 8.6）
- CLI 与 GUI 同步交付：全部功能有等价的命令行入口，供 AI 全量接管与自动化测试（见第 2 节第 7 条与 4.4）
- 附件（介绍材料）：可给索引文稿 / 内容位挂 Word、PDF 等说明材料，仅在 Rust 程序（客户端 / CLI）中管理与查看，插件不做（见 3.11）
- 索引页组装工作台：在索引页内从内容库选用页面、拖动排序，组装并导出一份新的 PPT；组装时按索引成稿给出“优选推荐”的后续选页建议（见 5.4）；导出文件仍与数据库保持连接（见 5.4），之后可继续往里插页（见 5.5）。**内容页只做内容维护**（浏览、发布、版本、标签、讲稿、语言绑定等），不承担组装与导出（见 4.2）
- 标签与适用说明：任何成员可给页面 / 版本打标签，向所有人说明它适用于哪个客户、哪种场合（见 3.8）；标签参与页库筛选、组装推荐与更新匹配
- 内容分组与索引文稿：客户端左侧建分组（如公司简介 / 公司技术 / 公司案例）组织内容（见 3.9）；“公司介绍”这类整体文稿在系统里以**索引**形式存在（见 3.10），在客户端点开即可浏览，满意后调用导出生成 PPT——导出时按索引逐项解析到最新版本，导出的永远是最新版（见 5.6）
- 公司式组织与权限：系统按公司—部门—成员建模（见第 7 节）；**分组同时是权限单位**：不同账户能看到的分组不同（有的看全部、有的只看技术、有的只看公司介绍），服务端强制校验，不靠界面隐藏
- 多语言：同一页的不同语言版本互相**绑定**（见 3.12）；接入 AI 把每页翻译成多语言，生成草稿、人工校对后发布（见 3.13）；支持一页双语的双语页（见 3.13）
- 个人绑定：封面 / 尾页等页面可把汇报人、手机号、微信二维码等位置绑定到账户资料，导出时自动替换成导出人本人的（见 3.14）
- 讲稿与自动备注：每一页可备好“介绍时要说的话”（可 AI 起草），导出时可选择是否把讲稿自动写入 PPT 的备注（见 3.16）

- 公网 / 云端同步、跨网络使用
- 按部门 / 分组的强制推送策略（二期）
- WPS 插件（第二期，需单独验证其插件接口）
- 自动合并同一页的双方修改

## 2. 已确认的硬性要求

1. **原地替换**：接受更新必须修改当前打开的原文件，页还是那些位置的页，保存还是原路径。生成一份“更新好的新 PPT”作为交付方式不可接受。
2. **不依赖 PowerPoint 分节**：分节既不作为更新单位，也不要求用户的文稿预先分好节。分节仅可作为可选标签用于浏览分类。
3. **形态同线并存、可相互替换**：同一内容位的精简版与详细版属于同一条内容线，是同一份内容在不同粒度下的呈现——由分拆（一页展开成多页）或合并（多页浓缩成一页）产生。它们长期并存，且在同一内容位上可以相互原地替换。任何形态都不是另一形态的“升级版”，选哪种取决于场合。
4. **本地优先用 Rust**：客户端与服务端用 Rust 实现；PowerPoint 侧一期由客户端内的 COM 桥模块对接（见 4.3），二期再做 PowerPoint / WPS 加载项。
5. **部署与开发环境分离**：目标局域网有一台常开电脑 / NAS 当主机；开发环境没有这台主机，开发时服务端跑在开发机上，上线时整体迁移过去，不改代码。
6. **组织与可见性在服务端强制**：账号、部门、权限是系统的一等公民，不是后补的设置页。成员只能看到被授权分组内的内容；页库、搜索、缩略图、组装、插件面板与更新下发都必须按账号的分组权限在服务端过滤——看不见的分组，其内容在任何接口里都不出现，连“存在”都不泄露。
7. **CLI 与 GUI 同步交付、功能等价**：本程序的全部功能除 GUI 外必须同步提供一套命令行接口（CLI），覆盖导入、发布、标签、索引编辑、组装、导出、查更新、组织与权限管理等一切操作，并按“供 AI 全量接管”的标准设计：非交互、结构化 JSON 输入输出、稳定退出码（见 4.4）。GUI 能做的事，AI 用 CLI 必须都能做；反之亦然（同一核心库实现，见 4.4）。

## 3. 核心数据模型

### 3.1 文稿 Deck

一份被管理的 PPT 文件。文件内嵌一份清单（Manifest），记录：文稿 ID、每个受管理页属于哪个内容位 / 哪种呈现形态 / 哪个版本。清单是插件在打开时比对更新的依据，靠它而不是靠页码认页。

**存储形态（只存拆分层，不存原稿）**：一份 PPT 进系统后**只以拆分形态存在**——每个内容位的每个形态版本存为一个小 PPTX 片段（1..N 页），文稿本身就是“清单 + 一串片段引用”。**不保留导入时的原始整份文件**：需要整份时随时由片段按清单拼回（导出就是这么做的），拼回的整份与原稿在页面层面等价（以第 9 节保真度测试为准绳）。拆分粒度是**内容块**而非单页：一个三页的块是一个片段，块内页不单独成片（但带页位与逐页指纹，见 3.5）。不留原稿的安全网在导入环节：拆分完成后、正式入库前，系统立即按清单把整稿拼回一遍，与源文件逐页比对（页数、逐页指纹、缩略图），**校验不过则整批不入库并报错**，源文件在校验通过前只作临时文件存在、通过后即弃（见 5.8）。

### 3.2 内容位 ContentUnit

最小管理单位，是一个“话题位置”，如“合作伙伴介绍”“封面”“公司介绍”。身份稳定，不随页数变化。每个内容位带：名称、一句**描述**（讲什么、适合什么场合——可由 AI 在导入时生成、人工修订，见 5.8）、主分组（3.9）、**维护人 / 维护部门**（归属责任，内容过期等提醒发给他）、主语言（3.12）。

### 3.3 内容修订 ContentRevision

同一内容位只有一条内容线。内容的每一次实质变更（事实、数据、名单、说法变了）记为一次内容修订 r1、r2、r3……，与它用几页呈现无关。这条修订轴是判断各形态“内容是否过期”的统一标尺。

### 3.4 呈现形态 Rendition

同一份内容的一种具体呈现，由 **形态 × 语言** 确定：

- 形态示例：精简、详细（可自定义）。形态之间只差呈现粒度与页数，不差内容归属
- 语言示例：中文、英文、日文；另有**双语对**（如中+英同页，见 3.13）

跨语言的对应关系（绑定）见 3.12；由 AI 生成译文与双语页的流程见 3.13。

形态由两种操作产生，这是本节与初版设计的关键区别：

- **分拆**：把较少页展开成较多页。例：合作伙伴原来 1 页讲完，后来拆成 3 页细讲——信息不变或更细，页数变多
- **合并**：把较多页浓缩成较少页。例：原来的 3 页（或 2 页）合成 1 页——还是同一份内容，但经过概括，细节有取舍

因此任意形态都可替换任意形态：替换在引擎层只是“删 N 页、插 M 页”，但在界面层必须向用户说清方向——切到合并形态意味着接受更概括的版本，切到分拆形态意味着展开来讲。例：“合作伙伴介绍”可有精简·中文（1 页，由 3 页合并而来）、详细·中文（3 页，由 1 页分拆而来）、精简·英文、详细·英文。

边界（v1.4 修订）：**形态意义上的合并**，来源页必须同属一个内容位。若把属于不同内容位的内容合到一页，那不再是某内容位的新形态，而是**合成出一个新内容块**（新内容位），走 3.15 的合成规则：新块独立成线、记派生谱系，与来源各走各的版本与更新。

### 3.5 版本 Version

每种呈现形态内不可变的历史版本，编号为**语义版本 X.Y.Z**（如 1.1.1 … 10.0.5——需求方在“顺序号 v1…v9”与“语义版本”之间明确选后者），包含：

- 页片段：一个小 PPTX，含 1..N 页（N 是该版本自己的属性，各版本页数可不同）
- 每页所用**字体清单**（入库时随片段记录，供组装体检与公司标准字体治理，见 5.4）
- **版本状态**：正常 / **已撤回**。已发布版本若被发现数据错误，作者或管理员可撤回它并指定替代版本（通常是修正后的新版本）：此后它不再被导出与推荐引用；持有它的文稿打开时收到**强提示**（级别高于普通更新、不可随手跳过），指引一键换到替代版本（流程见 5.2）。撤回留痕（谁、何时、原因）且不可恢复——纠错的方式永远是再发新版
- **版本号与发布递增**：X.Y.Z 在全系统统一使用——历史区、卡片徽标、替换选择器、CLI / API 的版本标识都是它；“最新版” = 语义版本序最大的已发布版本（原“最高版本号”规则等价迁移）；索引的发布标签同为 X.Y.Z 风格（展示可带 V 前缀）。发布时**人工点选递增段**：发布确认卡给出三个选项——**大版本**（X+1.0.0）/ **小版本**（X.Y+1.0）/ **文字调整**（X.Y.Z+1），点哪个系统就按哪段递增生成新号，人不手写数字；系统按本次变更**智能预选**推荐项：页数 / 形态变化或内容大改 → 大版本，内容修订更新（数据、说法变化）→ 小版本，仅文字、错别字、排版微调 → 文字调整；发布人可改选，预选、改选与最终号都记入版本记录。X.Y.Z 只是形态版本的发布号，与内容修订轴（rN）分工不变：新旧判断仍以所依据的 rN 为准。回滚发布新版时同样按点选段递增（见 6.4）
- **拖拽插入与级联重编号（编号可变、身份不变）**：内容块的历史版本区支持把一张新版本卡（刚发布待归位的新版，或从发布流带来的新版卡）**拖到历史序列的任意位置**落下（拖拽中有落点指示，松手前可取消）：落在中间即成为历史版本（最新版仍是序列首位那版），落在首位即成为最新版。**落点定号**：以落点前一版（更老一侧）为基，按发布人选定的递增段（大版本 / 小版本 / 文字调整，系统按变更类型预选，同发布递增规则）算出插入版的版本号；其后（更新一侧）的所有版本依次**级联顺移编号**，保持整条线严格单调递增——例：在 2.3.1 与 2.4.0 之间以“小版本”插入 → 插入版为 2.4.0，原 2.4.0 顺移为 2.5.0，其后同理；以“文字调整”插入 2.3.1 与 2.3.2 之间 → 插入版 2.3.2，原 2.3.2 起依次 +0.0.1 顺移直至有空位或到线尾。**护栏（关键）**：每个版本有不可变的**内部版本 ID**；一切引用——索引条目 / 锁定、快照、文稿清单、导出记录、离线快照——一律按 ID 绑定，X.Y.Z 只是该 ID 当前的**展示号**。因此级联重编号永不破坏任何引用：已导出的 PPT 再打开时按 ID 显示现行编号；导出记录保留导出当时的编号并可对照现行编号。每次编号变化逐版留痕（原号 → 新号、原因“因插入 X.Y.Z 于某位置”、操作者、时间），版本详情中可查**编号变更记录**。重编号不改版本内容、修订时间、依据的内容修订号与状态（已撤回仍撤回）；只允许该形态的维护人操作，操作本身记入审计；级联只在本形态线内，跨形态 / 跨语言线互不影响。**作用域**：本条只适用于内容块的形态版本线；索引的发布标签（tag）不可变、不适用（Git 标签不移动）。与删除替代的衔接：快照记原编号 + ID，按 ID 找不到已删版本时仍按删除替代规则沿现行编号向上找最近存续版本
- **修订时间**：版本的正式字段——发布时间戳，精确到分钟；在版本详情（历史卡展开与版本信息面）中与作者、改动说明、所依据的内容修订号一并明确展示，不再只是小字注脚
- **所依据的内容修订**：这个形态版本对应内容线上的哪次修订（如“依据 r5”）
- **来源**：直接编辑 / 由哪种形态的哪个版本分拆而来 / 由哪种形态的哪个版本合并而来
- 每页的缩略图、提取的文字（用于预览、搜索、文字差异对比）
- 每页的**讲稿**：介绍这一页时要说的话（见 3.16）
- 作者、时间、改动说明
- 全部页内容指纹（哈希），用于判断某页是否被本地改过
- **页位与逐页身份（多页版本）**：版本内的每一页有稳定页位（组内序号 + 可选页标题）与各自的指纹；新版本与上一版逐页对位比对，能确切说出“只有第 2 页变了”。这是单页更新（5.9 第 8 点）、页级冲突判断（6.1）与摘选页跟随更新的依据

### 3.6 页的身份

受管理的页绑定内容位 ID + 呈现形态 ID + 版本 ID。页码只是当前位置，会随插入 / 删除漂移，任何逻辑不得以页码作为身份。

### 3.7 绑定实例与组装记录

- 同一内容位可以在一份文稿里出现多次（例如正文出现一次、附录再出现一次），清单中按**绑定实例**逐个记录：实例 ID + 内容位 / 形态 / 版本 + 当前页范围。更新、切换形态、过期判断都以实例为对象，互不影响。
- 用户在索引页组装工作台里组装出的文稿，服务端存一份**组装记录**：文稿 ID、标题、创建者、有序的绑定实例清单、所用模板（见 5.4）。导出文件里的清单与这份记录对应同一文稿 ID；之后文件内的增删页要回写这份记录（由执行增删的插件 / 客户端负责，见 5.5），使服务端记录与文件实际内容不脱节。

### 3.8 标签与适用说明

标签的作用是让所有人不用猜就知道“这一片是给谁、干什么用的”。同一页面的不同版本可以有完全不同的标签——这正是版本之间最重要的人工说明。

- **挂载层级**：标签主要打在**版本**上（最精确）；内容位 / 呈现形态上可设默认标签，新版本自动继承，发布时可改。
- **维度**：
  - **客户**（受控词表，多选）：如“西门子”、其他客户名；外加系统值“通用”。词表由管理员维护，避免“西门子 / Siemens / siemens”各写一份
  - **场合 / 用途**（受控词表，多选）：如“详细业务介绍”“简要介绍”“内部汇报”“展会宣讲”
  - **自由标签**：任何成员可加，不受词表限制
- **适用强度**：客户标签分两档——“适用”（推荐给该客户用）与“专属”（含该客户的名称、Logo、案例或数据，只能给该客户用）。专属是后续筛选与误用警告的依据，见 5.4 / 5.5。
- **适用说明**：每个版本可写一句短说明，如“这版适合给西门子做详细业务介绍时用”，和标签一起显示在页库卡片、插件的版本列表里。
- **谁能打**：任何成员可新增标签（词表值或自由标签）；删除他人打的标签仅限原作者与管理员。标签变更记入操作记录（谁、何时、改了什么）。
- **与更新匹配的关系**：绑定实例记下其所绑版本的客户标签作为上下文；查更新时，同形态的新版本只有客户标签为“通用”或与该上下文有交集时，才算这个实例的候选更新。给西门子做的专属新版本，绝不能被提示给正在做其他客户文稿的人。场合标签不阻断更新，只影响推荐排序与筛选。

### 3.9 内容分组（左侧目录树）LibraryGroup

客户端最左侧是一棵按**用途**组织的目录树：一级目录是功能用途（如“公司介绍”），目录下可继续建**子文件夹**（如 公司介绍 > 客户版 / 展会版），子文件夹里放内容位与索引文稿（见 3.10）。目录同时是内容的组织方式与权限的划分单位（见第 7 节）：

- 分组由管理员 / 有管理权的成员创建、改名、排序；每个内容位 / 索引文稿有且只有一个**主分组**（它在左侧栏里的家）；跨分组的发现靠搜索与标签（3.8），不靠多处安家
- **点开一个目录，内容页右侧是该目录的维护视图**：平铺该目录下全部内容块的最新页供浏览与维护（内容页只做内容维护，见 4.2）；右侧顶部同时列出该目录的子文件夹入口，点入即切换。该目录的“成稿”（若设了主索引，主索引按顺序解析到最新版的整稿）不在内容页呈现——归索引页：打开主索引即见成稿（见 3.10 / 5.6）。内容页主窗口是左右两栏：**左 = 目录树，右 = 当前目录的内容维护区**
- 分组是授权的基本单位：对部门 / 成员的授权以“分组 × 能力”授予（查看 / 使用导出 / 发布 / 管理，见 7.3），授权默认含其子文件夹。成员登录后，左侧栏只出现其有权查看的分组

### 3.10 索引文稿 IndexDeck 与导出记录

“公司介绍”这类整体文稿在系统里的存在形式**不是一个 PPT 文件，而是一份索引**：

- 索引文稿 = 标题（如“公司介绍（2026 版）”）+ 所属分组 + 有序条目清单 + 默认上下文（目标客户 / 场合 / 语言）+ 所用模板。每条条目 = 内容位 + 呈现形态 + **版本策略**：
  - **跟随最新**（默认）：浏览与导出时解析为该形态的最新发布版本（再过 3.8 的标签匹配）
  - **版本锁定**：条目钉死在指定版本，用于必须冻结内容的场合（如已对外发布的定版介绍）。**锁定语义（钉死）**：锁定有两种来源——把条目当前解析到的版本锁定下来，或选定某个历史版本并锁定（与双击替换“选历史版自动锁定”衔接，见条目编辑交互）。锁定后，该内容块后续发布任何新版本都**不改变本条目的解析内容**：索引预览、导出、以及从本索引导出的 PPT 的更新检查全部以锁定版本为准，更新检查对锁定条目**静默跳过**（不产生更新提示、不进入结构 diff，见 5.7）；卡上常显锁定徽标（橙色，与跟随最新态的绿色分色，「保持最新」按钮同色语义，补记二十三），仅可被动提示一句“源内容块已出新版 vX（已锁定不跟随）”；只有维护人手动“更换版本”或“解除锁定”才能改变。导出前体检中锁定条目列为**已知项**而非警告升级项
- 索引条目可指向整组多页形态，也可摘选其中单页（同 5.4 摘选规则）。
- **Git 式仓库模型（需求方定：“索引做成类似于 git 的”）**：一份索引就是一个 **Git 式仓库（repo）**，坐落在它的目录坐标上（坐标 = 仓库地址，第一坐标；索引域另有四条专属设计验收标准——合理 / 现代化 / 易上手 / 易理解，见 4.2）；文件夹的“主索引”指向某个仓库的主分支 main（成稿线）。本节以下概念按 git 语义定义：**修订 = 提交（commit）**、**发布版本 = 标签（tag）**、**派生的主机制 = 分支（branch）**、原“副本（fork）”降为次要动作**复制为新索引**、分支之间可**合并（merge）**。导出绑定由（索引 + 版本）二元组升级为**（仓库、分支、tag / commit 快照）三元组**（见“导出记录”条与 5.7）。
- **索引总览卡（客户端呈现，不是新的数据对象）**：索引页第一级以卡片陈列当前账号有权查看的全部索引；卡面封面取该索引按当前解析结果的第一页（第一个条目当前版本的首页）整张缩略图（补记十三：不再拼图），卡面只留**标题、当前发布版本、生命周期状态、维护人、最近修改**（并以徽标区分主索引）；**目录坐标行、谱系行、解析后的条目数 / 总页数、语言已撤下卡面**（v2.17 补记九：卡面再简化）——目录坐标由总览按目录分组的分组头承载，谱系（分支：〈名〉 · 基于 V__ / 复制自：〈源仓库名〉 @ V__ / main · 原创仓库，见下“分支与谱系”条）与条目数等进双击打开的详情。卡面**不出现语言对应版的徽标与入口**（显示规则见下“语言对应”条）。它与演示厅条目共用同一套卡片组件（同样的封面 / 标题 / 介绍 / 署名 / 徽标排版，不另设索引专用卡样式），本质不同：演示厅条目是可直接展示的成品，索引卡是**可编辑的结构 / 配方入口**，因此卡面必须突出“可编辑、当前发布版本、条目数 / 总页数、目录坐标与谱系”；卡片本身不生成、也不代表一份存档 PPT。
- **目录坐标（常驻坐标，第一坐标）**：每份索引有且只有一个主目录（主分组，见 3.9），其**完整路径**（如“公司介绍 › 客户拜访”）即该索引的目录坐标，是定位索引的第一坐标。目录坐标在其出现的关键面**常显**——总览按目录分组的分组头、导出记录、分享对话框与分享落地页、搜索结果、群组空间条目；**总览卡面与详情页眉已按 v2.17 补记七 / 九撤下坐标行与坐标栏**（卡面再简化、页眉简化），坐标改由分组头与详情内信息承载——坐标作为定位依据的地位不变，只是呈现位置收敛；索引页左侧目录树为常驻导航，总览与详情 / 编辑器内都在。**坐标与身份分离**：索引 ID 是不变的身份，目录坐标可变更——“移动到其他文件夹”是详情内的显式管理动作，需“管理”权、写审计并记录坐标变更历史；已导出 PPT 按索引 ID 跟随更新线，不受坐标变更影响。
- **子索引（术语先行）**：“子索引”只指从某索引派生出的成果——同仓的**分支**（主要形式）或复制出的新索引；索引条目不是子索引。索引之间只有两种关系：**派生**（同语言分叉）与**语言对应**（跨语言镜像），界面与文档都不得混淆——语言对应版不是子索引，不进派生谱系、也不出现在总览层（见“语言对应”条的显示规则）。
- **提交（commit，原“索引修订”升级）**：索引的条目清单每发生一次增 / 删 / 改（换形态、换版本策略、调序）生成一个**提交**：含作者、时间、说明与对条目的 diff（增 / 删 / 改条目、排序、版本策略变更）。提交历史是**提交图（DAG）**，不是单线流水号；原修订号保留为提交短号展示。提交只是编辑流水，本身不惊动已分发的副本——只有在其上打标签发布才对外（见下）。
- **条目编辑交互（详情内定版，见 4.2 布局）**：索引详情的主体是全部条目的**内容块图墙**（每条目一张图形卡，见 4.2）。在图墙上：**拖拽条目卡排序**，松手即生成一个提交（说明自动记为排序变更，diff 记顺序变化；仍守乐观锁——基于的提交号冲突时拒绝并示对方 diff）；**双击条目卡 = 就地替换内容**：原位打开该内容块的替换选择，图形化列出同一内容块的其他形态与版本（各形态 / 版本的页面缩略图组，与内容页下钻同款呈现），选中即替换该条目——选某形态的最新版，条目保持 / 设为**跟随最新**；选历史版本，条目自动转为**锁定版本**并在卡上标明；多页形态可选摘页（子集），记摘页绑定（既有规则）。替换同样生成提交（diff 记条目形态 / 版本变更）。与拖拽排序、双击替换并列的另两个结构操作：**条目间插入**——相邻条目卡之间（及首尾）有插入点，点开内容选用器（组装工作台的选用模式）选一个内容块（形态 / 版本，默认跟随最新）即在该位置新增条目，生成提交（diff 记新增条目与位置）；**全面编辑**——条目卡上的入口，点击后跳转到内容页并直接打开该内容块（带返回上下文：来自索引 X 的条目 Y），在内容块视图里重新选定该条目使用该内容块的哪些页（页码选定 / 摘页重选），确认后回索引详情生效（摘页绑定更新）并生成提交。与内容页职责的衔接：内容页仍不做组装 / 导出，此处的选页是经索引跳转进入的**条目页选定模式**，内容页顶部带上下文条（“为索引 X 选页 · 确认返回”），不常驻于常规维护流。双击在此是替换、不是跳转：去内容页维护该内容块本身另有次级入口（按钮 / 右键），全面编辑是带选页目的的专用跳转；单击条目仍只是选定（显示条目信息与版本策略）。**条目快速换版（需求方定）**：除双击替换外，条目卡下方常设一条**快速换版带**——摆出该内容块当前形态**最近的几个历史版本**（从新到旧，图形小卡：版本徽标 + 页面缩略图），**单击某个历史版本即把该条目就地换成那一版**（直接替换条目当前页面；规则与双击替换一致：选历史版自动锁定、生成提交）；条目跟随最新由动作区「更换版本」之后的**「保持最新」按钮**控制（按钮面上带「保持最新」字样，补记二十五）：点它即设为 / 恢复为跟随最新（解除锁定）；点某个历史缩略图时条目转版本锁定，按钮回待点态；跟随中按钮呈绿色生效态。换版带只摆历史版本缩略图，个数按可用宽度自适应（宽则 4 个以上），没显示完的在带末设现代化「更多」，点开**弹窗展示该内容块当前形态的全部历史版本**（整条版本线，图形卡点选即换版，补记二十四）。条目卡**右上角设「删除」按钮**（补记二十二）：删除该条目并生成提交，只删条目、不删库中内容块。条目卡的动作顺序定版：**「更换版本」排在「去内容页维护」之前**。
- **标签（tag，发布版本）**：作者在某个提交上打一个正式版本标签发布出去，如 V1.0、V1.2、V2.0、V3.5.4（系统按“大版本 / 小版本 / 修订号”给出递增建议，作者可改）。标签**不可变**，冻结该提交的条目快照 + 版本说明。**已导出文稿的结构更新以“其跟踪的分支上出现新标签”为触发点**（见 5.7）：未打标签的提交只在作者端可见，打标签才推送。标签列表可查每个标签被导出了多少次。
- **分支（branch，派生的主机制）与谱系——第二坐标**：从任意提交或标签可拉出**分支**——同仓、同坐标、共享分叉点之前的提交历史，之后各自独立提交；分支可命名（如“西门子定制”“展会版”）。每个仓库有一条主分支 **main**（成稿线）；文件夹的“主索引”指向（仓库 + main 分支）。“哪个子索引由哪个派生”由分支图直接回答：分支名 + 分叉点（基于哪个 tag / commit）+ 分叉后各自的提交数。此前作为主机制的“副本（fork）”降为次要动作**复制为新索引**：生成新仓库、新坐标，记录派生自（源仓库 @ tag / commit），跨仓库不合并、不互扰。谱系仍是索引的**第二坐标**：总览卡片以谱系行常显——分支语境显示“分支：〈名〉 · 基于 V__”，复制出的新索引显示“复制自：〈源仓库名〉 @ V__”，有分支的仓库显示“含 N 条分支”；总览第二视图“按派生关系”即**仓库分支图**（一个仓库一张图，main 在主线、分支按分叉点挂出；独立复制的新索引是另一张图，图间以虚线标注“复制自 X @ V__”）；详情 / 编辑器顶部设“归属与谱系”常驻条（目录坐标 + 当前分支与分叉点 + 语言对应入口）。**更新严格按线走（按分支拉取）**：一份 PPT 只沿它跟踪的那条分支拉取更新（绑定三元组见“导出记录”条），其他分支的提交与标签对它不可见、互不影响。
- **版本带与老页面（详情「历史版本」视图）**：索引详情 / 编辑器的「历史版本」视图（顶部按钮切换、单区显示，见 4.2）设**版本带**：当前分支的发布标签从新到旧排列，形式与内容块历史版本一致（图形化、可点击）。点某个标签 → 进入该 tag 的**只读老页面**：整页图墙按当时快照呈现（条目、顺序、各条目解析版本都冻结在那个 tag），顶部标明“历史版本 V__ · 只读”；可从老页面一键导出当时的整稿（沿用导出记录规则，快照来源记为该 tag）；返回即回当前版。
- **删除替代（通用规则）**：任何“引用版本不存在”的场合——老页面快照里被引用的版本、锁定条目所锁的版本、替换选择器里失效的引用——若被引用的内容块版本已被删除（或不可用），不留空洞：以同一内容块、同一形态**沿版本号向上找最近的存续版本**替代展示，卡上标明“原版已删 · 以 X.Y.Z 替代”。替代只影响当次展示与该次导出，不改写历史快照记录（快照仍记原版本号 + 替代注记），且替代项在导出记录中可查。
- **合并（merge，本轮新增——明确变更：取代此前“一期不提供副本合回主线”的排除项）**：分支可向任意目标分支发起合并；以分叉点提交为 base 做**条目级三方合并**：只有单边改动的自动合入；同一条目双边都改 → 冲突，逐条人工裁决（用我的 / 用对方的 / 手动选该条目的形态与版本策略）；合并生成一个 **merge commit**，记录来源分支与裁决结果。冲突只到条目级，不做页内内容合并（与第 1 节“不自动合并同一页的双方修改”一致）。合并只发生在同一仓库的分支之间；“复制为新索引”产生的跨仓库索引不参与合并。
- **索引状态（生命周期）**：使用中 / **历史**（原称“已过期”，现称“历史”，仅改名，语义与触发条件不变：不再维护：禁止新导出并给出提示，其已导出文稿只再收到一次“该索引已转历史、建议改用 X”的通知，X 可指向替代索引（后继索引），由使用人决定是否换线重绑）/ **已作废**（停止一切更新服务，已导出文稿转为普通文件不再受管）/ **删除**（软删：目录中消失、更新服务停止；版本快照与导出记录留档备查，其分支与复制出的新索引不受影响）。状态变更需“管理”权（7.3），并记审计。历史状态的索引在总览中的呈现（默认不列出、分组头“历史”按钮展开、筛选档位）见 4.2。
- 一个目录可指定其中一份索引为**主索引（成稿）**：按 Git 模型即该目录指向某个**仓库 + 其 main 分支**（成稿线），它是该用途的官方成品序列——在索引页打开它即见成稿，也是组装时“优选推荐”的依据（5.4）。
- **主索引变更审核**：被指定为主索引的仓库，其 **main 分支**的条目增删与打标签发布需经该目录所属分组的**部门管理员确认**才生效（作者提交 → 待审核 → 通过后标签方才对外）；普通仓库 / 分支与日常页面发布不设此关，免得拖慢更新。此规则可按分组开关，默认对主索引开启。
- **推送到演示厅（索引 → 演示厅的正式通道）**：索引详情与总览卡的动作区都有“推送到演示厅”。维护人把做好的索引推送后，生成一条**演示厅待审提交**：推送以该仓库 **main 分支当前已发布的最新 tag** 为准；main 尚无任何已发布 tag 时，动作不可用并提示先打 tag 发布。待审提交进入演示厅广场的**上架审核队列**（审核方为演示厅 / 广场管理员）——与 3.17 里成员自荐（即演示厅条目的“申请公开”）**合并为同一队列**，不另设第二套队列；组织节点开启 7.8“成员自维护与申请公开”时，两者共用同一审批通道与同一状态机：**待审 / 通过 / 驳回（驳回必填理由）**，维护人可修改后**重新推送**再次进入待审；该节点设为 7.8 免审公开时，推送按其免审规则处理（推送即上架，留痕通知、管理员可下架）。**审核通过** → 在演示厅广场上架展示：生成的演示厅条目**绑定该索引**，来源标注为该索引名 + 其目录坐标（常驻坐标，见“目录坐标”条）；条目后续按 3.17 既有规则**跟随来源索引的新发布 tag 解析**（来源索引打新 tag 后条目解析随之更新，不需重新推送）。**审核驳回** → 索引详情与推送记录处显示驳回理由，并给出“修改后重新推送”入口。已上架后，来源索引转**历史 / 已作废**时，其演示厅条目按 3.17 既有规则处理（标注来源状态，不静默消失）。推送、撤回推送与审核结果均记审计。**推送不改变索引本身的更新线、分支与导出绑定**：导出物仍按（仓库、分支、tag / commit 快照）三元组走自己的线，演示厅条目只是该索引多了一个展示出口。
- **索引的语言对应版（并列，非分叉）**：一份索引做好后（如中文版），可点“制作英文版”（或任意已有语言→目标语言）：系统生成一份**并列的对应索引**——新索引有自己的 ID、发布版本与生命周期，与原索引以“语言对应”关系互链（各自头部标注对方），条目**结构镜像**：条目一一对应（第 i 条 ↔ 第 i 条同一内容位、同一形态粒度），只是每条解析到该语言的形态（靠 3.12 的逐页绑定）。与副本（3.10 分叉）的区别：副本是同语言的内容分道扬镳；语言对应版是同结构的另一语言面孔。两边的结构变更（增删条目、调序）会**提示同步**到对方（对方维护人确认后镜像跟随），内容版本各按各语言独立演进、独立发版；英文版可标注“结构基于中文版 V__”，落后时在索引页明示差几条。缺译条目在对应版里保留位置、解析时回退显示源语言页并标“缺译”（见 3.12）。导出、更新分发按语言版各自成线：从英文版导出的 PPT 只跟英文版的更新线。对应版是**另一个仓库**的镜像关系，**不是分支**，不出现在分支图上。**显示规则（需求方定）**：语言对应关系不在总览层露出——中文语境下索引总览只列中文索引，英文对应索引不作为独立卡片出现，卡面也不挂语言对应徽标 / 入口，“按派生关系”视图同样不渲染语言对应；英文语境对称同理（英文总览不列中文对应索引）。语言对应只在双击打开索引详情 / 编辑器之后显示：详情顶部“归属与谱系”条里给出对应版入口与状态（对方编号 / 版本、结构基于源版 V__、落后 N 条），“制作英文版”入口也在详情内。这与“单击选定、双击打开”的基线一致：总览保持当前语境语言的干净列表，打开后才见对应版。内容页同理：中文语境的列表层不铺英文索引 / 对应入口，打开内容块后在语言绑定区显示（3.12 既有规则不变）。
- 因为存的是索引，条目指向的页面一有新版，**下次浏览 / 导出自动就是新版**——不存在“系统里那份公司介绍 PPT 忘了更新”这回事。
- **导出记录**：每次从索引（或组装清单）导出，服务端记一条导出记录：来源**（仓库、分支、tag / commit 快照）三元组** / 组装 ID、**逐条快照**、导出人、时间、文件名。目录坐标随记录一并展示（常驻坐标，见“目录坐标”条）。导出的文件本身按 3.7 写入清单并登记为受管理文稿；它是一次性的快照交付，之后页面再更新，该文件按第 5.2 / 5.3 / 5.7 节在 PowerPoint 打开时收到更新提示（是否跟随，由使用人决定），而索引本身永远指向最新。

### 3.11 附件（介绍材料）

PPT 之外常有一份配套的介绍材料（Word 说明、PDF 白皮书等）。附件就是把这类材料挂在内容上一起管理：

- **挂载对象**：索引文稿（给整份成稿配材料，如“公司介绍”的配套 Word 说明）或内容位（给某个话题配材料）。一份对象可挂多份附件
- **内容与存储**：任意文件，主用 Word（.docx）与 PDF；原样存入服务端数据目录，记元数据（文件名、类型、大小、上传人、时间、一句说明）。附件本身不做版本线，换文件即新增一份、旧的保留可删（记操作日志）
- **使用方式（仅 Rust 程序）**：客户端在索引 / 内容位详情里列出附件，PDF 可在客户端内预览，Word 等提供下载 / 用本机程序打开；CLI 同步提供上传、列出、下载（4.4 覆盖范围之内）。**PowerPoint 插件不做附件**（按需求方明确指示）
- **权限**：附件跟随其挂载对象的分组权限（7.3）：有查看权才能看到与下载附件
- 附件上传时抽取文字入搜索索引（Word / PDF 解析、图片类附件 OCR），介绍材料可被全文搜索命中；搜索结果同样受权限过滤（见 4.2）
- 附件不进 PPT 导出物；导出时可勾选“同时导出附件”，把附件文件与 PPT 一并落到同一目录

### 3.12 语言绑定

同一页片子的不同语言版本必须显式知道彼此是“一页”——这就是语言绑定，它是 AI 翻译（3.13）、双语页与整稿换语言的前提：

- **基本绑定**：同一内容位下、同形态的各语言形态天然成组绑定（中文详细版 ↔ 英文详细版 ↔ 日文详细版）。**绑定落到每一页**：不只是形态成组，每一页都知道自己对应的英文页（及各语言页）是哪一页——实际使用中默认每页都有英文对应页，缺失的才是例外（进缺译清单）。内容位详情里按语言并列展示，缺哪种语言一目了然（缺译）。每个语言版本还记录它的**来源**（人工制作 / AI 翻译，见 3.13），详情与卡片以徽标区分——来源不同，可信程度与维护方式都不同
- **页级对齐**：多页形态跨语言时，页与页的对应默认按顺序对齐（中文第 2 页 ↔ 英文第 2 页）；两侧页数不同时（如中文 3 页、英文 2 页），可在客户端手工指定对齐关系，未对齐的页单独标记。切换语言、双语生成、增量翻译都按这个对齐走
- **绑定操作（就在打开的内容块里做，无独立工作台）**：页级绑定在**打开内容块后的当前版本页面缩略图处**完成——不设独立的「语言绑定主页 / 工作台」。打开一个内容块（如封面），每页带语言绑定入口：点开先选目标语言（英语 / 日语 / …，清单来自设置维护的内容语言清单，见 7.9；**双语**是可选形态之一，绑定后该页的双语形态与两个单语页互认），再从该语言下本内容块的页面里点选对应页即完成绑定；已绑定的页显示对方语言与页位小标，可改绑、可解绑；没有对应页的点「标记缺译 / 无对应页」留空位，不硬凑；页数对不齐时可 1 对 N / N 对 1 点选成组。绑定点选即生效，作用于整页语言切换、对应索引与 AI 增量翻译。若目标页已绑在别处，点选时先提示这是**移动绑定**还是取消，不静默抢绑。AI 自动翻译出的页天生带绑定（来源 = 翻译生成、无需人工配对）；人工制作的页经此块内绑定（或导入时的自动预配确认）才算绑好
- **补绑定（事后合并）**：语言版本若被分开导入成了两个内容位（常见情形：英文稿单独导入），可由用户声明“这两个内容位互为语言对应”，系统将其合并为一条内容线：形态与版本各归其位、历史保留、原有两个 ID 建别名不失效
- **整稿 / 单点换语言**：文稿（或单个绑定实例）可切换语言——按绑定关系原地换成对应语言形态的最新版（走 5.3 流程）；无对应语言的条目列入“缺译清单”并原样保留。索引带语言上下文导出（如“公司介绍 · 英文版”）同理：同一索引、换语言解析，缺译条目逐条报告
- **整页语言上下文（客户端）**：客户端顶部有全局语言切换（如 中文 / 英文），它决定当前一切视图的解析语言：**中文态下只显示中文页**（界面干净，不混杂其他语言）；切到英文态，内容页长卷、索引页与成稿解析整页改按英文呈现——有英文版的显示英文页（带 3.13 的来源徽标：人工制作 / AI 译 · 已校对）；**还没有英文版的条目，就地回退显示中文页并标“缺译”**，位置与结构不乱。在英文态点开某页的详情 / 大图时，**内嵌中文原文对照**（源页并排或可切换），供核对译文——即“外面是英文，里面留着中文”
- **译文过期**：每个内容位设主语言（默认其最初语言）。其他语言形态的最新版所依据的内容修订落后于主语言最新修订时，标“译文待更新”，出现在页库卡片与发布者待办里；增量重译或人工更新后解除（与 3.13 联动）

### 3.13 AI 翻译与双语页

**AI 翻译**（接入外部 AI 服务，把每一页翻成多语言）：

- 流程：选源形态（或整份索引）→ 选目标语言 → AI 逐页逐文本框翻译，原样保留版式与格式、只换文字 → 生成目标语言形态的**草稿**版本 → 人工在客户端逐页校对（可改字、可调字号）→ 发布。**AI 译文不经校对不得直接发布**（大公司对外材料的硬规矩）
- **术语一致性**：服务端维护术语库（如产品名、客户名、专有名词的标准译法）与“不译名单”，翻译时一并喂给 AI 并对产出做术语校验，不合术语的段落标出待改
- **版式风险提示**：译文长度与原文差异大（英文通常更长）时，可能溢出的文本框逐个标红提示，校对界面可一键缩小字号 / 扩框后再确认
- **增量翻译**：源头出新修订时，只重译发生变化的页与文本段；未变化段落复用已校对通过的译文——靠 3.12 的页级对齐与内容修订对位实现
- **译文来源与人工保护**：每个目标语言版本都记来源并全程可见（卡片 / 详情徽标）：「人工制作」= 人手工做好、经导入与中文页绑定进来的；「AI 翻译」= AI 产出（草稿标“待校对”，人工校对发布后标“AI 译 · 已校对”）。关键规则：**人工制作的译文受保护**——批量翻译与增量重译**永不覆盖**人工制作的版本；源页更新后，人工英文版只被标“译文待更新”并通知其维护人，由人决定如何改。维护人若想借 AI 一把，AI 生成的只能是并排的**对照草稿建议**，人采纳并发布后，新版本来源仍记“人工定版”。反之，AI 来源的译文在源更新时自动进入增量重译队列、生成新草稿待校对。来源也是导出体检的一项：对外场合用到“AI 译 · 未校对”的页会被拦下提示
- **服务接入**：AI 服务商可配置（地址与密钥存在服务端，管理员维护）；这是本系统唯一需要外网的能力，无外网时仅此功能不可用，其余功能不受影响。CLI 支持整份索引批量翻译，产物同样是待校对草稿

**双语页**（一页同载两种语言，如中英对照）：

- 形态上是独立的呈现形态：语言维度取值可以是**双语对**（中+英、中+日、英+日…）。在内容位详情、组装选页、原地替换里与单语形态同权，选它即整页替换为双语版
- 产生方式两种：人工制作后作为双语形态正常导入发布；或**系统辅助生成草稿**——取 3.12 绑定的两种单语形态，按对照版式模板（上下对照 / 左右对照）拼成双语草稿，缺一种语言时先走 AI 翻译补齐，再交人工定版
- 双语形态的过期判断同时看两个来源语言：任一来源的内容修订更新，双语形态标“待同步”；其版本记录所依据的两个来源修订各是多少

### 3.14 个人绑定与导出个性化

有些页（如封面、尾页）大部分内容全公司一样（公司地址、公司介绍），只有少数位置是“谁用就填谁”：汇报人姓名、手机号、微信二维码。这类位置做成**个人占位符**，绑定账户资料，导出时自动替换：

- **账户资料字段**：每个账号除登录信息外维护一份对外资料：汇报人姓名、职务、英文名、手机号、邮箱、微信二维码图片（可另加头像），以及**社交账号字段**：领英 LinkedIn、X、Facebook、Instagram、YouTube、TikTok、微博（每项可填账号 / 主页链接，适用者可另附二维码图片）。成员自己维护自己的，管理员可代填 / 代改。社交字段与基础字段同为个人占位符来源（封面 / 尾页可绑定，如尾页放领英二维码）
- **占位符类型**：
  - **文本占位符**：版本中的某个文本框（或其中一段文字）标记为某资料字段，如“汇报人”“手机号”。存储的片段里该处只存中性占位内容（如 `{{汇报人}}`），**绝不存任何真人的真实号码**——作者标记时若框里是自己的真号码，入库时自动洗成占位符
  - **图片内容块**：某个图片框标记为某图片字段，如“微信二维码”。它就是用户说的内容块：模板里放一张通用占位图，凡用到这个块的地方，导出时统一换成导出人自己的二维码图片（按原框尺寸填充、保持比例）
- **标记方式**：发布 / 导入时在客户端选中文本框或图片框，一键“绑定为个人字段”并选字段；绑定清单记入版本元数据（页内形状定位 + 字段名），与页片段一起版本化——改绑定即发新版本
- **替换时机（按接收人，不按作者）**：服务端存的永远是模板态片段。凡是片段要落到某个人手里的环节，都在交付前按**那个人**的资料渲染一遍：
  - 组装 / 索引导出：按导出人的资料替换；导出记录另记“归属人”（默认即导出人；管理员代他人导出时可指定归属人，按其资料渲染并在记录中写明）
  - 更新下发与桥插页：按接收文稿的当前账号替换——同事接受封面更新后，封面上的手机号仍是他自己的，不会被作者的覆盖
  - 客户端预览：默认按当前登录人渲染（所见即所得），可切换为“模板态”看占位原样
- **资料缺失时**：归属人没填手机号 / 没传二维码时，导出前明确列出缺失项，给出三选：先去补齐资料、留空导出（该处空白 / 保留占位图）、取消。绝不拿模板作者或他人的真实信息顶替
- **公司公共资料（与个人资料并列的第二套占位符来源）**：公司电话、公司公众号名称、公众号二维码、公司官网、公司地址，以及超级管理员维护的其他公司材料（公司级字段集，可增删）。维护人：**超级管理员**，或由超级管理员**指定的一名成员任「公司资料管理员」**代为维护——该指定只授予公司公共资料的维护权，不含其他超级管理员权限，可随时收回、改派（见 7.9）。版本中的形状可标记为**公司占位符**（如尾页的公司电话、公众号二维码位），存储同为模板态，交付时按公司公共资料渲染
- **导出版本类型：个人版 / 公用版**：组装 / 索引导出时可选——**个人版**（默认）按归属人个人资料渲染个人占位符；**公用版**把封面 / 尾页的联系区按**公司公共资料**渲染带入（公司电话、公众号二维码等），不带入任何个人资料。导出记录记明版本类型；客户端预览可切换个人版 / 公用版 / 模板态
- CLI 同步支持：查看 / 设置本人资料字段、导出时指定归属人、选择导出版本类型（个人版 / 公用版）（4.4 覆盖范围）

### 3.15 内容块层级与跨块合成（设计提案，待审阅）

需求方提出：整体功能应能用“内容块”来定义，且两个内容块的内容可以合到一页、成为一个新的内容块，块与块之间存在层级。层级如何处置，需求方未定，以下为设计方提案（与既有模型对齐，不推翻内容位 / 形态 / 版本）：

**三级块（严格分层，不跨级嵌套）**：

| 级别 | 是什么 | 例子 | 在既有模型里的位置 |
|---|---|---|---|
| 元素块 | 页内的一个形状级元素：一个文本框、一张图、一个图表、一个二维码块 | 微信二维码块、标题文本框 | 页片段内的形状；个人绑定（3.14）、页级对齐（3.12）的作用对象。此级不单独建库，只作为上级的组成部分被寻址 |
| 页块 | 整整一页 | 封面页、历史沿革页 | 内容位的一种单页形态版本即一个页块 |
| 组块 | 有序的多个页块 | 三页的详细版、一个完整模块 | 内容位的多页形态版本；索引文稿是组块之上的整稿组合，不再算块 |

即：**内容位仍是被管理、被版本化的“块”**（页块 / 组块同属其不同形态），元素块是其内部可寻址的零件。层级只回答“由什么组成”，不另起一套版本体系。

**两种关系分开记，不混**：

- **组成关系**（静态）：组块由哪些页块组成、页块由哪些元素块组成——随版本固定，一个组块版本钉死其所含页块的版本
- **派生关系**（谱系）：这个块是从哪些块**合成 / 分拆**来的——记在版本的“来源”里（与 3.5 既有来源字段同一处）

**跨块合成（本节的新增能力）**：把两个（或多个）块的内容合到一页（或一组页），结果**生成一个新内容位（新块）**：

- 新块独立成线：自己的形态、版本、标签、分组归属；命名与归属在合成时由作者指定
- 新块首个版本记派生来源：由块 A 的某版本 + 块 B 的某版本合成（逐一写明版本）
- 来源块不受影响，各自继续独立维护；引用来源的旧文稿、旧索引一概不动
- **来源更新不自动改新块**：来源块出了新版时，新块标“来源已更新”（与内容过期、译文待更新同一套标记哲学），作者可选择“重新合成”——系统按新来源版本重新拼一版草稿，人工调整后发布为新块的新版本；也可忽略标记继续用旧合成结果
- 权限：合成用到每个来源块都需查看权，新块的发布需其目标分组的发布权（7.3）；新块的客户“专属”标签按来源中最严的继承并提示作者确认（防把专属内容洗成通用）

**防环与深度**：组成关系严格按三级向下，天然无环；派生关系允许任意指向旧块，但系统校验不得指向自身或自己的后代合成结果，防谱系成环。

### 3.16 讲稿与自动备注

每一页除了画面内容，还应备好“介绍这一页时要说的话”——讲稿。它是演示质量的一部分，随版本管理：

- **存放**：讲稿挂在**版本**上、按页存放（多页版本逐页一份）。它属于该形态自己的内容：中文形态是中文讲稿，英文形态是英文讲稿（AI 翻译形态时讲稿一并翻译成草稿，见 3.13）
- **来源**：人工在客户端版本详情里逐页写 / 改；也可让 **AI 起草**——按页面文字、内容位描述与适用场合生成口语化讲稿草稿，并估算讲解时长（按字数），人工修订后定稿。导入整稿时（5.8），原稿自带的 PowerPoint 备注会被读入作为对应版本的初始讲稿，不丢失
- **修订规则**：只改讲稿**不递增版本号、不算内容修订、也不触发**同事端的页面更新提示（画面没变，不值得打扰）；讲稿的每次修改留痕。已分发文稿下次因其他原因接受该页更新时，顺带带上最新讲稿（限当初导出时选了带备注的，见下）
- **导出开关（自动备注）**：组装 / 索引导出时有“添加备注”开关（工作区可设默认）：
  - 开：把每页讲稿写入导出 PPTX 对应页的**演讲者备注**，导出人拿到的是能直接照着讲的讲者版；某页无讲稿时该页备注留空并在导出报告中列出缺讲稿的页
  - 关：导出干净稿，备注为空（适合直接发给客户的场合）
- **其他用法**：客户端浏览成稿时可切换“讲稿视图”逐页对照看稿；CLI 可批量导出整份索引的讲稿为一份文档（Word / Markdown）供打印提词——讲稿数据一份多用，但源头只在版本上

### 3.17 演示厅：成品广场、指定分享与我的库

在“拼页做稿”的工作区之外，产品再设一个面向“拿现成稿去展示”的板块，定名**演示厅**（不叫“成品”；本板块原工作名“展厅”，用户已正式定名“演示厅”，其子区名广场 / 我的库 / 收到的分享 / 群组空间不变）。演示厅里流通的基本单位是**成品条目**：一份可直接对外展示的完整稿——来源是一份索引的某个发布版本解析结果，或一份个人组装记录；条目带封面图（首页缩略图 + 若干页预览）、标题、一句介绍、客户 / 行业 / 场合标签，以及**署名信息：维护人是谁、最近由谁修改于何时**（卡片与详情都标注，修改历史可展开看谁改过哪几版）。**演示厅布局（需求方定）**：演示厅由广场、我的库、收到的分享、群组空间四个**切换式子区**组成，打开默认落广场，子区间切换进入、整页替换；**不设货架主页**——每个条目只在自己子区的视图里出现一处，不在别处整份复制展示（避免重复）。演示厅不设「我维护的」汇总区——本人维护的条目只以绿色外框线在所属子区原位标示（补记十四）。

- **广场（组织范围陈列）**：演示厅的公共区，由管理员运营：管理员可把优质成品直接上架、排序、写推荐语、设分类目录。**成员自荐不是另一套流程，而是演示厅条目在 7.8 下的“申请公开”**：只有在对应组织节点开启“成员自维护与申请公开”后，成员才能把本人维护的条目自荐到广场，并按 7.8 选择公开范围、走审批或免审；功能未开启时不显示自荐 / 申请公开入口，仍可由管理员直接选品上架（管理员本人的可直接上架）。获批条目只对所选组织范围内的账号出现在广场中，选择全公司范围时才公司级可见。广场条目仍受第 7 节权限约束：底层内容无权的账号在广场也看不到该条目。**索引推送同队列**：维护人把索引“推送到演示厅”（见 3.10）生成的待审提交与成员自荐进入**同一个上架审核队列**（管理员视角下队列卡片同样调用全站标准卡片，不另设样式，见补记十七）、共用同一审批通道与状态机；通过后生成的演示厅条目绑定来源索引，卡面与详情标注来源索引名与其目录坐标，后续按来源索引的新发布版本解析；来源索引转历史 / 已作废时，条目标注来源状态，不静默消失
- **指定分享（三种目标）**：不进广场也可分享，分享对象可以是成品条目，也可以是一份**索引**直接分享。目标分三种，落点不同：
  - **分享给个人**：对方在消息中心 / 演示厅“收到的分享”里看到，点**保存**即收进自己库里指定的目录；不保存则不进库，不强塞
  - **分享给部门**（按公司架构的部门树选，见 7.1）：该部门（默认含子部门）的成员人人在“收到的分享”里见到，各自决定存到自己哪个目录；它是发给“这个组织单元”的，之后新加入该部门的人也能看到这份分享
  - **分享给群组**（自建协作组，见 7.7）：不走个人保存——索引 / 条目直接进入该群组的**共享空间**，群组成员打开群组就能看到、使用，随时可再保存进自己的库
  三种分享的都是引用而非拷贝：源头更新时，收下的人照样收到更新提示（与导出文稿同规则）；分享人可随时撤销分享（群组里的由分享人或群组管理员移除）
- **群组空间与收到的分享：同版式同组件，语义分开（呈现一致化）**：演示厅内「群组空间」与「收到的分享」两个区**使用同一套卡片组件与版式**——同样的封面拼图、标题、一行简介、来源 / 分享人 / 时间小字、状态标，同样的打开方式（单击选定、双击 / 打开进详情预览，详情内开始演示、导出），同样的分区标题行样式（标题 + 数量 + 动作）；用户在两区之间切换不需要重新学一套界面。**但两区的落点语义不同，不得合并为一个区、不得改保存语义**：「收到的分享」是分享给个人 / 部门的先落区，条目须点**保存**并选目录才进我的库，不保存不进库、不强塞；「群组空间」是分享进群组后全体成员**直接可见可用**的区（条目级查看 / 使用权，见 7.7），不需要保存即可打开使用，成员可另行**保存到我的库**（存引用）。一致化之后，两区的差别只体现在卡片上的**来源标**（「来自某某的分享」/ 群组名）与**主动作**上：收到的分享的主动作是「保存」，群组空间的主动作是「打开」、「保存到我的库」为次级动作——实现时不得把两者做成完全相同而丢掉这一语义差别
- **我的库（个人陈列）**：每个账号有一套**个人目录**（左目录、右内容的版式与内容页一致）。账号开设时，管理员按“新人基础模板”初始化它：基础目录结构 + 一批官方推荐条目预先放入。此后完全归个人：可自建 / 改名 / 删除目录，可从广场拉入条目、可收下他人分享、可放自己的成品，也可移除（移除只是解除个人引用，不删源头内容）
- **拉入 = 引用**：从广场或分享拉入我的库，只是在个人目录里建一条指向该成品条目的引用；条目本身仍由其维护人维护、按其来源索引 / 组装的更新线走。想改内容的人，走“以此为基础做我的版本”（生成自己的组装 / 索引副本），不直接改动共享条目
- **离线缓存（只缓存实际采用的版本；与 7.6 离线降级互为引用）**：
  - **边界是“我的库”，不是广场全量**：可进入完整缓存范围的只有已进入本人我的库的条目——从广场拉入的、接受分享保存的、自己创建并已采用的。只在广场浏览过、未拉入的条目不缓存完整 PPT，最多保留卡片元数据与缩略图，供离线时浏览目录与辨认
  - **缓存单位 = 实际采用的一致快照**：缓存的不是零散页或“最新指针”，而是用户实际采用那一刻解析到的一整套版本组合——按当时的索引发布版 / 各条目版本组合物化，完整保存放映与预览所需的内容（物化 PPTX 或其全部片段、清单、逐页缩略图、讲稿与必要元数据），保证离线打开时整套版本一致，不会混进半套新版
  - **触发采用混合策略：一次确认 + 被动缓存**：用户第一次**真正使用**我的库中的条目时——开始演示、导出完整稿、以 DeckCraft / PowerPoint 打开完整 PPTX，或点“离线可用”——客户端只询问一次是否开启“自动缓存我用过的稿件”，三选一：**开启自动缓存 / 仅缓存本次 / 不开启**。开启后，后续凡是他真正用过的条目，系统都在后台被动缓存其当时采用的一致快照，不再逐份询问；**只拉入、只浏览卡片、只打开详情看缩略图，都不触发完整 PPT 缓存**。未开启自动缓存时，只有用户在单条上明确点“缓存到本地”才缓存。每条条目始终保留单条动作：缓存到本地 / 移除缓存 / 常驻本地 / 不要缓存（加入排除名单后，被动缓存也跳过它）
  - **历史版本默认不预缓存**：内容块或整稿的旧版本、未采用的形态 / 语言一律不预下载。用户在线主动打开某个历史版本时可临时缓存该版，之后按容量策略淘汰；不因看过一眼历史就把整条版本线搬到本地
  - **快照替换规则**：采用版被新版取代时，只有联网同步完整成功后才以新快照原子替换旧缓存，替换中途失败继续用旧快照。离线期间一律使用已采用的旧快照，并明确标注“离线缓存 · 版本 X · 尚有新版待联网确认 / 同步”（联网确认前写“待联网确认”），不得把缓存版表述为最新版
  - **离线能做什么**：断网或主机不可达时，我的库仍可打开；已缓存条目可看详情、预览 / 讲稿视图，并可沿正式演示路径用 DeckCraft 放映缓存的完整 PPTX；未缓存条目明确显示“未缓存，不能离线打开”。离线期间的个人目录整理等本地操作可排队，联网后同步；发布、申请公开、审批、分享等涉及服务端的操作仍须联网（见 7.6）
  - **状态与容量治理**：我的库卡片与详情显示“已缓存 · 版本 / 大小 / 缓存时间”与“离线可用”徽标；被动缓存显示后台进度且可取消。缓存有总容量上限：空间不足时先淘汰最久未用且未常驻的缓存，**不得静默删除常驻项**，淘汰常驻项或空间仍不足时必须提示用户；用户可把常用条目设为“常驻本地”免于淘汰，也可单条移除缓存、在设置中查看 / 调整容量与自动缓存开关
  - **缓存的三层落点（分工，不得混放）**：**单条**缓存的状态与操作位于**演示厅我的库的卡片内**——卡上直接带缓存状态（未缓存 / 缓存中（进度）/ 离线可用 + 采用版本与大小 · 时间小字 / 常驻标 / 已排除标）与单条操作（缓存到本地、移除缓存、常驻本地、不要缓存，走卡上小按钮或卡片「更多」菜单，守紧凑口径），用户不必离开卡片墙去别处管单个条目。**成规模的管理归内容页**：已缓存到本地的内容（采用快照）在内容页的**「本地缓存」管理视图**集中管理（入口在内容页左侧目录 / 视图切换处）——列出全部已缓存条目及其采用版本、大小、缓存时间与常驻状态，总容量占用一眼可见，逐条可离线打开本地稿、移除缓存、设 / 取消常驻、跳到对应内容块 / 索引；缓存下来的就是内容，其管理属于内容管理，与“内容页只做内容维护”不冲突。**设置页只管全局与策略**——自动缓存总开关、容量上限、管理员缓存策略与个人开关在设置页，设置页不列具体缓存条目
  - **管理员策略优先（更严格者胜）**：管理员可按公司 / 组织节点 / 内容分组设置本地缓存策略——**允许被动缓存 / 仅手动缓存 / 禁止本地缓存**；客户专属或其他高敏感内容可被设为仅手动或禁止缓存。用户个人选择与管理员策略冲突时以更严格者为准：策略为“仅手动”时自动缓存开关不可开启，策略为“禁止”时连手动缓存也不可用；策略收紧后，已有不合规缓存在下次联网校验时清除
  - **失效清除与本地安全**：退出登录不自动等于删除缓存；但账号被停用、条目权限被撤销、条目被撤回 / 下架，或用户把条目移出我的库时，客户端在重新联网校验后必须清除对应内容缓存（只保留必要的审计记录）。本地缓存按账号隔离存储，存放在受操作系统用户目录保护的位置，并应支持静态加密；缓存不得被其他账号或未登录状态打开
- **详情、预览与正式演示（三层分开，不得混称）**：
  - **条目详情 / 预览**：单击卡片只选定；双击卡片或点“打开”先进入条目详情，而不是直接放映。详情呈现封面与逐页缩略图、当前解析版本与来源（来源索引及发布版本 / 个人组装记录）、维护人与修改记录、逐页讲稿，并提供拉入我的库、分享、导出 PPTX 与“开始演示”等动作
  - **预览 / 讲稿视图**：原来的整稿页面流保留，但只叫“预览 / 讲稿视图”，用于逐页浏览、核对画面与照着讲稿预习；它不是正式放映，任何界面文案不得再把滚动缩略图页面流称为“直接演示”
  - **正式演示**：详情中的“开始演示”与卡片上的快捷“直接演示”执行同一动作——先按条目当前解析结果（索引发布版本 / 组装快照，含 3.14 的接收人个性化规则）**物化出一份完整 PPTX**，再进入全屏放映。放映的对象始终是这份当前版本的完整 PPT，而不是客户端拼出的缩略图流
  - **放映由 DeckCraft 承担**：正式放映通过独立的演示适配层调用 DeckCraft 的演示 / 渲染能力（优先复用 deckcraft-engine / deckcraft-render 及 DeckCraft 播放能力，见 8.6）；一期在嵌入接口尚不成熟时，可由适配层启动 DeckCraft 打开物化 PPTX 并进入演示。客户端自制页面流不承担正式放映
  - **观众屏与演讲者视图**：观众屏只显示当前幻灯片、全屏干净放映；演讲者视图在本机或第二屏显示当前页、下一页、该页讲稿、计时与页码 / 总页数。单屏时可切换到演讲者视图，但观众模式不得混入缩略图流、讲稿或管理控件
  - **不可用时明示降级**：DeckCraft 的实际放映保真度以 Phase-0 实测为准（8.6 / 第 10 节）。DeckCraft 不可用、启动失败或物化稿含其暂不支持的效果时，界面必须明确提示，并由用户选择改用 PowerPoint 放映或静态预览，同时说明动画、切换、音视频等效果可能不同或缺失；不得静默降级并冒充同等效果
- **版式**：演示厅延续全站规则——左侧目录、右侧内容；条目以**图形为主的紧凑卡片网格**呈现（封面图 + 标题 + 一行介绍 + 维护人小字），多个并排，绝不一个条目占一整行
- **我维护的条目：绿色外框线（唯一区分）**：演示厅各区（广场 / 我的库 / 收到的分享 / 群组空间）一致——凡**当前用户本人维护的**条目，其卡片加一圈**绿色外框线**作为唯一区分手段：不另设专区、不换卡片样式、不加其他特殊标记（卡面原有的维护人小字照旧）；别人维护的条目无此绿框。**两页颜色语义不同、互不借用**：索引总览的边框色编码的是公开范围（蓝 / 紫 / 绿 / 橙 / 灰色板，见 4.2），演示厅的绿色外框只表「我维护的」这一件事；演示厅内目前没有其他边框色编码、不产生冲突，今后演示厅若引入其他颜色编码须避开此绿框语义
- **不设「我维护的」汇总区（补记十四撤下）**：曾设演示厅页面下方汇总区把本人维护条目再聚合显示一遍，现已删除——本人维护的条目只以绿色外框线在所属子区原位标示，不重复展示。原口径留档：演示厅页面**最下方**另设一个单独的区「我维护的」，把当前用户维护的全部条目**汇总再显示一遍**——它是聚合视图，与主区混排并存：同一条目在它原本所在的区里照常出现，同时被收进本区，方便维护人一处看全自己维护的东西。本区卡片与全页**同款样式**（同一组件、同一字段），绿色外框线在本区同样保留。本区按当前账号取数：每个用户看到的都是自己维护的条目；本人无维护条目时本区不显示（或按全站空态体例给一句提示）。注意与索引总览「我的未公开」沉底区的区别：两者是同一种版式语言（本人条目沉底成区），语义不同——索引那个区收的是**未公开**的索引，演示厅这个区收的是**我维护的全部**条目（含已公开的），不得混淆

## 4. 系统组成

### 4.1 局域网服务端（Rust）

- 运行方式：一个独立服务程序。开发时跑在开发机（本机地址或局域网 IP）；上线时跑在常开电脑 / NAS。
- 数据：一份数据目录 = SQLite（元数据）+ 文件目录（页片段、缩略图、附件）。迁移 = 拷贝整目录 + 客户端改连接地址。**这份数据目录是全公司 PPT 资产的唯一副本**（系统不存原稿，见 3.1），因此备份是一期必备而非可选：服务端按计划**自动定时备份**数据目录，并支持备份到另一台设备 / NAS 路径；提供**一键恢复**（在新机器上还原并自动校验完整性）；管理员可随时手动备份。恢复演练应定期做，备份状态在主机管理页可见
- **存储保留策略**：草稿超过工作区设定天数未动自动清理（提前在消息中心提醒作者）；已发布版本永久保留，长期未被引用的可由管理员**归档**（冷存、仍可查可恢复）；页片段内的媒体文件按内容哈希**去重存储**，多片段引用同一份；主机管理页显示数据目录用量与增长，接近阈值时预警
- 接口：Axum + Tokio 提供 HTTP API；更新通知用 WebSocket 推送，并保留轮询兜底。
- 发现：mDNS 广播服务；同时支持手动填主机地址 / 主机名，界面展示地址（二维码可选）。
- 职责：版本存储与递增、成员与设备确认、发布与冲突检查、给插件下发页片段、客户端更新分发（可选）
- **权限校验在服务端逐请求执行**：每个 API 先按账号的分组授权过滤再返回；页库列表、搜索、缩略图与片段下载、更新查询、导出生成，无一例外（见第 7 节）。

### 4.2 Rust 客户端

- 内容库浏览：**左侧目录树**（一级为用途目录，可建子文件夹，只显示当前账号有权查看的分组，见 3.9）；内容页只做内容维护：点开目录右侧为该目录下内容块的维护浏览（最新页平铺，另有按文稿 / 内容位 / 呈现形态浏览，缩略图墙，文字搜索，版本历史与回退选择）；内容页不设组装与导出（组装工作台见下条与 5.4）；内容页**不设「我的维护」专区 / 板块**——本人维护的内容块就在原目录位置以**绿色外框线**标记（与演示厅绿框同义，见 3.17），不另分区；本人提交后**被驳回**的版本不进正式内容页、他人不可见，只在本人视图中原位显示并以**红 / 粉色标示**（红色系外框 + 「已驳回」徽标，理由在双击打开的详情中看，见 7.8）
- 索引文稿与文件管理：索引页默认先进入**索引总览**（两级结构见下），选定索引后可预览其按条目解析到最新版本的成稿、导出为 PPT、分享、推送到演示厅（见 3.10）、建副本或制作语言对应版；进入索引详情后可查看**提交图**（git log --graph 形态：分支线与标签徽标画在图上，点任意提交看它的 diff 与快照；分支切换、从此提交拉分支、打 tag 发布、发起合并都从图上发起）、导出记录、历次导出的版本快照，并可从索引直接再导一份最新版（见 3.10 / 5.6）
- 附件管理：给索引文稿 / 内容位上传、预览（PDF）、下载 Word / PDF 等介绍材料（见 3.11）
- 索引页组装工作台（组装与导出只在此发起）：在索引页内新建组装 / 新建索引时进入；其内容选用器平铺展示全部内容的最新页（按语言过滤、按内容位展开形态与页——复用内容浏览组件但处于选用模式，不是内容页），点选入组装清单、拖动排序、预览整稿顺序与总页数，选模板后导出新 PPT（见 5.4）；组装成果保存为索引或个人组装记录，也能打开已有组装记录继续调整

- 发布管理：草稿与已发布状态、发布范围、各形态的内容过期提醒（见 6.3）
- 标签管理：给版本打 / 改标签与适用说明（见 3.8）；管理员维护客户与场合词表

- 设置 · 组织管理（管理员，在设置页内，不是顶层页签，见 7.9）：公司 / 部门维护、成员账号开设与停用、按分组给部门 / 成员授权（见第 7 节）

界面技术暂定纯 Rust 路线（egui，见第 8 节复用资产），以 POC 结果为准；备选 Tauri。**界面设计要求**：内容索引 / 成稿页（产品的主页面）按现代桌面应用的视觉标准设计——卡片化的页面墙、清晰的状态徽标（已更新 / 内容已过期 / 专属等）、拖放时的实时预览与顺滑反馈、统一的设计语言（间距、圆角、明暗主题），不得做成老式树表 + 弹窗的观感。此页的设计原型单独维护，是 UI 验收的参照物。

**界面原则：现代化、克制、简洁（全局最高优先级，需求方定）**。先划清边界：本原则**只针对产品页面设计与界面文案**；本规格、功能介绍与设计记录属于设计文档，必须把背景、规则、边界、例外、交互与验收写全，**不因“简洁”删减或压缩文档内容**。产品界面则严格执行以下口径：① **页面里不写功能说明书**——删除 / 收起各页面的解释性段落、规则说明、操作教程、重复提示、设计原理文案与大段副标题，用户不需要先读一段话才知道怎么用；② **只保留完成任务必需的信息**：标题、图形 / 缩略图、对象名、必要的状态徽标、版本号 / 页数等关键数字、维护人 / 时间等小字元信息、短动作按钮；卡片文案最多保留一行简介，分区头只留标题、数量与动作，不带说明段；③ **解释按需出现**：次要说明收进 tooltip、帮助入口、首次使用的一次性引导或详情 / 展开层，默认界面不铺开；确认 / 警告 / 错误只保留一句结论 + 必要动作，不写长篇原因；审计、历史等专业信息放在详情或展开层；④ **视觉同样要克制**：现代视觉语言、统一的间距与层级、克制的色彩 / 阴影 / 装饰、少控件堆叠、留白充足、图形优先——不得做成老式、拥挤、装饰过度或层级混乱的页面，这不只是删字的问题。**控件尺寸同理克制（需求方纠正）**：按钮、页签、筛选片等控件默认紧凑小尺寸（够用、够点即可），页面面积优先留给封面 / 缩略图与文字说明，按钮不得与内容争空间；⑤ **底线**：极简不得删掉关键状态、风险确认、必要操作与无障碍标签。设计目标一句话：**看图即懂，点开再看细节**。原型与正式客户端的每一页（含各对话框与横幅）都按此审计。**主要页面无弹窗（全局规则，需求方定）**：所有主要页面与主要工作面（详情、编辑、设置、合并裁决、更换版本选择、组装工作台等）一律以**整页 / 页内视图**呈现、页内层级进入，不以模态弹窗承载；仅**轻量小确认**（删除确认、驳回理由填写、下架确认等，一句结论 + 必要动作）可保留小浮层；大图预览浮层是预览手段、不是页面，不在此限。
**卡片统一与信息分层（全局原则，本条为上述极简原则的细化，全产品适用）**：① **一张标准卡片（唯一组件，硬规则）**——全产品只设一张**标准卡片**：固定骨架（封面 / 缩略图区、标题、必要信息行、状态徽标位、维护人 + 时间小字、动作区），圆角 / 间距 / 尺寸口径固定；所有页面（演示厅各区、内容页、索引总览与详情图墙、我的库、收到的分享、群组空间等）一律**调用这一张标准卡片**渲染，页面特有信息只能经徽标位与一行小字位传入，不另造卡片结构与样式——索引总览里主索引之下的其他索引（如公司拜访、区域拜访）与主卡片同款同组件，历史卡、未公开卡亦然（差异只在徽标与边框色）。② **卡上只留必要文字**——卡片文字以识别与决策所需为限：名称、一行简介（上限一行）、关键状态 / 版本 / 数量、维护人与时间；不放说明性、介绍性长文字。③ **其余进详情**——详细介绍、历史、记录、关系、完整字段与次级操作一律放进**双击打开的详情**里，卡片层不承载；这与全局基线「单击选定、双击打开」同源：卡片负责扫视与定位，详情负责看全。④ **硬底线不变**——关键状态、风险提示与必要动作不得因精简而从卡片 / 页面上消失。

**索引设计四条验收标准（需求方定：“索引要做的合理，操作及页面要现代化，容易上手和理解”——与上条界面原则并列，专用于索引域，是索引相关一切设计与验收的标尺）**：① **合理**——模型与 Git 心智同构（仓库 / 提交 / 标签 / 分支），一份索引一个仓库、一个坐标；关系靠结构表达，不靠文字解释。② **现代化**——图形优先（内容块图墙、提交图、分支图），拖拽等直接操作；禁止老式的“树 + 表格 + 层层弹窗”形态出现在索引页。③ **易上手**——全站基线不变（单击选定、双击打开）；索引详情的结构操作收敛为三个：**拖拽排序、双击替换、条目间插入**；其余动作（打标签发布、拉分支、合并、锁定、全面编辑）都从提交图上或条目卡上的显性入口发起，不藏菜单深处。④ **易理解**——在索引的任何界面，用户一眼能回答三个问题：**这份索引在哪**（目录坐标常显）、**它从哪来**（分支 / 派生关系在图上）、**它现在是什么状态**（当前分支、当前 tag、哪些条目锁定）。索引总览与索引详情的每次改版都逐项对照这四条验收，不满足的不得默认通过。

**页面结构（需求方纠正）**：**索引页与内容页是两个独立页面**，外加第三个独立板块**演示厅**（成品广场与我的库，见 3.17）——界面最顶部一级页签固定顺序为 **演示厅 → 内容页 → 索引页 → 设置**（需求方定），应用打开**默认落在演示厅**，切换即整页替换，各页独立成篇、互不混排：索引页只管索引本身（条目结构、版本策略、发布版本、谱系、生命周期），内容页只做内容维护（长卷浏览、维护下钻、发布与版本维护，不含组装与导出——组装与导出归索引页的组装工作台；已缓存到本地的采用快照在内容页的「本地缓存」视图集中管理，属内容管理，见 3.17），演示厅只管成品的陈列、分享与个人库，设置页承载个人设置与各级管理设置。**组织管理不再是顶层页签**，它是设置页内的一个区（「设置 · 组织管理」）：原组织页的全部能力（组织树维护、成员归属、7.8 的节点配置与审批中枢、分组授权）随之迁入，功能不减；设置页按管理层级分级展示，见 7.9。语言切换是全局上下文，对各页同时生效。**索引页两级结构（需求方指定）**：索引页默认落点是第一级**索引总览**，不再默认打开某一份“公司介绍”。总览**与演示厅采用一致的页面结构与卡片组件**（需求方定：索引页和演示厅一致即可，不另 invent 一套视觉 / 交互体系）：同样的顶部页签下左导航 + 右内容、同样的搜索 / 筛选位置、同样的紧凑卡片网格尺寸与间距、同样的“封面图 + 标题 + 一句介绍 + 维护人 / 最近修改 + 状态徽标”排版、同样的单击选定 / 双击打开。左侧分区只设与演示厅可类比的三类——**全部索引、按目录（目录树）、我维护的**（开启 7.8 时含待审批状态）；主索引与语言对应不再单设导航分区，只作卡片徽标与工具栏筛选。总览带**状态筛选，固定三档且顺序不可换：使用中（默认，打开索引页即此档）→ 历史 → 全部（排在最后）**——默认只见使用中的索引，“全部”须用户主动切换才把历史索引一并列出。右侧默认**按目录分组陈列**：以文件夹为分组标题（显示完整路径与份数，**份数只计使用中**），组内是**紧凑的索引卡片网格**，一行多张，**主索引在本组内优先展示**（组内第一张，带主索引徽标）。每个目录分组头在“目录名（N 份索引）”之后另有**“历史（N）”按钮**（N 3.10）：该视图默认不显示历史索引，切到“历史 / 全部”档时以当前档为准，历史索引在图上降权呈现。**视图切换的位置（布局定版）**：“按目录 / 按派生关系”切换是小尺寸分段控件，置于**右侧内容区顶部工具行的右端**，与左侧目录树在视觉上明确分开——左侧是目录导航（坐标），右上是本区的视图切换，两者不挤在同一列；该切换只作用于右侧内容区（按目录 = 分组卡片，按派生关系 = 底色标出并带“当前”小标、自动定位到可见区，其**祖先链**（从根到它的分叉路径）以强调线连起，其直接派生（子分支）在其下展开，用户一眼看到自己在图中的位置、来路与下游；高亮只表定位、不改数据，点击图中其他节点可切换查看该分支（或经入口跳到该分支视图）；详情不再把图墙、提交图、版本带、导出记录纵向全量堆叠（此“顶部切换 + 单区显示”对应索引四条验收标准中的**现代化与易理解**：页面不堆叠、当前任务一眼聚焦）。默认区就是这份索引全部条目的**内容块图墙**——每条目一张图形卡：该内容块当前解析版本的全部页面缩略图（多页成组）+ 内容块名 + 形态 / 语言 + 版本策略徽标（跟随最新 / 锁定），按索引顺序逐条排列，**每张条目卡为横向左右布局**（左封面缩略图组、右选择与信息区，补记十九），一眼看全这份索引由哪些块组成。**拖动条目卡即调整索引顺序**（拖拽中显示落点指示，松手生成提交）；**双击条目卡在原位打开替换选择**，就地把该条目换成同一内容块的其他形态 / 版本（规则见 3.10 条目编辑交互）；条目卡之间（及首尾）有**插入点**（点开选用器新增条目，生成提交）；单击条目只选定并显示条目信息与策略；条目卡上的**全面编辑**入口跳到内容页为该条目重选页（内容页顶部带“为索引 X 选页 · 确认返回”上下文条，确认后回详情生效，见 3.10），另有次级入口可跳到内容页维护该内容块本身。详情内另可增删条目、打 tag 发布；**提交图、「历史版本」视图内的版本带（当前分支的 tag 从新到旧，图形化排列，点开进入该 tag 的只读老页面，见 3.10）与导出记录各归其视图区**，内容与功能不减，只是按需切换显示；详情的低频动作（移动到其他文件夹、生命周期变更、删除等）收进一个**「更多」菜单**，不平铺在页面上；个人维护中的索引在总览与详情中沿用 7.8 的状态与权限，不因进入总览而变成正式索引。**版式连贯性（需求方指定）**：内容页内部，右侧内容区是自上而下**连成一体的一条长卷**——各模块的内容依次衔接、页面按顺序连排，模块之间以标题带分隔，不做成互不相连的独立画面；左侧目录树是这条长卷的导航（目录区不带「目录」标题字；一级目录可新建、重命名、拖拽排序，排序后长卷模块顺序同步，补记二十七）：点击目录平滑滚动定位到该模块段落，滚动长卷时左侧高亮随当前可见模块联动（scroll-spy）。右侧内容块支持块级操作：复制 / 剪切 / 粘贴（粘贴到目标目录即生成副本或移动归属）、拖拽到左树目录移动归属、多选（Ctrl / Shift），多选后可「组合为新的内容块」（按 3.15 组成规则新建、记组成来源，补记二十八）。内容可先以草稿上传或加占位页定位置，做好后对草稿 / 占位执行原位替换，替换完成二选一：删除被替换页则新内容沿用其版本号原位接管，不删除则按顺序排号发为新版本（补记三十一）。索引页内部如需按模块分组条目，沿用同样的模块顺序与标题带。**交互基线（需求方定，全局统一）：单击 = 选定，双击 = 打开。** 索引卡片、内容块卡片、页面卡片、缩略图、历史版本条目一律如此：单击只选中（选中的就是卡片当前所示的形态 / 版本，可配合 Ctrl / Shift 多选）；双击才打开——索引卡片的打开 = 进入索引详情 / 编辑，内容块的打开 = 进入下一层级，页面 / 缩略图的打开 = 展开大图预览，历史版本条目的打开 = 展开该版每页。不为不同对象另设打开手势。
**索引总览的陈列与公开范围色板（与 7.8 衔接）**：我维护的索引与全部索引**同款卡片**（同样的封面、标题、版本与状态徽标，不搞特殊样式）。分区只按公开状态分：**已公开的索引**（不论谁维护）与大家的索引**混排**在主区（按目录分组 / 按派生关系视图的规则不变）；**我维护但尚未公开的**——未申请公开、审批中、被驳回待改——统一沉到总览**最下方**的独立区“**我的未公开**”，同款卡片，带状态小标（未申请 / 待审 / 已驳回）；该区**只对维护人本人可见**，他人（含管理员）视角下不出现任何人的未公开区（与不可见不泄露一致）。**卡片边框颜色只编码一件事：公开 / 分享到的组织范围**，与 7.8 申请公开的范围档位一一对应，全产品统一低饱和色板：**全公司公开 = 蓝色边框；上级组织 = 紫色边框；本部门及子部门 = 绿色边框；仅本部门 = 橙色边框；未公开（仅自己）= 灰色边框**（灰色为未公开区专用）。边框色不与状态混用——状态仍走徽标。总览工具行放一个**小图例**（色点 + 范围名，可悬停展开），不占版面。索引详情中公开范围以文字 + 同色标点在标题行小字呈现，与卡片边框呼应。
**派生结构速览已撤下（v2.17 补记九，需求方定）**：总览卡上不再设「派生结构」按钮与底部预览坞——双击进入详情后经「派生关系」视图看分支图即可；本段以下为已作废的原设计，仅留档。原设计为：索引总览的卡片上另设一个条件按钮——**「派生结构」按钮只在该索引有派生关系时出现**：它有直接 / 间接派生分支，或它本身派生自别人（即在仓库分支图上有父或有子）；完全独立、无派生的索引不显示此按钮，不占卡面。**悬停预览**：鼠标悬停在该按钮上（延迟约 300ms 后触发，避免划过误触），页面**最底部升起一块横贯宽度的预览坞**（高度约页面高度的 1/3，坞内图内容可滚动），坞内渲染该索引所在仓库的**分支图**（复用“按派生关系”视图的同一渲染：根在左 / 上、分支按分叉点展开），且**本索引节点高亮**——与详情「派生关系」视图同一套高亮规则（强调色描边 / 底色 + “当前”小标、祖先链以强调线连起）；鼠标移开按钮（且没有移入预览坞）时，预览坞收起消失。**点击钉住**：点击该按钮，预览坞**钉住固定**，不再随鼠标移开而消失；此后鼠标可以离开按钮、**移进预览坞里慢慢看**，并可**点坞内节点**——点其他节点切换高亮查看其关系（分叉点、提交数随之呈现），点节点上的打开入口可进入该索引详情；坞内另有“打开完整派生关系”入口，跳进当前索引详情的「派生关系」视图（完整版）。**解除钉住**：再次点击该按钮、点坞上的关闭按钮、或按 **Esc**，预览坞收起。**钉住与悬停的叠加规则（二选一已定）**：已有钉住内容时，悬停其他卡的「派生结构」按钮只作**临时预览**——临时覆盖坞内容，鼠标移开后**恢复为被钉住的那份**；悬停不改变钉住对象，要换钉住对象须点击目标卡的按钮。**同图两开法**：速览坞与详情「派生关系」视图是同一张分支图的两种打开方式——速览在总览层看大概、定位来路与下游，完整版在详情里切换查看与发起分支操作；两处的数据与高亮规则全局一致。**触摸设备**没有悬停：点按该按钮即按“钉住”打开，再点一次（或点关闭）收起。
**内容块详情（页内层级导航，文件管理器式）**：点开一个内容块不是弹独立窗口，而是像文件管理器 / 素材管理工具（如 Billfish）那样**在内容页内进入下一层级**：当前内容区整层换成该块的下一层——若该块由子块组成（3.15 的组成关系），列子块（仍是块，可继续点开下钻）；同时列出当前形态版本的每一页**缩略图**。即一层里可以既有内容块、又有缩略图，逐层下钻直到页。内容区顶部常驻**层级面包屑**（如 公司介绍 / 合作伙伴介绍 / 渠道伙伴）与返回上一层，点面包屑任意一级直接回到那一层。**双击任一缩略图展开大图预览**（浮层：整页高清图 + 该页讲稿、版本与标签信息，可前后翻页；单击缩略图仅选定该页，遵 4.2 交互基线）；大图与每一层级上都带“编辑”入口，走 5.12 的编辑回路。
**层内布局（需求方指定，自上而下）**：进入一个内容块的层级后，版面分三段：① **顶部：推荐区**——系统推荐的本块内容置顶呈现：默认是主索引当前采用的形态与版本（即 5.4 的“优选”），无主索引采用时用该形态的最新发布版；推荐可以不止一组——例如当前客户 / 场合上下文下有多个推荐形态（如详细版推荐给正式汇报、精简版推荐给简要介绍），每组各带理由标签成组置顶，推荐组有几页就展示几页缩略图。② **中部：子块与当前页**——子块入口与（当前所选形态版本的）每页缩略图。③ **下方：历史版本**——该块的历史版本**从新到旧**排列（v6、v5、v4、v3、v2、v1，直到 v1），不用一行一行的文字列表——与上方完全相同的**图形化呈现**：每个版本是一组紧凑的版本卡片，直接摆出该版全部页面的缩略图（多页版本一排小图）、大号版本号徽标与状态徽标（已撤回等）；发布时间、作者、改动说明只作小字辅助、一行带过，不做主信息。**版本卡片不逐个占满整行**：它们以网格流式并排排列（一行摆多个版本，从左到右、从新到旧），卡片宽度随本版页数自然伸缩、缩略图用小尺寸，v6、v5、v4…一眼扫完，不必逐屏滚动。单击选定某版（4.2 交互基线）、双击展开该版每页大图，并可选用 / 回退。背后的原则是：使用者对图形远比对文字敏感，找东西靠认图不靠读字——内容页的一切列表都优先图形化，文字只作辅助；历史按形态（与语言）切换查看，默认停在推荐区所用形态的那条线。
**嵌套块的调取与推荐选择**：内容块一层里除了直属页面，还可以继续嵌内容块。每个子块卡片直接展示它自己的推荐组（推荐形态 / 版本的全部页缩略图与推荐理由），用户**不必进入子块**，在组装工作台的选用器或向已有文稿插页的流程中可点“选用其推荐”，把该子块推荐的全部页面作为调取页加入组装 / 插入清单（内容页本身只维护，不做组装）。若选用父块整体，调取时按层内顺序**递归展开**：直属页取父块所选形态 / 版本，嵌套块默认取各自的推荐；用户也可在父层逐个展开并改选某个嵌套块的形态 / 版本。组装记录逐节点保存实际选用的内容块、形态与版本，后续更新检查按这些节点分别跟随，不把嵌套块压成一张无来源的散页。

### 4.3 PowerPoint 侧（一期：客户端 COM 桥；二期：加载项）

> 已审定（2026-11-14）：一期不做独立插件。PowerPoint 侧能力由**客户端内置的 COM 桥模块**承担——客户端经 COM 自动化连接本机正在运行的 PowerPoint，对打开的文稿读清单、查更新、原地插删页；提示与审阅界面呈现在客户端里。本文其余各节出现的“插件”均指这项 PowerPoint 侧能力（一期 = COM 桥，二期 = 加载项），职责不变。桥是核心库之外的一个独立适配层（类同 8.5 的分层原则），CLI 经桥同样可触发对已打开文稿的操作。二期加载项目标：Office JS（PowerPointApi 1.2 已含 `insertSlidesFromBase64` / `Slide.delete` / `exportAsBase64` / `getImageAsBase64`，已核实）与 WPS 的插件体系。

职责：

- 以当前登录账号的身份与主机通信；所有面板内容（更新、可切换形态、页库）都只含该账号有权查看的分组内容（见第 7 节）
- 打开文稿时读清单、查主机、列出更新与可切换形态
- 预览（缩略图、文字差异）、逐个 / 全部接受、跳过
- 执行原地替换（流程见 5.3）
- 发布入口：选中页导出为片段，指定内容位与呈现形态，并声明它依据的内容修订与来源（直接编辑 / 分拆自 / 合并自），提交为新版本（是否纳入一期，见第 10 节）

COM 桥的实现要点（一期）：通过运行对象表连接已打开的 PowerPoint 实例（多实例 / 权限级别不一致时给出明确提示）；桥不可用（PowerPoint 未开、非 Windows）时，客户端照常提供库、组装、导出等全部离线功能，只是不提供对已打开文稿的操作。

### 4.4 CLI（与 GUI 同核，AI 全量接管入口）

架构前提：全部业务逻辑实现在一个**核心库**里（版本、索引解析、组装、导出、权限、更新比对），GUI（4.2）、CLI、服务端 API 都只是它的前端 / 适配层——这与 DeckCraft“每个动作都可由 CLI 与 MCP 驱动”的分层一致，其 deckcraft-cli / deckcraft-mcp 即现成参考。

- **覆盖范围（与 GUI 等价，缺一不可）**：登录与主机连接；导入 PPTX 并拆分指认；发布 / 草稿；标签增删与词表维护；目录与索引的增删改、条目调序与版本策略设置（索引域命令按 **Git 心智**提供等价操作：log / branch / tag / diff / merge / checkout 的语义映射到既有 JSON 命令，功能等价规则不变）；组装清单的建立、按索引导出、导出记录查询（组装 / 导出命令归**索引域**，对应 GUI 索引页的组装工作台；内容域命令只含维护类操作，与内容页只做维护一致）；对指定文稿查更新并输出差异清单（含 5.7 四类结构变更）；组织管理（部门、账号、分组授权）；服务端运维（初始化数据目录、备份、成员设备确认）；**全量数据导出**——一条命令把全部片段、附件与元数据（JSON）打包导出为开放格式，保证公司资产不被本系统锁死、可迁出自查
- **AI 友好规范**：
  - 全非交互：一切参数走命令行参数 / 选项 / 标准输入的 JSON，绝不中途提问；破坏性操作用显式 `--yes` 确认，不弹确认框
  - 结构化输出：`--json` 输出机器可读结果（对象带稳定 ID），错误输出到 stderr 且带稳定错误码与非零退出码；人读格式只是同一数据的另一渲染
  - 可脚本化：批量操作支持一次传入多个 ID；导出 / 导入等长操作输出确定的产物路径与 ID；操作尽量幂等，重复执行不产生重复数据
  - 身份与权限：CLI 以某个账号登录（令牌存放于本机受保护文件 / 环境变量），一切操作同样受第 7 节权限约束——AI 接管的是“某个账号能做的全部”，不是绕过权限的后门
  - `--dry-run`：发布、导出、结构更新类操作先预演并输出将发生的变更清单
- **用途定位**：除 AI 接管外，CLI 同时是第 9 节验收场景的自动化执行工具——验收要能以脚本形式重跑，而不是靠人手点 GUI

## 5. 核心流程

### 5.1 发布

> 整份现成 PPT 的首次导入与拆分走 5.8 的导入工作台；本节是单块 / 少量页的日常发布。

1. 作者在客户端导入整份 PPTX，或在插件中选中页导出
2. 把页指认到内容位 + 呈现形态；系统比对指纹，只把真正变了的收为新版本草稿。若这次发布是把已有形态分拆或合并成新形态，按 3.4 记录来源
3. 作者填改动说明，并确认这次发布是否包含内容实质变更：有，内容修订递增；仅是分拆 / 合并等呈现变化，内容修订不变，新形态版本依据同一次修订
4. 选择“仅本地保存草稿”或“发布到主机”。发布时服务端递增该形态的版本号并通知；同时按 6.3 按内容修订标尺检查同内容位其他形态是否已过期
5. **评审评论**：任一版本（含草稿）可挂文本评论——评审者在客户端版本详情里留言（可 @ 维护人），作者据此修改；评论留痕随版本保留，是“内容过审”的记录。评论不改变版本内容本身

### 5.2 打开检查

1. 插件打开文稿，读清单得到各内容位当前（形态，版本，所依据的内容修订）
2. 向主机查询同一内容位的最新状态，分两类呈现，不混淆：
   - **有更新**：正在用的形态有更新的版本，或该形态所依据的内容修订已落后于内容线的最新修订。候选版本须先过 3.8 的客户标签匹配：与本实例客户上下文不相干的专属版本不进入候选、不提示
   - **可替换形态**：同内容位还有其他形态可选——同线内容、粒度与页数不同，可相互替换。列表中标明每个形态的页数、所依据的内容修订、客户 / 场合标签与适用说明；若对方依据的修订更新，还要标明“含更新的内容”
3. 清单里没有的页、主机上没有的内容位，不提示
4. 若该文稿是从某份索引导出的（清单记有来源索引与导出时的索引修订），还要按 5.7 做一次索引差异比对，把新增模块 / 删除模块 / 索引层面的换形态并入同一份更新清单
5. **撤回强提示（最高优先级）**：若文稿正在用的某版本已被撤回（3.5），更新清单顶部单独成栏强提示：注明撤回原因与指定的替代版本，一键按 5.3 换到替代版本。此栏不提供“本版内不再提醒”——只要还在用被撤回的版本，每次打开都提示（与普通更新的克制策略区别对待，因为这是纠错而非升级）

### 5.3 接受更新（原地替换）

对每个被接受的内容位，按以下顺序执行（多个内容位时逐个处理，每处理完一个重新核对位置）：

1. 从主机取目标版本的页片段（Base64 小 PPTX）
2. 记录该内容位在当前文稿中的起始位置与页数
3. 把新页插入到该位置
4. 核对插入的页数无误后，删除该内容位的旧页
5. 更新清单：该位置页群改绑目标（形态，版本）
6. 全部完成后只提示结果，**不自动保存**；用户检查后自行保存到原路径。中途失败则停下并明示未完成项，用户可撤销或关掉不保存，回到替换前状态

形态切换复用同一流程，目标改为所选呈现形态的所选版本（默认最新版）。这覆盖两种方向：分拆方向的 1 页换 3 页，与合并方向的 3 页（或 2 页）换 1 页，引擎处理完全相同（删 N 页、插 M 页）；切换确认界面须显示页数变化（如 3 页 → 1 页）并说明目标形态是更概括还是更展开。整份文稿页数随之增减，后面内容位按绑定 ID 定位，不受页码漂移影响。

**多页组的页级替换（只动变了的那页）**：若新旧版本页数相同、且逐页对位比对（3.5 页位）显示只有部分页变了，同事接受更新时只原地替换那几页（删 1 插 1），组内未变的页原封不动——好处是同事对未变页的本地状态（包括他自己的未保存浏览位置、甚至对其他页的本地改动）完全不受影响。页数不同或几乎整组都变时，退回整组替换。

### 5.4 页库组装与导出（新文稿）

1. **内容选用器**：组装只发生在**索引页的组装工作台**（新建组装 / 新建索引时进入，见 4.2）；选用器是工作台内的工具，复用内容浏览组件但处于选用模式，不等于内容页（内容页只做维护）。选用器由服务端给出“最新页”视图——每个内容位、每种呈现形态只呈现其最新发布版本（所依据的内容修订落后于最新修订的形态带过期标记，见 6.3）。页面以缩略图卡片平铺，卡片显示其客户 / 场合标签与适用说明，可按语言、标签过滤，按文字 / 标题搜索、按内容位筛选。
   组装开始时先定**本次上下文**（目标客户 + 场合，如“西门子 + 详细业务介绍”）：页库据此把匹配标签与“通用”的页排在前面推荐，其他客户的**专属**页默认折叠。组装清单与导出文稿的清单都记下这个上下文，供之后查更新与插页时继续按它匹配（见 3.8、5.5）。
2. **点选**：用户逐页点选要用的页面，有快慢两条路径：
   - **快捷选（默认取最新）**：在选用器的最新页流里直接点选卡片，入选的就是卡片当前显示的那一份——跟随最新策略下即该形态的最新发布版本，不需要任何额外动作
   - **打开选（选形态 / 选版本）**：双击（或点开）卡片进入该内容位的详情：并列展示它的各种呈现形态与各自的版本历史（含页数、所依据的内容修订、客户 / 场合标签与适用说明）。选一页形态的某版本，就用那一版本；选三页形态的某版本，**默认三页全选**，也可只勾其中一两页单独使用
   操作粒度对用户是“页”，但多页形态在卡片流里是一个可展开的**页组**：默认整组入选、整组移动；只取其中部分页时，被摘出的页在组装记录中按“摘选页”单独记绑定来源（源形态与版本），源形态更新时按页单独提示，不自动整组替换。
3. **优选推荐（成稿引导）**：选页不必从零摸索——每选中一页，系统按已选内容给出“接下来选这几页”的推荐：
   - **主来源：索引成稿**。已选页若属于某目录的主索引（3.10），按该索引的序列推荐紧随其后的条目（如选了“公司介绍”的开头页，接着推荐成稿里的第 2、3、4 项），并标明出处（“公司介绍 · 成稿后续”）。同理，已选清单若已构成某主索引的一段前缀，直接提示“一键按成稿补齐其余页”
   - **次来源：历史共现**。其他索引 / 组装 / 导出记录里常与已选页搭配出现的页，按共现次数推荐
   - **优选标记**：同一内容位有多个候选（不同形态 / 版本 / 标签）时，主索引当前采用的那个标“优选”，排在前面；这不妨碍用户改选其他候选
   - 推荐只认当前账号有权查看的分组（第 7 节），且服从 5.4 第 1 步的客户 / 场合上下文：其他客户的专属页不进入推荐
4. **拖动排序**：在组装清单里拖动调整顺序（页组整体拖动；组内顺序固定），实时显示总页数与整稿缩略图顺序，可预览。
5. **选模板**：新文稿需要母版 / 主题来源：从模板库选一个模板文稿作为基底（决定尺寸、母版、主题），所选页按“保留源格式”插入。此项不选则用工作区默认模板。
6. **导出前体检**：点导出后、生成文件前，系统自动过一遍本次组装并列出问题让导出人确认（可逐项处理或知情继续）：混入了与本次客户上下文不同的**其他客户专属页**；引用了内容已过期（依据修订落后）的形态；用了**锁定版本**的条目（提醒不会跟随更新）；所用字体不在公司标准字体清单内、或接收环境可能缺失；含个人占位符但归属人资料缺失（与 3.14 的三选衔接）；来源索引已转历史等。体检不阻断导出（除权限类硬错误），但每一项都必须被导出人显式确认，体检结果记入导出记录
7. **导出**：服务端按组装清单生成 PPTX（生成引擎与页片段同一条路线，见 8.4）；生成前先做个人占位符渲染（含占位符的页按归属人资料替换，缺失项按 3.14 规则先行处理），并按导出选项决定是否把讲稿写入备注（“添加备注”开关，见 3.16），同时完成两件使导出文件“仍连着数据库”的事：
   - 在文件内写入清单：新文稿 ID + 每个绑定实例的（内容位，形态，版本）
   - 在服务端登记组装记录（见 3.7），创建者可在客户端里重新打开这份组装继续调整、再次导出
8. 导出后这份 PPT 与其他受管理文稿完全同权：被作者更新到、打开查更新、逐个接受、切换形态、回退，都按第 5.2 / 5.3 节同一套逻辑走。导出不是一次性快照。

注：组装本质上是手工现搭一份索引。若这份组合要长期复用（如“公司介绍”），把它**存为索引文稿**（3.10），之后浏览与导出按索引走 5.6，不必每次重新点选。

### 5.5 向已有文稿插入未纳入的页

导出之后（以及对任何受管理文稿），可以继续往里插入当初没有选入的页库页面，两个入口做同一件事：

- **插件入口**：文稿在 PowerPoint 里打开时，用插件的页库面板浏览最新页，选中后指定插在当前页之前 / 之后，原地插入并新建绑定实例，随后插件把新组装清单回写服务端组装记录，用户保存的仍是原文件。若要插入的页带其他客户的“专属”标签，而本文稿上下文是另一客户，插入前必须弹出明确警告并经用户确认（防把 A 客户的页误插进 B 客户的稿子）；客户端入口同理。
- **客户端入口**：文稿没有在 PowerPoint 里打开时，在客户端里打开该文稿的组装记录，调整清单（增页、删页、排序）后对原文件重新落盘。若该文件此刻正被 PowerPoint 打开，客户端须提示改走插件入口，不直接改文件。
- 同一内容位重复插入允许（见 3.7 绑定实例），每次插入是独立实例。

另一个相邻情形一并支持：要插入的页**还不在页库里**（本地新做的一页）——在插件里选中该页可“导入页库并登记”：指定内容位与呈现形态（新建或已有）、发布到主机后，它即成为受管理页并建立绑定，流程与 5.1 发布衔接。

### 5.6 索引文稿的浏览与导出（导出即最新）

这是“公司介绍”这类文件的日常用法，也是本系统文件管理的主线：

1. **浏览**：在客户端左侧分组里点开索引文稿，客户端按条目逐项向服务端解析版本（跟随最新 / 锁定版本，见 3.10），在线呈现整稿缩略图顺序与总页数。某条目所用版本自上次导出后已有新版时，该条目带“已更新”提示，浏览者看到的就是新版内容。在详情中可把条目送入组装工作台继续组装（选页规则同 5.4 第 2 步）。
2. **导出**：点导出即调用 5.4 第 6 步同一条导出口：服务端按解析结果（导出那一刻的最新版本）生成 PPTX，写入清单、记导出记录。使用者**不需要**先“把系统里的介绍更新一遍”——索引没有实体文件可更新，导出动作本身完成取最新。
   也可以不整份导出：在组装工作台中以本索引为起点新建组装，勾选其中几页，并立即按优选推荐给出后续选页建议（5.4）。
3. **再导出**：页面后续再更新，回到索引点导出即可得到新一份最新文件；历次导出记录并列保留，可对比各自的版本快照。
4. 导出权限按分组校验（见 7.3）：有查看权不等于有导出权；无导出权的成员可在线浏览，不能生成文件。

### 5.7 按索引分发的结构更新（给已导出副本的更新）

从索引导出的 PPT 分发给同事后（同事装有本软件或插件），后续更新**以那份索引为基准**计算，而不是只看单个内容位有没有新版本：

1. **基准与比对**：导出文件清单里记有来源**三元组（仓库、分支、导出时的 tag / commit 快照）**（见 3.10）。该分支发布新标签后，打开文件时插件把新版本的条目清单与导出快照逐条比对，差异即更新清单（未打标签的提交不触发）。**锁定条目静默跳过**：按其锁定版本比对，源内容块之后出任何新版都不产生变更项、不进入结构 diff（见 3.10 锁定语义）。四类变更：

   | 变更类型 | 触发 | 接受后的动作 |
   |---|---|---|
   | 内容更新 | 条目没变，但所指形态出了新版本（如页面文字改了） | 按 5.3 原地替换该条目的页 |
   | 页数 / 形态变化 | 条目换了形态，或新版本页数不同：一页变三页、两页变一页 | 按 5.3 原地替换（删 N 页插 M 页），确认界面明示页数变化 |
   | 新增模块 | 索引里新增了条目（导出时没有） | 在其相邻条目（前一条目之后）的位置原地插入新模块的页，并新建绑定实例 |
   | 删除模块 | 索引里删掉了条目（介绍不再需要） | 原地删除该条目对应的页，并解除其绑定 |

2. **审阅方式**：同事可**逐条审阅**——每条变更可预览（新页缩略图 / 文字差异；删除类展示将删的页；新增类展示将插入的位置与内容）后单独接受或跳过；也可**全量更新**——一次接受全部变更。两条路都走完后只提示结果、不自动保存，用户检查后存回原路径（与 5.3 同规）。
3. **顺序与定位**：变更逐个执行，每个变更动手前都按绑定实例 ID 重新定位，不依赖页码；前一个变更引起的页数增减不影响后一个。新增模块的插入锚点取它在索引里的前一条目（若前条目已被本地删掉，锚到再前一个仍存在的条目；都没有则插到后一条目之前）。
4. 仅作者**在自己电脑上删页**不触发任何分发；只有索引条目被删除（或内容位被下线）才产生“删除模块”变更。手工组装导出、没有来源索引的文稿不走本节，只走 5.2 的条目级更新。
5. **按线隔离**：比对永远只针对文稿跟踪的那一条**分支**——只沿本分支拉取（pull）它后续的标签与结构变更。同一仓库的其他分支、以及复制出的新索引（另一仓库）发布任何标签，都不会进入本文稿的更新清单；反之亦然。索引被标过期 / 作废 / 删除后的行为按 3.10 的状态定义执行（过期给一次性迁移通知，作废 / 删除后不再查更新）。

### 5.8 整稿导入：导入工作台与 AI 自动拆分

把一份做好的 PPT 第一次纳入系统，走导入工作台（客户端 / CLI 均可，GUI 流程如下）：

1. **选文件定大方向**：导入人选 PPTX，并先定两件全局事：拟归属的目录（可后改）与导入人自己作为默认维护人。系统解析全稿：逐页缩略图、标题、正文、备注、语言、指纹
2. **AI 划板块（自动拆分）**：AI 综合分隔页 / 章节页样式、标题变化、版式切换与内容话题相似度，把连续页划成候选内容块，并给每块一个**置信度**。低置信度的分界（如话题渐变处）高亮，等人工重点看
3. **AI 匹配与新建（三选一，逐块给出）**：
   - **已存在**：指纹或内容与库中某版本一致 → 建议直接关联，不重复入库
   - **归入已有内容位**：与某内容位高度相似但内容有变（或页数变了）→ 建议作为它的新版本（或新形态——页数明显不同且像展开 / 浓缩时提示）
   - **全新内容块**：库里没有 → **AI 自动新建内容位**：生成名称（取板块主题，目录内重名自动避让）、写一句描述（讲什么 + 适用场合）、建议目录归属与语言、顺带建议标签（文中出现客户名 / Logo 时提示相应客户标签，含“专属”可能）
   另有一项顺带检测：封面 / 尾页上疑似个人信息的位置（手机号样式文本、二维码图）→ 建议按 3.14 绑定为个人字段
4. **人工确认归属（工作台）**：导入人逐块（或批量）确认四件归属——**目录**（放哪个分组）、**内容位**（归入已有还是新建、用 AI 的名字还是改名）、**形态与语言**、**维护人**（默认导入人，可指给部门 / 他人）。分界可拖动调整：把两块并成一块、把一块拆成两块，都是一键操作。两种提交模式：
   - **审阅模式**（默认）：全部确认后才入库
   - **快速模式**：高置信度的块（尤其是 AI 新建与完全匹配）自动入库，低置信度的留待审阅；生成一份导入报告，整批导入可一键撤销
5. **入库与纳管**：确认的块按 5.1 规则生成版本（草稿或直接发布，取决于导入人的发布权与选择）；入库前执行**拼回校验**——按清单把整稿拼回，与源文件逐页比对（页数、逐页指纹、缩略图），不过则整批回滚并报告差异页。校验通过后源文件即弃（系统不存原稿，见 3.1）；整份原稿登记为一份文稿（其清单与片段引用），系统产出一份**带清单的纳管版文件**（由片段拼成）供导入人替换原文件继续使用——此后它就是受管理文稿，走第 5.2 节起的全部更新流程
6. **增量再导入**：同一份稿改好后再导入，指纹与匹配会把未变块标“无变化”跳过，只把变了的块提为对应内容位的新版本候选，工作台只审变化部分

CLI 对应：`import` 命令支持 `--ai-split`、`--quick`（快速模式）、`--dir`、`--owner`，输出每块的处置结果（JSON），规则与 GUI 完全一致。

### 5.9 复制粘贴发布（从 PowerPoint 直接粘出新版本）

日常改一页不必走整稿导入。作者在 PowerPoint 里改好后：

1. **复制**：在 PowerPoint 中选中一页或多页，Ctrl+C
2. **粘贴**：切到客户端，选中目标内容位（或在其详情页中），Ctrl+V（或右键“粘贴为新版本”）。客户端从剪贴板取出页片段（Windows 剪贴板含演示文稿片段数据；取不到时自动改走 COM 桥——按源文稿与当前选区从 PowerPoint 直接导出选中页，效果一致）。等价入口：在 PowerPoint 里选好页后点客户端的“取 PowerPoint 选中页”按钮，免去剪贴板一步
3. **确认卡（一步，不繁琐）**：粘贴后弹一张预发布卡，预填：目标内容位 = 刚才选中的那个、形态 = 该内容位当前形态、语言 = 其语言；作者可改目标（换内容位 / 新建内容位）、改形态（作为已有形态的新版本，或另立新形态）、补改动说明、勾“含内容实质变更”（决定内容修订是否递增，同 5.1）。点“发布”即完成
4. **自动成为最新**：发布成功的一刻，新版本自动就是该形态的最新版（新版本号按发布确认卡点选的递增段生成，见 3.5）——**不需要、也没有“设为最新”这个手工动作**；“最新版”在全系统只有一个定义：该形态语义版本序最大的已发布版本。导出、索引解析、更新提示随之都指向它
5. **粘贴旧内容同理**：把旧版本页粘回来发布，仍是追加一个新版本（内容与旧版相同、版本号更新），历史不改写——这就是正确的“恢复旧内容”做法，与 6.4 回退等效但保留痕迹
6. 粘贴的目标若是多页且与目标形态现行页数不同（如给精简版粘了 3 页），确认卡明示页数变化并让作者三选：作为该形态新版本（页数就此变）、另立新形态、或这其实是分拆来源（按 3.4 记来源）
7. 权限与指纹照 5.1 / 7.4：无目标分组发布权则粘贴入口不可用；粘贴内容与现行最新版指纹完全一致时，提示“与最新版相同”并默认不生成新版本（可强制）
8. **只改多页组中的一页**：目标形态现行版本有 N 页（如 3 页）而只粘来 1 页时，确认卡给出页位选择（以组内缩略图点选“替换第几页”），系统把粘来的页拼入现行最新版片段的对应页位、其余页原样保留，发布为新版本——新旧版逐页对位可确切标注“仅第 2 页变更”。同理支持“在组内插入一页”（页数 +1）与“从组内删去一页”（页数 −1），都生成整组新版本；组内页的增删改不改变它属于同一形态这一事实

### 5.10 分发台账与版本分布

导出不是终点：服务端凭导出记录（3.10）+ 各文稿的更新检查回执，形成**分发台账**——按索引 / 按文稿查看：这份稿一共导出过多少份、分别在谁手里（归属人）、各自停在哪个索引发布版本 / 索引修订、落后了几条更新、有没有人还在用已撤回的版本。维护人 / 管理员可对落后者**一键提醒**（走消息中心，5.11）。台账只对有相应管理权的人可见；它是“谁还拿着三个月前的稿子在对外讲”这类事故的治本工具。

### 5.11 消息中心（待办与通知）

客户端内置消息中心，集中承接一切“等某人处理”的事，不只靠打开 PPT 时撞见：

- **给维护人的**：我维护的内容有形态过期 / 译文待更新 / 来源块已更新（3.15）/ 我维护的索引有待审核变更
- **给持有人的**：你导出的稿落后新版本了（来自分发台账的提醒）、你正在用的版本被撤回、你所属索引已转历史并建议迁移
- **给评审 / 被授权人的**：有人请你评审某版本（5.1 评论 @）、你的临时授权即将到期（7.3）
- 一期只做站内消息（客户端 + CLI 可查）；企业微信 / 邮件外发是预留渠道（二期接入同一事件源即可）

### 5.12 编辑回路（点开就能改，改完即更新）

内容块详情 / 大图预览上的“编辑”，一期采用**外部调用**实现（内嵌编辑器见 8.6 的二期深化）：

1. **打开编辑**：在内容块详情点“编辑”，客户端把该块当前形态最新版的片段物化为一个可编辑 PPTX（多页块即整组页；单页摘选则只给该页），放入本机受监视的工作目录，并**调用外部编辑器**打开它。可选编辑器：PowerPoint、WPS、DeckCraft——按用户在设置里定的默认编辑器；未设时按本机已安装情况探测并让用户选一次后记住
2. **编辑期间**：该块在客户端标“编辑中”（含编辑人）；用户在熟悉的编辑器里改，正常保存即可。客户端监视工作文件变化。若改动涉及增删页（页数变了），后续确认时按 5.9 第 6/8 点的规则处理（新版本页数变化 / 组内页位调整）
3. **更新（发版）**：用户回到客户端点“更新”（或保存后客户端主动弹出提示），系统把工作文件与打开时的版本逐页比对指纹：无变化则提示“未做修改”并清场；有变化则弹出与 5.9 相同的发布确认卡（目标块 / 形态 / 改动说明 / 内容修订勾选），发布即新版本
4. **页面即时刷新**：发布成功后，详情页、缩略图、长卷与索引视图立即换成新版本呈现（缩略图与提取文字由服务端重新生成后回填）；“编辑中”标记清除，工作文件归档留痕（谁、何时、改了哪几页）
5. **异常兜底**：编辑器里误改了不属于本块的来源（把别稿内容粘进来）不做拦截——粘贴发布同理，按新内容发版即可；两人同时编辑同一块时，后发版者按 7.6 并发规则成为下一版本，不覆盖先者

## 6. 版本与冲突规则

### 6.1 本地修改

打开时对每页算指纹，与所绑版本不符 → 标记“本地已修改”。该内容位有更新时，给三个选择：用新版（覆盖本地改动）、保留本地（跳过这次更新）、先预览再定。系统不做页内自动合并。**判断细到页**：多页组内逐页比对——同事只改了组内第 3 页、而更新只动第 2 页时，第 2 页可正常接受（页级替换，见 5.3），第 3 页保持他的本地状态不被牵连；只有同一页既被本地改、又被新版改时，才对那一页出三选一。

### 6.2 并发发布

同一种呈现形态以服务端最新版为基准递增。后发布者若基于旧版，发布时收到冲突提示，需确认后作为再下一个版本发布，历史不改写。

### 6.3 内容修订与形态过期

因为所有形态同属一条内容线，过期判断不再靠猜测，而是按内容修订对齐：某形态的最新版本所依据的内容修订，落后于内容线的最新修订 → 该形态标“内容已过期（如依据 r4，最新为 r5）”，在客户端与发布者界面可见，不阻断任何操作。作者把该形态按新修订更新（或由新修订的内容重新合并 / 分拆生成）并发布后，标记自动解除。仅呈现变化（分拆 / 合并）不递增内容修订，不会触发其他形态过期。

### 6.4 回退

所有版本不可变且长期保留。在插件里把某内容位切回任一旧版本即是回退，走 5.3 同一流程。

### 6.5 结构更新的边界规则

- **删到本地改过的页**：某条目在同事本地被改过（6.1 指纹不符），而索引侧又把它删了——删除变更默认不勾选，须单独明确确认后才执行，防误删同事自己的劳动成果
- **拒绝过的变更不反复打扰**：同事跳过某条变更后，系统记下“该文稿已搁置至索引版本 X”；同一版本内不再提示同一条变更，来源索引再发布新版本后才重新进入清单
- **权限过滤同样适用**：结构更新只对当前账号有查看权的分组条目下发（7.4）；无权分组的条目即使被索引删除，也不在同事端产生任何提示或动作
- **作者侧的删除是两步**：把条目移出索引只影响“之后的分发更新”；页库里的内容位与历史版本不因此删除，其他引用它的索引 / 文稿不受影响

## 7. 组织、账号与权限

组织不是附属功能：谁能看见哪些片子、谁能往哪个分组里发布，由这一节决定，并由服务端强制执行（见第 2 节硬性要求 6）。结构参考常见企业组织（飞书 / 企业微信 / 钉钉的“公司—部门—成员”通讯录 + RBAC 授权）裁剪到局域网小团队规模。

### 7.1 组织结构

- **公司（组织）**：顶层。一个局域网部署 = 一家公司（数据模型保留组织 ID，二期可扩多组织 / 云端）。
- **部门**：树形，可多层（如 公司 > 华东区 > 销售部）；成员有且只有一个**主部门**，可兼属多个部门（兼属关系同样获得授权来源）。**公司架构要有专门的设置处**：管理员在客户端「设置 · 组织管理」区维护这棵部门树（新建 / 改名 / 移动 / 删除部门、调整成员归属、设部门管理员），CLI 同步可管（4.4）；部门树同时是授权（7.3）与分享目标（3.17）的选取来源，界面里凡要“选部门”都从这棵树选，不另建名单
- **成员账号**：由管理员开设（局域网版不开放自助注册），账号 = 登录名 + 密码（服务端 Argon2 哈希存储）+ 显示名 + 所属部门 + 对外资料字段（汇报人、手机号、微信二维码等，见 3.14）。停用账号立即失去全部访问；其已发布版本保留署名，不随停用删除。**离职 / 转岗交接**：停用账号时若其名下有担任维护人的内容位与未处理待办，系统提示管理员一键转交给指定接任人（或其部门），转交留痕。
- **登录与设备**：客户端用账号密码登录，服务端发会话令牌；插件不单独登录，复用本机客户端登录态。新设备第一次登录需管理员 / 主机端确认（沿用此前决定）。主机不可达时插件不弹更新提示，客户端可看本地缓存，草稿可存本地待恢复后发布。

### 7.2 角色（系统级）

| 角色 | 权限 |
|---|---|
| 超级管理员 | 全部：组织 / 部门 / 账号管理、所有分组的全部能力、词表维护、主机设置与备份 |
| 部门管理员 | 本部门及子部门的成员管理；被授予分组的管理；在管辖组织节点开启 7.8 高级功能时，审批落入本范围的公开申请 |
| 普通成员 | 仅其被授予的分组能力（见 7.3） |

### 7.3 分组授权（内容级，核心）

授权以 **分组 × 能力** 为单位授予**部门**或**单个成员**；成员的有效权限 = 其主部门 + 兼属部门 + 个人授权的并集（部门授权默认向子部门继承，可关）。**授权可设有效期**（到期日可空 = 长期有效）：跨部门项目借人、借内容时授临时权，到期自动失效并记审计；到期前在消息中心提醒被授权人与管理员，可续期。

能力分四档，逐级包含关系之外单独勾选：

- **查看**：在页库 / 分组栏 / 搜索 / 插件面板中看到该分组内容（含缩略图）
- **使用**：组装、插入、从索引导出 PPT（在“查看”之上）
- **发布**：向该分组导入、发布新版本、管理标签（在“查看”之上）
- **管理**：改分组结构、维护该分组的索引文稿与授权建议（由超级管理员最终确认授权变更）

按需求方的例子落位：

- 管理层 / 少数账号：全部三个分组（公司简介 / 公司技术 / 公司案例）查看 + 使用，部分含发布
- 技术员工：只授“公司技术”分组
- 普通支援人员：只授“公司简介（公司介绍）”分组

### 7.4 强制点（服务端逐项执行，缺一不可）

- 页库与分组栏：只返回有“查看”权的分组与内容
- 搜索与文字索引：结果先按账号过滤，无权内容不出现在结果与计数里
- 缩略图 / 预览图 / 页片段下载：与内容同权，无权直接拒绝（缩略图就是内容本身）
- 更新查询与下发：插件查更新时，只对账号有权分组内的绑定实例返回候选与片段；一份文稿里混有无权分组的页时，那些页在系统内保持“不可见、不可更新”，文件本身已在用户手中的不在系统控制范围
- 导出生成：逐条校验索引 / 组装条目的分组“使用”权，任一条目无权则整份导出拒绝并指明条目
- 发布与导入：校验目标分组“发布”权
- 审计：登录、导出、发布、授权变更记操作日志（谁、何时、对什么）

### 7.5 部署注记

- 服务端口固定并在界面明示；注意 Windows 防火墙与 NAS 的端口放行。
- 密码与令牌只存主机；数据目录迁移（第 2 节要求 5）时账号与授权一并迁移。

### 7.6 并发与一致性规则

- **索引编辑**：索引修订号即乐观锁——提交编辑时若服务端修订已前进（别人在你打开后改过），提交被拒并展示对方的新修订差异，由你基于最新重新提交，不做自动合并
- **同内容位并发发布**：版本号由服务端串行递增，两人同时发布同一形态时后到者基于前者结果成为下一个版本，不覆盖、不丢版；发布确认卡会提示“刚有人发布了 vX”
- **同一文稿多端打开**：更新检查相互独立，原地替换只作用于执行它的那个 PowerPoint 实例；清单以服务端为唯一事实源，本地缓存只读降级（4.3 的离线规则）
- **离线降级与缓存一致性**：主机不可达时，客户端只以 3.17 的离线缓存为准提供只读能力——我的库中已缓存的采用快照可查看、预览讲稿并经 DeckCraft 放映，未缓存内容明确不可用，不拿广场浏览残留冒充完整内容；个人目录整理等纯本地操作可排队待联网同步，发布 / 申请公开 / 审批 / 授权类操作一律不离线执行。联网恢复后先做权限与版本校验：缓存快照只有在新快照完整同步成功后才原子替换，权限被撤销、条目被撤回或账号被停用的缓存按 3.17 清除

### 7.7 自定义群组（协作组）

与按公司架构来的“部门”不同，**群组**是成员自建的协作圈子（如某个项目组、某个客户攻坚组）：

- **建组与成员**：任何成员可新建群组、命名、把其他成员拉进来（被拉者收到通知，可退出）；建组人是群主，可设群管理员、移出成员、解散群组。群组与部门互不隶属，一人可参加多个群组
- **群组共享空间**：每个群组有一块共享空间，成员可把**索引**或演示厅成品条目直接分享进来（3.17）；空间里的东西对全体群组成员可见可用，成员可再把其中条目保存进自己的库。分享人或群管理员可把条目移出空间；空间内条目的呈现与操作形态与演示厅「收到的分享」一致（同卡片、同版式、同打开方式，见 3.17），差别只在落点语义与主动作——群组空间不需保存即可用，主动作是「打开」
- **权限口径**：群组分享只产生**条目级**授权——成员凭群组成员身份获得对已分享条目的查看 / 使用权（打开、组装引用、导出），不因此获得其底层内容分组的任何其他权限，也不获得发布 / 管理权；退出或被移出群组后，该条目级授权随即失效（已保存进个人库的引用同理失效，除非其本人另有权限来源）。这使跨部门协作不必先改组织授权，同时不捅破第 7.4 节的服务端过滤
- 群组列表与空间在客户端有独立入口（亦可从分享流程直达）；CLI 可建组、管成员、分享与移除

### 7.8 成员自维护与申请公开（高级功能）

这是一个由管理员显式开启的组织级高级功能，解决“普通成员自己做的页、索引和成品，先自己维护，成熟后再进入组织正式区”的问题。它不改变 7.3 的分组授权：开启后增加的是一种**以对象归属为边界的自维护权**，不是把整个内容分组的发布 / 管理权下放给所有成员。

- **设置与生效范围**：入口在「设置 · 组织管理」的管理员设置中，配置项包括：① 功能开关（**默认关闭**）；② 公开方式（**需审批**为默认，或**免审公开**）；③ 非实质修改处理（**跟随审批**为默认，或**免审直改**，仅在“需审批”模式下有意义）。配置可落在公司根节点或任一部门节点，未显式配置的子节点继承最近祖先节点的配置；超级管理员可配置全公司并可锁定下级配置，部门管理员只能配置本人管辖且未被上级锁定的节点及其子部门。CLI 可查看 / 修改同一配置
- **谁获得自维护权**：功能开启后，该组织节点内的普通成员可维护**同时满足三项**的对象：由本人上传或创建、当前维护人是本人、且对象归入本人主部门的维护区（或管理员明确指定的被授权组织节点维护区）。管理员转交维护人后，原维护人的自维护权随即结束。它不授权成员修改他人的正式内容、主索引或整个内容分组，也不因上传动作自动获得底层受限内容、其他客户专属内容或无权来源内容的发布权
- **三类维护对象与状态**：同一套状态在内容页、索引页、演示厅保持一致——**我的维护 / 待审批 / 被驳回 / 已公开**：
  - **内容页**：成员通过导入、粘贴或新建产生的自有内容块 / 形态版本先进入“我的维护”，可继续编辑版本、页位、标签、适用说明与讲稿，但不能直接写进正式内容页。**驳回的呈现（需求方定）**：被驳回的版本不进入正式内容页、在他人视图中不出现；只在维护人自己的内容页视图中原位展示，卡片以**红 / 粉色标示被驳回**（红色系外框 + “已驳回”徽标），双击打开可见驳回理由，修改后可重新提交；内容页不另设“我的维护”板块，本人维护的内容块以绿色外框线原位标记（见 4.2）
  - **索引页**：成员可新建并维护自己的索引草稿（条目、顺序、版本策略只能引用其有权查看 / 使用的内容），不能改动正式索引；它与正式索引分开列在“我的维护”中
  - **演示厅**：成员可从自己的组装 / 索引或有权使用的来源制作演示厅条目草稿，维护封面、标题、介绍与标签；这里的**自荐就是该条目的“申请公开”**，不再另设一套上架审批（见 3.17）
- **申请公开与范围选择**：维护完成后，维护人点“申请公开”，确认目标落点（内容目录 / 索引目录 / 演示厅分类）并**只选择一个公开范围**：① 本部门（仅所选部门直属成员）；② 本部门及子部门；③ 本人组织链上的某个上级组织（含该节点及其子部门）；④ 全公司。提交时系统冻结本次申请的对象快照（页面版本、索引修订或演示厅条目修订）；待审期间继续编辑只形成新的维护稿，不偷偷改变已提交快照，维护人可撤回后按新快照重提。上述四档范围在索引总览与详情中以卡片边框颜色统一编码（全公司 = 蓝、上级组织 = 紫、本部门及子部门 = 绿、仅本部门 = 橙、未公开 = 灰，见 4.2 陈列与色板条），改投范围获批后边框色随之变更
- **审批路由与结果**：申请自动路由给**目标范围根节点的组织管理员**——部门范围给该部门管理员，上级组织给该上级节点管理员，全公司给超级管理员 / 公司管理员；目标节点暂无管理员时逐级上送最近祖先管理员。该节点任一有审批权的管理员处理即可，结果留痕。**通过后无需第二次发布动作，申请快照直接进入所选范围的正式内容页 / 索引页 / 演示厅**；驳回必须填写原因，申请回到“被驳回”状态并保留意见，维护人修改后可重新提交。待审批、通过与驳回均进消息中心
- **公开后的可见与使用口径**：公开动作生成带目标组织节点、是否含子部门、申请人、审批人 / 免审标记与时间的发布记录；之后加入该组织范围的成员同样能看到该对象。批准只产生对**该已公开对象本身**的查看 / 使用资格，不产生其所在内容分组的发布 / 管理权；引用型对象仍逐项执行 7.4 的服务端过滤，申请人无权发布或属于其他客户专属的来源内容会在提交前被拦截并指明原因，不能借申请公开“洗”成可公开内容
- **免审公开**：当公开方式设为“免审公开”时，“申请公开”按钮变为“直接公开”：维护人选定范围后立即进入正式区，不等待审批；系统仍完整记录对象快照、范围、操作者与时间，并通知对应组织管理员。对应管理员可随时**下架 / 撤回公开**并填写原因，对象退回维护人的“我的维护”，发布历史不删除。由“需审批”切到“免审公开”只影响切换后的新提交，已在待审批的申请不自动通过，须由管理员继续处理或退回
- **已公开对象的后续维护**：公开对象保留一个线上公开指针和一份维护人的工作稿，二者分离。页面内容、页数 / 形态、索引条目 / 顺序 / 版本策略、演示厅来源稿或其组织范围发生变化，均属**实质更新**：在“需审批”模式下生成待审新版本，旧公开版继续生效，批准后原子切换；范围扩大或改投其他组织时，按新目标范围重新路由审批。讲稿、标签、演示厅介绍等非实质修改按③配置：设为“跟随审批”就与实质更新同走申请；设为“免审直改”才可直接更新线上对象，且仍生成版本 / 审计记录并通知对应管理员——系统不提供绕过该配置的默认直改通道
- **关闭功能后的处理**：关闭某节点的自维护功能后，该范围停止新建、编辑与新申请，入口隐藏；未决申请退回维护稿并标注“功能已关闭”。已经公开的对象不自动消失，继续按原公开范围生效，但转由对应组织管理员维护 / 下架，待功能重新开启或维护人被重新指定后再恢复自维护。所有开关、模式切换、提交、审批、驳回、直接公开、下架与维护人转交均记审计日志；GUI 与 CLI 的状态、错误码和权限判断一致

### 7.9 设置页按管理层级分级展示

设置页是**同一页、按登录者层级拼装内容**（需求方定：“不同的管理层级所展示出来的设置页面是不一样的”）。组织管理位于设置页内（「设置 · 组织管理」区），不是顶层页签（见 4.2 页面结构）。三级口径：

- **超级管理员**：全部设置——公司级全局项（7.8 高级功能总开关与默认值、3.17 离线缓存总策略、备份与主机设置、AI 翻译服务配置、术语库与不译名单、内容语言清单（公司启用的内容语言种类，如中文 / 英语 / 日语，可增删；语言绑定的可选语言与全局语言切换以此为准，双语形态由其中两种语言组合）等）+ 完整组织树与全部节点的组织管理 + 全部审批队列。**公司公共资料**（3.14：公司电话、公众号与二维码、官网、地址等）也在超级管理员维护之列；超级管理员可**指定一名成员为「公司资料管理员」**代为维护公司公共资料，该成员在设置页只多出公司公共资料区，不获得其他超级管理员权限。
- **部门管理员**：只见本人管辖范围（本人部门及其子部门**子树**）的设置——子树内的组织维护、成员归属、本范围的分组授权授予、7.8 本节点的自维护 / 申请公开配置与本范围审批队列；公司级全局项对他**只读可见并标明“由超级管理员维护”**（或不展示），不得修改其他部门与全局设置。
- **普通成员**：只有个人设置——个人资料（3.14 的对外字段：姓名、职务、英文名、电话、邮箱、微信二维码及领英 / X / Facebook / Instagram 等社交账号）、本人的离线缓存开关与容量（受管理员策略上限约束，界面明示上限与来源）、个人偏好；界面中**不出现任何组织管理区**（被指定为公司资料管理员的成员例外，只多出公司公共资料区）。
- **不可见即不存在**：无权看到的设置区不渲染、不留占位，与不可见分组不泄露存在的原则（第 2 节第 6 条）一致；服务端对设置类接口同样逐项校验层级与管辖范围，不靠界面隐藏。CLI 的设置类命令同样按层级裁剪，无权命令返回稳定的权限错误码（4.4 功能等价规则不变）。

### 8.4 风险与使用原则（重要）

- DeckCraft 自述仍处 **alpha** 阶段；其 ROADMAP（2026-11 修订）自评对 PowerPoint 的兼容广度约 84%、就绪度约 55%（目标为 PowerPoint for Mac 16.113）。**不得**在未验证前假定其 PPTX 往返无损。
- 因此页片段的生成设两条候选路线，POC 后定其一或分工：
  - 路线 A：用 deckcraft-pptx 导入模型后导出片段
  - 路线 B：直接在 OOXML 包层面做手术（复制页部件与关系、其余部件原样保留），DeckCraft 源码作为关系处理的参考实现
- 采用时锁定确切版本 / commit（其自身对 craft-libs 也是锁 rev 的做法），并保留上游许可证与声明文件；跟随上游升级需过第 9 节的保真度测试集。

### 8.5 界面壳与多语言（复核结论，2026-11-14）

用户特别指出该系列“有构建 Rust 程序的界面和壳，还有多语言”，复核其清单与源码后确认，此言属实，且成体系：

**桌面应用壳（可直接借鉴 / 复用）**：

- 每个 Craft 应用的桌面壳 = **eframe（egui）应用**：DeckCraft 的 app crate 已处理 wgpu 渲染、系统剪贴板（含图片）、AccessKit 无障碍、原生文件对话框（rfd）、Windows 的 exe 图标与 VERSIONINFO（winresource 构建脚本）、macOS 的“双击 / 打开方式”文档事件等琐碎但费工的桌面集成——这些正是自研客户端最容易低估的工作量
- `deckcraft-ui-egui` 明确设计为**可替换的界面层**，其下的 engine / model / pptx 不依赖它。这与我们“服务端 + 客户端 + 插件共用核心逻辑、界面各表”的结构天然合拍：核心逻辑（版本、片段、索引解析、权限客户端）应放独立 crate，界面只是壳
- `craft-launcher` 是套件级启动 / 分发器，`craft-update` 带 local-mirror ——局域网场景里“主机分发客户端、客户端自更新”一条链现成
- `craft-platform`（平台生命周期服务）、`craft-dialogs`（原生对话框）、`craft-atomic`（原子写文件）补齐壳的边角

**多语言（两层，分开处理）**：

- **界面多语言**：`craft-libs` 的 `craft-i18n` crate 提供查词、回退、复数规则、数字格式与系统区域识别（基于 ICU4X）；翻译内容在独立的 `storytold/craft-i18n` 仓库，以 TSV 目录维护（`locales/<locale>/common.tsv` 全套件共享 + 每应用一份可覆盖），有专门的 CI 校验 crate 验格式，缺失条目自动回退英文，目录以构建期环境变量**可选**嵌入，不嵌入也能编译运行。区域命名用 BCP 47（如 zh-hans）。我们客户端的一期界面语言（中 / 英）可直接沿用这套机制与文件格式
- **内容多语言**：即 3.4 的语言形态（中 / 英 / 日各一份呈现），是业务数据，与界面多语言无关，不要试图用同一套机制解决

结论：第 10 节第 6 条（界面路线）在证据上明显倾向 **egui 路线**——壳、控件、对话框、自更新、多语言一整套已被同一技术栈验证过；Tauri 只保留为 POC 对比项。

### 8.6 与 DeckCraft 的兼容要求

除复用其代码外，产品层面还要与 DeckCraft 本身兼容（用户明确要求）：

- **导入兼容**：在 DeckCraft 里制作 / 编辑并保存的 .pptx，与 PowerPoint 制作的文件同权：可直接导入、拆分、发布、纳入索引，不要求任何格式转换
- **打开兼容**：本系统导出 / 组装生成的 .pptx 须能在 DeckCraft 中正常打开、编辑、另存，无错误、无可见劣化（纳入第 9 节第 13 条测试集一并验证）
- **放映集成（演示厅正式演示，一期）**：演示厅的正式放映由 DeckCraft 承担渲染，通过独立的演示适配层调用 deckcraft-engine / deckcraft-render 及其演示播放能力；一期允许以外部调用方式启动 DeckCraft、打开系统物化的完整 PPTX 并进入演示，是否进一步嵌入播放器由 POC 决定。Phase-0 必须实测 DeckCraft 对真实业务稿的放映保真度（版式、图表、动画、切换、音视频与双屏演讲者视图）；未达标或不可用时按 3.17 明示降级到 PowerPoint 放映或静态预览，不得把客户端缩略图流称为同等放映
- **清单往返兼容（关键）**：文稿内嵌清单（3.1）必须经得起 DeckCraft 的“打开—另存”往返而不丢失、不损坏——清单的嵌入位置与格式要选标准 OOXML 扩展点，并在 POC 中实测 DeckCraft 往返后清单仍可被插件读出。若实测不保，再评估改用 DeckCraft 会保留的部件形式
- **可选的深度集成（二期候选，一期不做）**：服务端借 deckcraft-render / deckcraft-pdf 生成缩略图与预览（不依赖客户端导出图片）；客户端内嵌 DeckCraft 引擎做离线预览 / 轻编辑。是否提前到一期，由 POC 结果与第 10 节第 9 条决定
- **内嵌编辑器（二期深化，需求方提出）**：把 Craft 的 PPT 编辑器（deckcraft-engine + deckcraft-ui-egui，与客户端同为 Rust / egui 栈，嵌入在架构上可行）直接包进客户端——在内容块详情里就地编辑、保存即发版，免去外部程序跳转；并随 DeckCraft 上游版本更新而跟进升级。**一期不做内嵌**：编辑走 5.12 的外部调用回路，且 DeckCraft 本身就是可被调用的外部编辑器之一——用户在一期就能用上 Craft 编辑，只是以独立程序形态。二期是否内嵌，取决于 POC 对 deckcraft-ui-egui 可嵌入性、与本系统片段 / 清单格式对接成本、跟随上游更新的维护成本三项评估

## 9. 一期验收标准（场景）

1. 30 页文稿，其中 5 个内容位有同形态新版本：打开时精确提示这 5 个；全部接受后仍在原文件、原路径，页内容为新版，未更新的内容位不受影响。
2. “合作伙伴介绍”在精简·中文（1 页）与详细·中文（3 页）之间来回切换：既包括分拆方向（1 页换 3 页），也包括合并方向（3 页换 1 页）；均原地完成，总页数相应 −2 / +2，切换确认界面正确显示页数变化与概括 / 展开方向，后续内容位定位正确，保存后重开无修复提示。
3. 内容实质变更并递增内容修订、只更新了详细形态时：用详细版的人收到更新提示；用精简版的人打开时能看到该内容位标“精简版依据的内容已更新”，可选择等精简版更新、或直接换到详细版，不被强制替换。随后作者发布依据新修订的精简版，过期标记自动解除。
4. 某页被本地改过又有新版：打开时标“本地已修改”，接受前给出明确选择，不静默覆盖。
5. 主机迁移：把数据目录从开发机拷到另一台机器，改地址后客户端与插件正常连接，版本与绑定关系完整。

17. AI 翻译闭环：对一份中文索引批量发起英、日翻译，产物为草稿而非已发布；术语库中的产品名按标准译法出现，不合术语处被标出；某页英文译文过长溢出的文本框有明确标记；校对后发布，英文 / 日文形态出现在内容位详情中且与中文按修订正确对位。源头中文再出新修订后，只有变化页进入增量重译队列，未变页的已校对译文保持不变。
18. 双语页：由绑定的中、英单语形态辅助生成一份中英双语草稿（上下对照），人工定版发布后，双语形态与单语形态并列可选；在文稿中把某内容位切到双语形态，原地替换成功；随后英文源头更新内容修订，双语形态被标“待同步”。
19. 个人绑定：封面版本中把汇报人、手机号文本框与二维码图片框绑定为个人字段后，入库片段为模板态（无任何真人信息）；账号 A（已填资料）导出含该封面的稿子，封面显示 A 的姓名、手机号与二维码；账号 B 导出同一索引，显示的是 B 的；封面后来发新版，A 在 PowerPoint 里接受原地更新后，页上仍是 A 自己的资料；账号 C 未传二维码时导出，事先收到缺失提示并按其选择留空导出。
20. 跨块合成：把“公司介绍”块与“发展历程”块各取一页合成为一页新块“公司概览”，新块有独立版本线且首版来源可查；随后“发展历程”发新版，“公司概览”被标“来源已更新”，执行重新合成得到草稿，调整后发布为其 v2；合成时若来源之一带某客户“专属”标签，新块被要求确认标签继承，不默认洗成通用。
21. 索引标签与分支隔离：“公司介绍”仓库在某提交上打标签 V1.0 时导出一份 PPT 给同事（绑定三元组：该仓库 + main 分支 + V1.0 快照）；作者继续提交增删条目但未打标签，同事打开无任何提示；打标签 V1.2 后，同事打开得到对应的结构更新清单。另从 V1.0 拉出分支“展会版”改条目并打其 V1.0 标签：从 main 导出的 PPT 不收到该分支的任何更新，从分支导出的 PPT 只跟分支走；任一索引详情的提交图里能查清谱系（哪条分支从哪个 tag / commit 分叉、分叉后各自提交数）。
22. 索引生命周期：把某索引标为“历史”（原称“已过期”）并指向替代索引后，新导出被阻止并给出提示，其存量导出文稿只收到一次迁移通知；标为“已作废”后，存量文稿不再收到任何更新提示且文件本身不受影响；删除（软删）后该索引从目录消失，其分支与复制出的新索引仍可正常打开与发版。

31. 编辑回路：在客户端点开一个三页内容块，看到三页缩略图，点第二页缩略图展开大图；点“编辑”（默认编辑器为 PowerPoint）后片段在 PowerPoint 中打开，改掉第二页文字并保存；回客户端点“更新”，比对显示仅第 2 页变更，确认发布为新版本后，详情页与长卷中的缩略图立即换成新版；同流程把默认编辑器换成 WPS 与 DeckCraft 各走一遍，结果一致。

37. 索引总览与两级编辑：成员打开索引页时默认看到索引总览而非直接进入“公司介绍”：页面骨架与卡片组件与演示厅一致，左侧分区只有全部索引、按目录、我维护的三类，主索引 / 语言对应与状态走卡片徽标和工具栏筛选，右侧默认按目录分组、以紧凑网格并排显示其有权查看的“公司介绍”（主索引）、展会版副本、“产品与解决方案”“技术能力”“客户案例”等索引（中文语境下英文对应版不作为卡片出现）；无权索引不出现在列表与计数中。每张卡以该索引第一页整图为封面（补记十三），正确显示当前发布版本、维护人、最近修改与状态，以及主索引徽标（条目数 / 总页数、目录坐标与谱系已按补记九撤下卡面、进详情）。单击“公司介绍”只选定并亮出预览成稿、导出、分享、建副本与新建索引等动作（制作语言对应版在详情内），不进入编辑；双击卡片或点“打开编辑”后进入第二级详情，面包屑可返回总览，原有条目增删、拖拽排序、版本策略、发布版本、语言对应、副本谱系、生命周期与导出记录均可操作，并能从一个条目跳到内容页查看对应页面。
38. 演示厅详情与 DeckCraft 正式演示：成员在演示厅单击一套稿只选定，双击进入条目详情 / 预览而不是放映，详情中能核对逐页缩略图、当前解析版本与来源、维护人 / 修改记录、讲稿及导出 / 分享动作；原页面流只以“预览 / 讲稿视图”存在。点详情中的“开始演示”或卡片上的“直接演示”后，系统先按当前解析结果物化完整 PPTX，再由 DeckCraft 进入全屏放映：观众屏只显示当前幻灯片，演讲者视图同时显示当前页、下一页、讲稿、计时与页码。临时禁用 DeckCraft 后再点演示，界面明确提示 DeckCraft 不可用，并让用户选择 PowerPoint 放映或静态预览，同时说明动画、切换与媒体效果可能不同，不静默降级。
39. 离线缓存（一次确认 + 被动缓存）：成员把三套稿拉入我的库，又在广场浏览了第四套但未拉入。第一次真正使用第一套稿（点开始演示）时，客户端只询问一次是否开启“自动缓存我用过的稿件”，他选择开启，第一套稿当时采用的一致快照被缓存；之后他实际演示第二套稿时，系统在后台被动缓存其采用快照并显示进度，不再弹窗询问；第三套只被拉入并打开详情看过缩略图，从未真正使用，因此没有完整 PPT 缓存；三套稿的历史版本与其他形态均未被预下载。随后断开主机：第一、二套仍能打开详情、看讲稿并用 DeckCraft 放映缓存版本，卡片标明“离线缓存 · 版本 X”；第三套显示未缓存、不能离线打开完整内容；广场里只浏览过的第四套离线时只有卡片元数据与缩略图。恢复联网后，系统提示第一套已有新版，只有在他确认同步且新快照完整下载后才替换旧缓存。若管理员把第二套所属分组策略改为“禁止本地缓存”，下次联网校验时其缓存被清除且手动缓存入口不可用，用户自己的自动缓存开关不能绕过该策略。

40. 内容页职责收敛：在内容页任意目录与内容块下钻层中，全程只有维护动作（浏览、发布、版本、标签、讲稿、语言绑定、附件、撤回、申请公开），不存在组装托盘、拖拽组装与导出入口，单击选定只服务于维护、双击打开即进入维护下钻；在索引页打开组装工作台，用选用器点选页面（含一个 3 页形态整组、一次摘选单页）、拖动排序、按优选推荐补齐、选模板并导出新 PPT 全流程走通，组装成果可存为索引或个人组装记录。
41. 目录坐标常驻与派生谱系：任一索引在总览卡片（按目录分组与跨组搜索结果中）、详情顶部坐标栏、导出记录、分享对话框与搜索结果中，目录坐标（完整路径）均常显不消失；把一份索引“移动到其他文件夹”后坐标随之更新且留变更历史，其已导出 PPT 仍按索引 ID 正常跟随更新。总览切到“按派生关系”视图，能从根索引沿连接线追到第三代子索引，卡片谱系行与详情“归属与谱系”条一致；中文语境总览中不出现英文对应索引卡片与语言对应徽标，打开该索引详情后才见语言对应入口与状态，且语言对应不被画进派生谱系、不被误认为子索引。

42. Git 式分支与合并：从“公司介绍”仓库的 V1.2 拉出分支“西门子定制”改条目，main 同时并行演进；分支打标签后，只有跟踪该分支的 PPT 收到结构更新，跟踪 main 的不受影响。随后把该分支合并回 main：只有单边改过的条目自动合入；同一条目双边都改过的逐条弹出裁决（用我的 / 用对方的 / 手动选条目形态与版本策略），裁决完成后生成一个 merge commit 并记录来源分支与裁决结果。另有一份此前“复制为新索引”的独立仓库，全程不参与合并、也不受影响。

43. 索引详情图墙与就地替换：双击打开“公司介绍”索引详情，顶部坐标栏与归属 / 谱系条之下，全部条目以内容块图墙呈现（每卡含该块当前解析版本的全部页缩略图、形态 / 语言与跟随最新 / 锁定徽标），顺序与索引一致；拖动其中一张条目卡换序，落点指示正确，松手后提交图多出一个“排序变更”提交且顺序生效；双击“合作伙伴介绍”条目卡，原位打开替换选择（图形化列出该块其他形态与版本），选详细 · 中文 3 页最新版后，卡片即时变为 3 页组、总页数 +2，提交 diff 记为条目形态变更；再双击改选该形态的一个历史版本，条目自动转为锁定版本并在卡上标明；全程不离开索引页。

44. 条目插入、全面编辑重选页与锁定：在索引详情图墙中点两个条目之间的插入点，用选用器选入一个新内容块，图墙在该位置多出一条目且提交图多出“新增条目”提交；对一个 3 页条目点“全面编辑”，跳转到内容页并直接打开该内容块（顶部有“为索引 X 选页 · 确认返回”上下文条），把选页改成第 1–2 页后确认返回，条目变为 2 页摘页绑定并生成提交；把另一条目锁定在历史 v2 后，其内容块发布 v3：索引预览、从本索引新导出、以及此前已导出的 PPT 打开检查三处，该条目内容均保持 v2、无任何更新提示，卡上只有“源内容块已出新版 v3（已锁定不跟随）”弱提示；维护人手动解除锁定后，该条目才恢复跟随并在下次导出 / 检查时解析到 v3。

45. 语义版本号与索引老页面：给某内容块发布新版本时，发布确认卡给出大版本 / 小版本 / 文字调整三段点选——页数变化的变更预选大版本、仅改错别字的变更预选文字调整，发布人改选小版本后生成的新号按小版本段递增且版本记录含预选与改选；该版详情中正式显示修订时间（精确到分钟）、作者、改动说明与依据的内容修订号。打开某索引详情，切到「历史版本」视图，版本带从新到旧列出其标签；点开旧标签进入只读老页面，图墙冻结在当时快照，其中一条目引用的内容块版本已被删除，页面以同块同形态的次近存续版本替代并标注“原版已删 · 以 X.Y.Z 替代”，从老页面导出整稿后，导出记录中能查到该替代项与来源 tag。

46. 拖拽插入历史与级联重编号：某内容块详细形态的历史线为 …2.3.1、2.4.0、2.5.0…，维护人把一张新版卡拖到 2.3.1 与 2.4.0 之间并选“小版本”递增，插入版得号 2.4.0，原 2.4.0 顺移为 2.5.0、原 2.5.0 顺移为 2.6.0，整线顺序与编号严格单调；此前把条目锁定在原 2.4.0 的索引，其条目按内部 ID 仍指向同一版内容，卡上显示新编号 2.5.0；此前导出的一份 PPT 打开时按 ID 显示现行编号，其导出记录仍保留导出当时的编号且可对照现行编号；被顺移各版的详情中“编号变更记录”逐版可查（原号 → 新号、原因、操作者、时间），且各版内容、修订时间与状态未变。
47. 索引总览默认档、分组历史按钮与推送演示厅：成员打开索引页，总览默认停在“使用中”档、只见使用中的索引，状态筛选三档顺序为使用中 → 历史 → 全部（“全部”在最后）；“公司介绍”分组头显示“公司介绍（2 份索引）”且份数只计使用中，其后有“历史（1）”按钮，点开后在本组内并列加载出 1 份带“历史”徽标、降权呈现的历史索引卡，分组头份数不变，再点收起；维护人把“公司介绍”主索引点“推送到演示厅”，提交进入演示厅广场审核队列（与成员自荐同一队列），管理员通过后该索引在广场上架可见，条目标注来源索引名与其目录坐标，来源索引随后打新 tag，广场条目解析随之更新、无需重新推送；另一份索引推送后被驳回并写明理由，其详情显示驳回理由与“修改后重新推送”入口，修改后重推再次进入待审；一份 main 尚无已发布 tag 的索引点“推送到演示厅”时被提示先发布，不能推送。
48. 导航与设置分级：应用打开默认落在演示厅，顶层页签顺序为演示厅 → 内容页 → 索引页 → 设置，顶层无“组织管理”页签，组织管理只在设置页内出现。同一设置页以三种身份打开内容不同——超级管理员见全部设置（公司级全局项、完整组织树与全部节点管理、全部审批队列）；部门管理员只见本人部门及子部门子树的组织维护、成员归属、本范围授权与 7.8 配置和审批队列，公司级全局项只读并标明由超级管理员维护，且通过任何入口（GUI 与 CLI）都改不到其他部门的配置（CLI 返回权限错误码）；普通成员只见个人设置（个人资料、本人离线缓存开关与容量且标明管理员上限、个人偏好），界面中不存在任何组织管理区与占位。
49. 总览陈列与范围边框色：成员 A 维护三份索引——一份已按全公司公开、一份仅本部门公开、一份未申请公开。A 打开索引总览：前两份与他人索引以同款卡片混排在按目录主区，边框分别为蓝色与橙色，工具行图例可查对应关系，详情坐标条的范围文字与标点同色；第三份只出现在总览最下方的“我的未公开”区（灰色边框、带“未申请”小标）。管理员与同事打开总览，均看不到 A 的未公开区。A 把第二份的公开范围改投为本部门及子部门并获批后，其卡片边框变为绿色，详情范围标点同步变色。
50. （已作废）派生结构速览——v2.17 曾定：总览卡「派生结构」按钮悬停升起底部预览坞、点击钉住。**需求方于 v2.17 补记九撤下此设计**：总览卡不再有派生结构按钮与预览坞，派生关系只在双击进入索引详情后经「派生关系」视图查看。本场景作废，不再验收。

## 10. 待确认 / 待实测

1. 同事的 PowerPoint 具体版本与授权形态（是否支持 PowerPointApi 1.2），操作系统是否全 Windows — 决定插件走 Office JS 还是 COM 兜底。
2. WPS 的使用占比 — 决定第二期 WPS 插件的优先级与路线。
3. 常开主机的形态：Windows 电脑还是 NAS（品牌 / 系统 / 能否跑 Docker 或原生服务）— 决定服务端打包方式。
4. 发布入口一期是否必须在插件内完成（选中页直接发布），还是先只在客户端导入发布、插件专心收更新。
5. 页片段生成路线 A / B — 由第 9 节第 13 条的保真度 POC 结果决定。
6. 客户端界面路线：egui（随 DeckCraft 复用，证据见 8.5，倾向已明确）还是 Tauri — POC 中各做一个内容库页面原型后最终定。
7. 组织的两个细节默认：一名成员可兼属多个部门（7.1 已按此设计）、部门授权默认向子部门继承（7.3 已按此设计）——若与公司实际管理习惯不符再改。
8. 账号开设方式：一期按管理员开设（7.1）；是否需要“邀请链接 + 自行设密码”再议。
9. DeckCraft 兼容深度：一期定为文件级兼容 + 清单往返验证（8.6）；服务端渲染缩略图、客户端内嵌 DeckCraft 编辑等深度集成是否提前，看 POC 与实际需要。
10. **（已定）一期架构形态：两件套**。客户端（含 COM 桥）+ 服务器，见 4.3；二期补 PowerPoint / WPS 加载项。
11. DeckCraft 放映能力与保真度：deckcraft-engine / deckcraft-render 当前可调用的演示接口、外部启动方式、版式 / 图表 / 动画 / 切换 / 音视频支持范围，以及观众屏 + 演讲者视图的双屏实现方式——由 Phase-0 实测决定嵌入播放器还是外部调用 DeckCraft；若关键效果不达标，须在开发前定明示降级口径与是否调整一期范围。

## 11. 分期

- **第 0 期 POC**：保真度测试（路线 A / B 对比）+ 在真实 PowerPoint 版本上验证 insertSlidesFromBase64 / Slide.delete 的原地替换闭环 + 插件读清单查更新的最薄链路。
- **第 1 期 局域网 MVP**：本规格第 1–8 节全部内容。形态为两件套：Rust 客户端（GUI + CLI，内含 PowerPoint COM 桥）+ Rust 服务端。
- **第 2 期**：PowerPoint / WPS 加载项（插件形态）、按部门 / 分组的强制推送、云端 / 跨网与多组织（如仍需要）。
