# PPT 管理器 — 设计需求说明

> 本文档是本产品的设计需求说明。它完整地说明这个产品要做成什么样、各项决定为什么这样定、规则与边界在哪里，供需求方通读评审，也可用于向开发方、合作方说明产品。产品暂定名为「启幕」（2026-11-14 定，暂定，后续可更换；正式定名前商标 / 公众号查重尚未进行），本文仍暂以「PPT 管理器」泛称。逐条规则、字段定义与验收口径，以《PPT应用-局域网版规格》（v2.17，以下简称「规格」）为准；面向使用者的功能叙述见《PPT管理器-功能介绍》。

## 一、产品概述

### 1.1 定位

**面向大企业的 PPT 内容管理平台，第一期以局域网形态部署。**

这套系统管的不是一个个 PPT 文件，而是公司全部演示内容本身：内容按话题拆开存放在服务器上，各自留版本；需要一份整体文稿时，用「索引」把内容按顺序引用起来，导出时才临时组装成 PPT；稿子交付出去之后仍与服务器上的源头相连，源头一有新版，文件打开时就收到更新提示，并能在**打开的原文件里原地换页**。

局域网是第一期的部署形态，不是产品定位的上限。组织、部门与权限从第一天起就按大公司的形态建模，数据模型为将来扩展到多组织、云端预留。

### 1.2 要解决的问题

- **同一份内容散落无数文件**：公司介绍、产品说明这类内容在几十份 PPT 里各存一份，改一处要满世界找文件，改漏、改错是常态。
- **稿子发出即失控**：文稿发给同事后，作者更新了源头，对方手里仍是旧版，没人知道谁在拿着三个月前的稿子对外讲。
- **同一话题版本混乱**：同一话题有精简版、详细版、中文、英文、给不同客户的不同说法，长期并存却没人说得清该用哪一版、哪一版是最新。
- **权限没有边界**：技术资料与对外介绍混在一起流传，谁能看哪些材料、谁能往外发，没有服务端强制的边界。

### 1.3 核心价值

产品的价值主张可以收成三条：

1. **页面级版本管理**：内容按「内容块」拆分管理，每块有自己的形态、语言与版本线，改哪块发哪块，不再整稿复制来复制去。
2. **索引化组装**：整体文稿在系统里只以「索引」（一组有序引用）的形式存在，不存一份会过期的整稿文件；浏览与导出时按索引逐项解析到最新版——系统里永远不存在「那份公司介绍忘了更新」这回事。
3. **原地更新分发**：已分发的文稿通过内嵌清单与源头保持连接，更新在原文件内原地替换（不生成新文件），逐条可审阅、可跳过、可回退。

### 1.4 设计原则（贯穿全文）

- **内容只有一份源头**：服务器是唯一事实源，PPT 文件是按索引临时组装出的交付物。
- **身份靠 ID，不靠位置**：页面、版本、索引的身份都是稳定 ID，页码只是当前位置，任何逻辑不得用页码认页。
- **权限在服务端强制**：界面隐藏不算权限；无权的内容在任何接口里都不出现，连「存在」都不泄露。
- **发布即生效、历史不改写**：新版本发布自动成为最新，旧版本不可变、长期保留；纠错永远靠发新版或撤回，不靠改历史。
- **GUI 与 CLI 同步等价**：全部功能有一套命令行接口，功能等价，供 AI 全量接管与自动化验收。

## 二、用户与组织

### 2.1 组织结构

系统按真实公司的架构建模：**公司（组织）> 部门树 > 成员账号**。

- 一个局域网部署对应一家公司；部门是树形结构，可多层（如 公司 > 华东区 > 销售部）。
- 成员有且只有一个**主部门**，可兼属多个部门，兼属关系同样构成授权来源。
- 账号由管理员开设（一期不开放自助注册），密码以 Argon2 哈希存于服务端；账号停用立即失去全部访问，其已发布版本保留署名。停用时若名下有担任维护人的内容与未处理待办，系统提示管理员一键转交接任人并留痕。
- 客户端用账号密码登录，服务端发会话令牌；PowerPoint 侧不单独登录，复用本机客户端登录态；新设备首次登录需管理员或主机端确认。
- 部门树在「设置 · 组织管理」中维护（新建 / 改名 / 移动 / 删除部门、调整成员归属、设部门管理员），CLI 同步可管；界面里凡要「选部门」，都从这棵树选，不另建名单。

### 2.2 三种系统角色

| 角色 | 职责范围 |
|---|---|
| 超级管理员 | 全部：组织 / 部门 / 账号管理、所有分组的全部能力、词表维护、主机设置与备份、公司级全局配置与全部审批队列 |
| 部门管理员 | 本部门及子部门的成员管理；被授予分组的管理；管辖节点内的自维护功能配置与公开申请审批 |
| 普通成员 | 仅其被授予的分组能力；开启高级功能时另有对象级的自维护权（见 2.5） |

### 2.3 内容分组与能力授权

**内容分组（目录）既是内容的组织单位，也是权限的划分单位。** 客户端左侧目录树的一级目录按用途划分（如公司介绍、公司技术、公司案例），可建子文件夹；每个内容块、每份索引有且只有一个主分组（它在目录树里的「家」），跨分组的发现靠搜索与标签，不靠多处安家。

授权以**分组 × 能力**为单位，授予部门或单个成员：

- **查看**：在页库、目录、搜索、PowerPoint 侧面板中看到该分组内容（含缩略图）；
- **使用**：组装、插入、从索引导出 PPT；
- **发布**：向该分组导入、发布新版本、管理标签；
- **管理**：改分组结构、维护该分组的索引与授权建议。

成员的有效权限 = 主部门授权 + 兼属部门授权 + 个人授权的并集；部门授权默认向子部门继承，可关闭。授权可设**有效期**（到期日可空，空即长期有效），到期自动失效并记审计，到期前在消息中心提醒被授权人与管理员，可续期。典型落位：管理层看全部三个分组；技术员工只授「公司技术」；普通支援人员只授「公司介绍」。

服务端对每个请求逐项执行权限过滤：页库与分组栏、搜索结果与计数、缩略图与片段下载、更新查询与下发、导出生成（逐条校验，任一条目无权则整份拒绝并指明条目）、发布与导入——缺一不可。登录、导出、发布、授权变更均记审计日志。

### 2.4 自定义群组

群组是成员自建的协作圈子（如项目组、客户攻坚组），与按公司架构来的部门互不隶属，一人可参加多个群组。任何成员可建组、拉人（被拉者可退出）；群主可设群管理员、移出成员、解散群组。

每个群组有一块**共享空间**：成员可把索引或演示厅成品条目直接分享进来，全体成员打开群组即可见可用，可再保存进自己的库。权限口径是关键约束：群组分享只产生**条目级**授权（对已分享条目的查看 / 使用），不产生其底层内容分组的任何其他权限，也不产生发布 / 管理权；退出或被移出群组后，该条目级授权随即失效，已保存进个人库的引用同理失效（除非本人另有权限来源）。这样跨部门协作不必先改组织授权，也不会捅破服务端的权限过滤。

### 2.5 成员自维护与申请公开（高级功能）

为解决「普通成员自己做的页、索引和成品，先自己维护，成熟后再进入组织正式区」的问题，系统提供一个由管理员显式开启的组织级高级功能：

- **默认关闭**。配置落在公司根节点或任一部门节点，子节点继承最近祖先的配置；超级管理员可锁定下级配置，部门管理员只能配置本人管辖且未被锁定的节点。配置项三件：功能开关、公开方式（**需审批**为默认，或**免审公开**）、非实质修改处理（**跟随审批**为默认，或**免审直改**）。
- **自维护权以对象归属为边界**：成员只能维护同时满足「本人上传或创建、当前维护人是本人、归入本人主部门维护区（或管理员明确指定的节点维护区）」的对象。它不授权成员改动他人的正式内容、主索引或整个内容分组，也不能借此把无权来源、其他客户专属内容「洗」成可公开内容——提交前系统逐项拦截并指明原因。
- **统一状态机**：内容页、索引页、演示厅三处状态一致——**我的维护 / 待审批 / 被驳回 / 已公开**。成员的对象先进入「我的维护」：内容块可编辑版本与标签讲稿，个人索引可维护条目与版本策略，演示厅条目（其「自荐」就是申请公开）可维护封面、标题、介绍与标签；三者都不能直接写进正式区。
- **申请公开**：维护人确认目标落点，并**只选一个公开范围**：① 本部门；② 本部门及子部门；③ 本人组织链上的某个上级组织；④ 全公司。提交时冻结对象快照；待审期间继续编辑只形成新维护稿，不改变已提交快照，可撤回后按新快照重提。申请自动路由给目标范围根节点的组织管理员（全公司范围给超级管理员），无管理员时逐级上送。**通过后快照直接进入正式区，无需第二次发布**；驳回必须填写原因，可改后重提。四档范围在索引总览与详情中以卡片边框颜色统一编码（见 5.6）。
- **免审公开**：选定范围后立即公开，系统仍完整记录快照、范围、操作者与时间并通知管理员；管理员可随时下架 / 撤回并填写原因，对象退回维护人的「我的维护」，发布历史不删除。由需审批切为免审，只影响切换后的新提交，已在待审批的申请不自动通过。
- **已公开对象的后续维护**：线上公开指针与维护人的工作稿分离。实质更新（页面内容、页数 / 形态、索引条目 / 顺序 / 版本策略、演示厅来源稿、公开范围）在需审批模式下生成待审新版本，旧公开版继续生效，批准后原子切换；范围扩大或改投时按新范围重新路由审批。讲稿、标签、介绍等非实质修改按配置走审批或免审直改，不提供绕过配置的直改通道。
- **关闭功能后的处理**：该范围停止新建、编辑与新申请，入口隐藏；未决申请退回维护稿并标注原因；已公开对象继续按原范围生效，转由对应组织管理员维护，待功能重开或维护人被重新指定后再恢复自维护。全部开关、模式切换、提交、审批、驳回、直接公开、下架与转交均记审计；GUI 与 CLI 的状态、错误码与权限判断一致。

### 2.6 设置页按管理层级分级

设置页是**同一页、按登录者层级拼装内容**。组织管理位于设置页内（「设置 · 组织管理」区），不是顶层页签。

- **超级管理员**看全部：公司级全局项（自维护功能总开关与默认值、离线缓存总策略、备份与主机设置、AI 翻译服务配置、术语库与不译名单等）、完整组织树与全部节点的组织管理、全部审批队列。
- **部门管理员**只见本人管辖子树（本人部门及子部门）的设置：子树内组织维护、成员归属、本范围分组授权、管辖节点的自维护配置与本范围审批队列；公司级全局项只读可见并标明「由超级管理员维护」，不得修改其他部门与全局设置。
- **普通成员**只有个人设置：个人资料（见 4.11）、本人的离线缓存开关与容量（受管理员策略上限约束，界面明示上限与来源）、个人偏好；界面中不出现任何组织管理区。
- **不可见即不存在**：无权看到的设置区不渲染、不留占位；服务端对设置类接口同样逐项校验层级与管辖范围；CLI 的设置类命令按层级同样裁剪，无权命令返回稳定的权限错误码。

## 三、核心概念与数据模型

### 3.1 内容块：内容线、形态、版本

**内容位（ContentUnit）** 是最小管理单位，一个稳定的「话题位置」，如「合作伙伴介绍」「封面」「公司介绍」。它的身份稳定，不随页数变化。每个内容位带：名称、一句描述（讲什么、适合什么场合，可由 AI 在导入时生成、人工修订）、主分组、维护人 / 维护部门（内容过期等提醒发给他）、主语言。

**内容修订（ContentRevision）** 是内容本身的变更轴：同一内容位只有一条内容线，内容的每一次实质变更（事实、数据、名单、说法变了）记为一次修订 r1、r2、r3……，与它用几页呈现无关。这条轴是判断各形态「内容是否过期」的统一标尺：某形态最新版所依据的修订落后于内容线的最新修订，该形态即标「内容已过期」（如依据 r4、最新 r5），作者按新修订更新并发布后标记自动解除；仅呈现变化（分拆 / 合并）不递增内容修订，不触发其他形态过期。

**呈现形态（Rendition）** 是同一份内容的一种具体呈现，由**形态 × 语言**确定：形态如精简、详细（可自定义）；语言如中文、英文、日文，另有双语对（见 4.12）。形态之间只差呈现粒度与页数，不差内容归属。形态由两种操作产生：**分拆**（把较少页展开成较多页，如 1 页合作伙伴介绍拆成 3 页细讲）与**合并**（把较多页浓缩成较少页，如 3 页合成 1 页）。因此任意形态可替换任意形态——引擎层只是「删 N 页、插 M 页」，界面层必须向用户说清方向：切到合并形态意味着接受更概括的版本，切到分拆形态意味着展开来讲。边界：形态意义上的合并，来源页必须同属一个内容位；把不同内容位的内容合到一页，产生的是一个**新内容块**（见 3.5），不是某内容位的新形态。

**版本（Version）** 是每种形态内不可变的历史版本，编号为**语义版本 X.Y.Z**（如 1.1.1、10.0.5），全系统统一——历史区、卡片徽标、替换选择器、CLI / API 的版本标识都是它；索引的发布标签同为 X.Y.Z 风格（展示可带 V 前缀）。「最新版」= 语义版本序最大的已发布版本。每个版本包含：

- 页片段：一个小 PPTX，含 1..N 页（N 是该版本自己的属性，各版本页数可不同）；
- 每页的**页位与逐页身份**：组内序号与各自的指纹，新旧版逐页对位可确切说出「只有第 2 页变了」——这是单页更新、页级冲突判断与摘选页跟随更新的依据；
- 每页所用字体清单（入库时记录，供组装体检与公司标准字体治理）；
- 所依据的内容修订、来源（直接编辑 / 分拆自 / 合并自）、作者、改动说明；
- **修订时间**：发布时间戳、精确到分钟，在版本详情中与作者、改动说明、所依据的修订号一并正式展示；
- 全部页与逐页的内容指纹；每页的缩略图与提取文字；每页的讲稿（见 4.10）；
- **版本状态**：正常 / **已撤回**。已发布版本被发现数据错误时，作者或管理员可撤回它并指定替代版本：此后它不再被导出与推荐引用；持有它的文稿打开时收到**强提示**（级别高于普通更新，不受普通提醒的克制规则约束、每次打开都提示），指引一键换到替代版本。撤回留痕且不可恢复——纠错永远靠发新版。

**版本号如何产生**：发布时人工点选递增段——发布确认卡给出三个选项：**大版本**（X+1.0.0）/ **小版本**（X.Y+1.0）/ **文字调整**（X.Y.Z+1），人不手写数字。系统按变更智能预选：页数 / 形态变化或内容大改 → 大版本；内容修订更新 → 小版本；仅文字、错别字、排版微调 → 文字调整。发布人可改选；预选、改选与最终号都记入版本记录。回滚发布新版时同样按点选段递增。X.Y.Z 只是形态版本的发布号，与内容修订轴分工不变：新旧判断以所依据的修订号为准。

**拖拽插入历史与级联重编号**：内容块的历史版本区支持把一张新版本卡**拖到历史序列的任意位置**：落在中间即成为历史版本，落在首位即成为最新版。落点定号：以落点前一版（更老一侧）为基，按选定的递增段算出插入版的号；其后（更新一侧）的所有版本依次**级联顺移编号**，整条线保持严格单调递增。例如在 2.3.1 与 2.4.0 之间以「小版本」插入 → 插入版为 2.4.0，原 2.4.0 顺移为 2.5.0，其后同理。**护栏：编号可变、身份不变**——每个版本有不可变的内部 ID，一切引用（索引条目与锁定、快照、文稿清单、导出记录、离线快照）一律按 ID 绑定，X.Y.Z 只是该 ID 当前的展示号，因此级联重编号永不破坏任何引用：已导出的 PPT 再打开时按 ID 显示现行编号，导出记录保留导出当时的编号可对照现行编号。每次编号变化逐版留痕（原号 → 新号、原因、操作者、时间），在版本详情的「编号变更记录」中可查。重编号不改版本内容、修订时间、依据的修订号与状态；只允许该形态的维护人操作并记审计；级联只在本形态线内。本条只适用于内容块的形态版本线——**索引的发布标签不可变、不适用**。

### 3.2 目录树与主索引

客户端最左侧是一棵按用途组织的目录树：一级目录是功能用途（如「公司介绍」），其下可建子文件夹。每个内容位与每份索引有且只有一个主分组。

一个目录可指定其中一份索引为**主索引（成稿）**：按 Git 模型（见 3.3），即该目录指向某个仓库 + 其 main 分支（成稿线）。它是该用途的官方成品序列——在索引页打开它即见成稿，也是组装时「优选推荐」的依据。被指定为主索引的仓库，其 main 分支的条目增删与打标签发布，默认需经该目录所属分组的**部门管理员确认**才生效（作者提交 → 待审核 → 通过后标签方才对外）；普通仓库 / 分支与日常页面发布不设此关。此规则可按分组开关。

### 3.3 索引：Git 式仓库模型

「公司介绍」这类整体文稿在系统里的存在形式**不是一个 PPT 文件，而是一份索引**：

> 索引 = 标题 + 所属分组 + 有序条目清单 + 默认上下文（目标客户 / 场合 / 语言）+ 所用模板。每条条目 = 内容位 + 呈现形态 + 版本策略（跟随最新，或固定锁定版本，见 3.4）。

索引按 Git 的心智建模（**一份索引 = 一个仓库 repo**），坐落在它的目录坐标上：

- **提交（commit）**：条目清单每发生一次增 / 删 / 改（换形态、换版本策略、调序）生成一个提交，含作者、时间、说明与条目级 diff。提交历史是提交图（DAG），不是单线流水号；原修订号保留为提交短号展示。提交只是编辑流水，本身不惊动已分发的副本。
- **标签（tag）**：作者在某个提交上打正式版本标签发布（V1.0、V3.5.4 等，系统按大 / 小 / 修订给出递增建议，作者可改）。标签**不可变**，冻结该提交的条目快照与版本说明。已导出文稿的结构更新以「其跟踪的分支上出现新标签」为触发点：未打标签的提交只在作者端可见。
- **分支（branch）**：派生的主机制。从任意提交或标签可拉出分支——同仓、同坐标、共享分叉点之前的提交历史，之后各自独立提交；分支可命名（如「西门子定制」「展会版」）。每个仓库有一条主分支 **main**（成稿线）。「哪个子索引由哪个派生」由分支图直接回答：分支名 + 分叉点 + 分叉后各自的提交数。
- **合并（merge）**：分支可向任意目标分支发起合并，以分叉点提交为 base 做**条目级三方合并**：只有单边改动的自动合入；同一条目双边都改 → 冲突，逐条人工裁决（用我的 / 用对方的 / 手动选该条目的形态与版本策略）；合并生成一个 merge commit 并记录来源分支与裁决结果。冲突只到条目级，不做页内内容合并。合并只发生在同一仓库的分支之间。
- **复制为新索引**：整份另起炉灶的次要动作——生成新仓库、新坐标，记录派生自（源仓库 @ tag / commit），跨仓库不合并、不互扰。
- **语言对应索引**：一份索引可「制作英文版」（或任意已有语言 → 目标语言），生成一份**并列的对应索引**：新索引有自己的 ID、发布版本与生命周期，与原索引以「语言对应」关系互链，条目**结构镜像**（第 i 条 ↔ 第 i 条，同一内容位、同一形态粒度，只解析到该语言的形态）。两边的结构变更会提示同步到对方，对方维护人确认后镜像跟随；内容版本各按各语言独立演进、独立发版；对应版可标注「结构基于中文版 V__」，落后时明示差几条。缺译条目在对应版保留位置，解析时回退显示源语言页并标「缺译」。导出与更新分发按语言版各自成线。**对应版是另一个仓库的镜像关系，不是分支，不出现在分支图上。** 索引之间只有两种关系：派生（同语言分叉）与语言对应（跨语言镜像），界面与文档都不得混淆。
- **术语**：「子索引」只指从某索引派生出的成果（同仓分支，或复制出的新索引）；索引条目不是子索引。

**目录坐标（第一坐标，常驻）**：每份索引主目录的**完整路径**（如「公司介绍 › 客户拜访」）是它的目录坐标，在索引出现的每一处常显——总览卡片、详情 / 编辑器顶部常驻坐标栏、导出记录、分享对话框与落地页、搜索结果、群组空间条目，不因页面切换、滚动或视图模式而消失。坐标与身份分离：索引 ID 是不变的身份，坐标可变更——「移动到其他文件夹」是显式管理动作，需管理权、写审计并记录坐标变更历史；已导出的 PPT 按索引 ID 跟随更新线，不受坐标变更影响。**谱系是第二坐标**：总览卡片以谱系行常显（分支名与分叉点 / 复制来源 / 含 N 条分支），总览的「按派生关系」视图就是仓库分支图。

**生命周期**：

| 状态 | 含义 |
|---|---|
| 使用中 | 正常维护与导出 |
| 历史（原称「已过期」，仅改名，语义不变） | 不再维护：禁止新导出并给出提示；其已导出文稿只再收到一次「该索引已转历史、建议改用 X」的通知，X 可指向替代（后继）索引，由使用人决定是否换线重绑 |
| 已作废 | 停止一切更新服务，已导出文稿转为普通文件不再受管 |
| 删除 | 软删：目录中消失、更新服务停止；版本快照与导出记录留档备查，其分支与复制出的新索引不受影响 |

状态变更需管理权并记审计。

**导出记录**：每次从索引（或组装清单）导出，服务端记一条导出记录：来源**三元组（仓库、分支、tag / commit 快照）**或组装 ID、逐条快照、导出人、时间、文件名，目录坐标随记录一并展示。导出的文件按清单登记为受管理文稿；它是一次性的快照交付，此后页面再更新，该文件在 PowerPoint 打开时收到更新提示，是否跟随由使用人决定。**更新严格按线走**：一份 PPT 只沿它跟踪的那条分支拉取更新，其他分支的提交与标签对它不可见、互不影响。

**版本带与老页面**：索引详情的「历史版本」视图设版本带——当前分支的发布标签从新到旧图形化排列。点某个标签进入该 tag 的**只读老页面**：整页图墙按当时快照呈现，顶部标明「历史版本 V__ · 只读」；可从老页面一键导出当时的整稿，导出记录记明快照来源为该 tag。

**删除替代（通用规则）**：任何「引用版本不存在」的场合——老页面快照引用的版本、锁定条目所锁的版本、替换选择器里失效的引用——若被引用的内容块版本已被删除或不可用，不留空洞：以同一内容块、同一形态**沿版本号向上找最近的存续版本**替代展示，卡上标明「原版已删 · 以 X.Y.Z 替代」。替代只影响当次展示与该次导出，不改写历史快照记录（快照仍记原版本号 + 替代注记），替代项在导出记录中可查。

### 3.4 条目锁定

索引条目的版本策略只有两态：**跟随最新**（浏览与导出时解析为该形态的最新发布版本，再过标签匹配）与**固定（锁定）**。锁定有两种来源：把条目当前解析到的版本固定下来；或在替换时选定某个历史版本（选历史版自动锁定）。

锁定语义钉死：锁定后，该内容块后续发布任何新版本都**不改变本条目的解析内容**——索引预览、导出、以及从本索引导出的 PPT 的更新检查全部以锁定版本为准；更新检查对锁定条目**静默跳过**（不产生更新提示、不进入结构差异比对）；卡上常显锁定徽标，仅可被动提示一句「源内容块已出新版 vX（已锁定不跟随）」；只有维护人手动「更换版本」或「解除锁定」才能改变。导出前体检中锁定条目列为**已知项**，而非警告升级项。索引条目可指向整组多页形态，也可摘选其中单页（见 4.7）。

### 3.5 内容块层级与跨块合成

块分三级，严格分层：

| 级别 | 是什么 | 在模型中的位置 |
|---|---|---|
| 元素块 | 页内的一个形状级元素：文本框、图片、图表、二维码块 | 页片段内的形状，是个人绑定、页级对齐的作用对象；不单独建库，只作为上级的组成部分被寻址 |
| 页块 | 整整一页 | 内容位的单页形态版本 |
| 组块 | 有序的多个页块 | 内容位的多页形态版本；索引是组块之上的整稿组合，不再算块 |

**内容位就是被版本化管理的块**（页块 / 组块同属其不同形态），层级只回答「由什么组成」，不另起一套版本体系。两种关系分开记：**组成关系**（组块由哪些页块组成、页块由哪些元素块组成，随版本固定）与**派生关系**（这个块从哪些块合成 / 分拆而来，记在版本的「来源」里）。

**跨块合成**：把两个（或多个）块的内容合到一页（或一组页），结果**生成一个新内容位（新块）**：新块独立成线（自己的形态、版本、标签、分组归属），首个版本逐一记明派生来源（块 A 的某版本 + 块 B 的某版本）；来源块不受影响，各自继续独立维护，引用来源的旧文稿、旧索引一概不动。来源更新不自动改新块：来源出新版时新块标「来源已更新」，作者可「重新合成」（按新来源版本拼一版草稿，人工调整后发布为新块的新版本），也可忽略标记。合成时每个来源块都需查看权，新块发布需目标分组的发布权；新块的客户「专属」标签按来源中最严的继承并提示作者确认，防把专属内容洗成通用。组成关系严格按三级向下、天然无环；派生关系校验不得指向自身或自己的后代合成结果，防谱系成环。

此外，内容块可**嵌套**：一个块的层级里除了直属页面，还可继续嵌子块，逐层下钻直到页。每个子块在父层直接展示它自己的推荐组（见 4.7、5.4）。（说明：3.5 中跨块合成一节在规格中标注为「设计提案，待审阅」；嵌套块的浏览与调取行为已由需求方另行确认，见 5.4。）

### 3.6 清单（Manifest）与绑定实例

一份被管理的 PPT 文件内嵌一份**清单**，记录：文稿 ID；来源索引时记来源三元组（仓库、分支、导出时的 tag / commit 快照）；每个受管理页群的绑定实例。PowerPoint 侧在打开时靠清单而不是靠页码认页、比对更新。PowerPoint 的分节既不作为更新单位，也不要求文稿预先分节；分节仅可作为可选标签用于浏览分类。

**绑定实例**：同一内容位可以在一份文稿里出现多次（正文一次、附录再一次），清单中按绑定实例逐个记录——实例 ID + 内容位 / 形态 / 版本 + 当前页范围。更新、切换形态、过期判断都以实例为对象，互不影响。绑定实例记下其所绑版本的客户标签作为上下文，查更新时按此上下文做标签匹配（见 4.4）。

**组装记录**：用户在组装工作台里组装出的文稿，服务端存一份组装记录（文稿 ID、标题、创建者、有序的绑定实例清单、所用模板）。导出文件里的清单与这份记录对应同一文稿 ID；之后文件内的增删页要回写这份记录（由执行增删的一方负责），使服务端记录与文件实际内容不脱节。

### 3.7 存储形态：只存拆分层，不存原稿

一份 PPT 进系统后**只以拆分形态存在**：每个内容位的每个形态版本存为一个小 PPTX 片段（1..N 页），文稿本身就是「清单 + 一串片段引用」。**不保留导入时的原始整份文件**；需要整份时随时由片段按清单拼回（导出就是这么做的），拼回的整份与原稿在页面层面等价（以保真度测试为准绳，见 8.3）。拆分粒度是内容块而非单页；块内页不单独成片，但带页位与逐页指纹。

不留原稿的安全网在导入环节：拆分完成后、正式入库前，系统立即按清单把整稿拼回一遍，与源文件逐页比对（页数、逐页指纹、缩略图），**校验不过则整批不入库并报错**；源文件在校验通过前只作临时文件存在，通过后即弃。由此推出一个运维结论：**服务端数据目录是全公司 PPT 资产的唯一副本，定时备份与一键恢复是一期必备，不是可选**（见 7.2）。

## 四、功能需求

### 4.1 整稿导入与 AI 分割工作台

把一份做好的 PPT 第一次纳入系统，走导入工作台（客户端与 CLI 均可）：

1. **选文件定大方向**：导入人选 PPTX，先定拟归属目录与默认维护人（默认导入人本人，均可后改）。系统解析全稿：逐页缩略图、标题、正文、备注、语言、指纹。
2. **AI 划板块**：AI 综合分隔页 / 章节页样式、标题变化、版式切换与内容话题相似度，把连续页划成候选内容块并给出每块的**置信度**；低置信度的分界高亮，等人工重点看。
3. **AI 匹配与新建（逐块三选一）**：与库中版本一致的 → 建议直接关联，不重复入库；与某内容位高度相似但内容有变的 → 建议作为它的新版本（页数明显不同且像展开 / 浓缩时，建议为新形态）；库里没有的 → **AI 自动新建内容位**：生成名称（取板块主题，目录内重名自动避让）、写一句描述、建议目录归属与语言、建议标签（文中出现客户名 / Logo 时提示相应客户标签，含「专属」可能）。另有一项顺带检测：封面 / 尾页上疑似个人信息的位置（手机号样式文本、二维码图）→ 建议绑定为个人字段（见 4.11）。
4. **人工确认四件归属**：导入人逐块（或批量）确认——**目录**（放哪个分组）、**内容位**（归入已有还是新建，用 AI 的名字还是改名）、**形态与语言**、**维护人**。分界可拖动调整，并块、拆块都是一键操作。两种提交模式：**审阅模式**（默认，全部确认后才入库）与**快速模式**（高置信度的块自动入库，低置信度的留待审阅；生成导入报告，整批导入可一键撤销）。
5. **入库与纳管**：入库前执行拼回校验（见 3.7），不过则整批回滚并报告差异页。通过后源文件即弃，整份原稿登记为一份文稿，系统产出一份带清单的**纳管版文件**（由片段拼成）供导入人替换原文件继续使用——此后它就是受管理文稿，走全部更新流程。
6. **增量再导入**：同一份稿改好后再导入，未变块标「无变化」跳过，只把变了的块提为对应内容位的新版本候选，工作台只审变化部分。

### 4.2 日常发布与剪贴板发布

日常发布是单块 / 少量页的路径：把页指认到内容位 + 呈现形态，系统比对指纹，只把真正变了的收为新版本草稿；作者填改动说明，并确认本次发布是否含内容实质变更（含则内容修订递增；仅分拆 / 合并等呈现变化则修订不变）。可先仅本地存草稿，再决定发布到主机；发布时服务端递增版本号并通知，并按内容修订标尺检查同内容位其他形态是否已过期。并发发布以服务端最新版为基准串行递增：后发布者若基于旧版，收到冲突提示，确认后作为再下一个版本发布，历史不改写。

**剪贴板发布**是日常改一页的最短路径：作者在 PowerPoint 里改好、选中一页或多页复制，切到客户端选中目标内容位粘贴——客户端从剪贴板取出页片段；取不到时自动改走 COM 桥，从 PowerPoint 直接导出当前选中页（等价入口为客户端的「取 PowerPoint 选中页」按钮）。随后弹一张**预填好的确认卡**（目标内容位、当前形态、语言已预填；可改目标、改形态、补改动说明、勾「含内容实质变更」、点选版本递增段），点「发布」即完成。规则：

- **自动成为最新**：发布成功的一刻新版本自动成为该形态的最新版——全系统不存在、也不需要「设为最新」这个手工动作；
- 粘贴旧版本的页回来发布，仍是追加一个新版本（内容与旧版相同、版本号更新），这就是留痕的「恢复旧内容」做法；
- 粘贴内容与现行最新版指纹完全一致时，提示「与最新版相同」并默认不生成新版本（可强制）；
- 页数不一致时确认卡明示并三选：作为该形态新版本（页数就此变）、另立新形态、或记为分拆来源；
- **只改多页组中的一页**：目标形态现行版本有 N 页而只粘来 1 页时，确认卡给出页位选择（以组内缩略图点选「替换第几页」），系统把粘来的页拼入对应页位、其余页原样保留，发布为整组新版本，并可确切标注「仅第 2 页变更」；同理支持组内插入一页（页数 +1）与删去一页（页数 −1）；
- 无目标分组发布权则粘贴入口不可用。

任一版本（含草稿）可挂**评审评论**：评审者在版本详情里留文本评论（可 @ 维护人），作者据此修改；评论留痕随版本保留，是「内容过审」的记录；评论不改变版本内容本身。

### 4.3 编辑回路

内容块详情与大图预览上都有「编辑」入口。一期采用**外部调用**实现：点击后，客户端把该块当前形态最新版的片段物化为一个可编辑 PPTX，放入本机受监视的工作目录，并调用外部编辑器打开——编辑器可选 PowerPoint、WPS、DeckCraft，按用户设置里的默认编辑器（未设时按本机安装情况探测，用户选一次后记住）。编辑期间该块在客户端标「编辑中」（含编辑人）。用户在熟悉的编辑器里改完保存，回到客户端点「更新」：系统把工作文件与打开时的版本逐页比对指纹——无变化则提示「未做修改」并清场；有变化则弹出与剪贴板发布相同的确认卡，发布即新版本。发布成功后，详情页、缩略图、长卷与索引视图立即换成新版呈现，「编辑中」标记清除，工作文件归档留痕。两人同时编辑同一块时，后发版者按并发规则成为下一版本，不覆盖先者。把编辑器直接内嵌进客户端是二期深化（见 8.4），一期先用调用，链路已经闭环。

### 4.4 标签体系

标签的作用是让所有人不用猜就知道「这一片是给谁、干什么用的」。标签主要打在**版本**上（最精确）；内容位 / 呈现形态上可设默认标签，新版本自动继承、发布时可改。同一页面的不同版本可以有完全不同的标签。

- **维度**：客户（受控词表，多选，如「西门子」，外加系统值「通用」）；场合 / 用途（受控词表，多选，如「详细业务介绍」「简要介绍」「内部汇报」「展会宣讲」）；自由标签（任何成员可加）。受控词表由管理员维护，避免同一客户各写一份。
- **适用强度**：客户标签分两档——「适用」（推荐给该客户用）与「专属」（含该客户的名称、Logo、案例或数据，只能给该客户用）。
- **适用说明**：每个版本可写一句短说明（如「这版适合给西门子做详细业务介绍时用」），显示在页库卡片与版本列表里。
- **权限与留痕**：任何成员可新增标签；删除他人打的标签仅限原作者与管理员；标签变更记入操作记录。
- **参与三处**：页库筛选与推荐排序；组装上下文（先定客户 + 场合，对的页排前面，其他客户的专属页默认折叠）；**更新匹配**——绑定实例记下其所绑版本的客户标签作为上下文，同形态的新版本只有客户标签为「通用」或与该上下文有交集时，才算这个实例的候选更新。给西门子做的专属新版本，绝不能被提示给正在做其他客户文稿的人。场合标签不阻断更新，只影响推荐排序与筛选。往某客户上下文的文稿里插入另一客户的专属页，必须弹明确警告并经确认。

### 4.5 搜索

按标题、页面提取文字、标签、内容位搜索，附件的抽取文字同样入索引（见 4.13）。搜索结果先按账号权限过滤——无权内容不出现在结果与计数里。版本间可做文字差异对比，辅助审阅更新。

### 4.6 组装工作台与优选推荐

组装只发生在**索引页的组装工作台**（新建组装 / 新建索引时进入）。它是一个内容选用器：复用内容浏览的组件但处于选用模式，不等于内容页（内容页只做维护，见 5.3）。选用器由服务端给出「最新页」视图——每个内容位、每种形态只呈现其最新发布版本；依据修订落后的形态带过期标记。页面以缩略图卡片平铺，卡片显示客户 / 场合标签与适用说明，可按语言、标签过滤，按文字 / 标题搜索、按内容位筛选。

- **先定上下文**：组装开始时先定本次上下文（目标客户 + 场合，如「西门子 + 详细业务介绍」）。页库据此把匹配标签与「通用」的页排在前面，其他客户的专属页默认折叠。组装清单与导出文稿的清单都记下这个上下文，供之后查更新与插页时继续按它匹配。
- **快捷选**：在最新页流里单击卡片即选入，选的就是卡片当前显示的那一份（跟随最新策略下即该形态的最新发布版本），不需要任何额外动作。
- **打开选**：双击卡片进入该内容位详情，并列展示它的各种形态与各自的版本历史；选某形态的某版本就用那一版；选多页形态的某版本**默认整组全选**，也可只勾其中一两页。
- **摘选页**：操作粒度对用户是「页」，但多页形态在卡片流里是一个可展开的页组：默认整组入选、整组移动；只取其中部分页时，被摘出的页在组装记录中按「摘选页」单独记绑定来源（源形态与版本），源形态更新时按页单独提示，不自动整组替换。
- **嵌套块调取**：选用器里每个子块卡片直接展示它自己的推荐组，可点「选用其推荐」把该子块推荐的全部页面加入清单，不必下钻；选用父块整体时按层内顺序递归展开（直属页取父块所选形态 / 版本，嵌套块默认取各自推荐，可在父层逐个改选）；组装记录逐节点保存实际选用的内容块、形态与版本，后续更新检查按节点分别跟随。
- **拖动排序**：在组装清单里拖动调整顺序（页组整体拖动，组内顺序固定），实时显示总页数与整稿缩略图顺序，可预览。
- **选模板**：从模板库选一个模板文稿作为基底（决定尺寸、母版、主题），所选页按「保留源格式」插入；不选则用工作区默认模板。
- 组装成果保存为索引或个人组装记录。组装本质上是手工现搭一份索引，要长期复用就存为索引文稿，之后浏览与导出按索引走。

**优选推荐（成稿引导）**：选页不必从零摸索——每选中一页，系统按已选内容给出「接下来选这几页」的推荐：

- **主来源：索引成稿**。已选页若属于某目录的主索引，按该索引的序列推荐紧随其后的条目并标明出处（如「公司介绍 · 成稿后续」）；已选清单若已构成某主索引的一段前缀，直接提示「一键按成稿补齐」其余页。
- **次来源：历史共现**。其他索引 / 组装 / 导出记录里常与已选页搭配出现的页，按共现次数推荐。
- **优选标记**：同一内容位有多个候选（不同形态 / 版本 / 标签）时，主索引当前采用的那个标「优选」，排在前面；不妨碍用户改选其他候选。
- 推荐只认当前账号有权查看的分组，且服从本次客户 / 场合上下文：其他客户的专属页不进入推荐。

### 4.7 导出与导出前体检

**导出即最新**：索引在客户端点开即可浏览（按条目逐项解析：跟随最新 / 锁定版本，某条目所用版本自上次导出后已有新版时带「已更新」提示，浏览者看到的就是新版内容），点导出即生成 PPT——导出的永远是导出那一刻的最新版，不存在先去「更新系统里那份文件」的动作，因为系统里根本没有那份文件。可以整份导出，也可以不整份导出：在组装工作台中以本索引为起点新建组装，勾选其中几页。导出权限按分组校验：有查看权不等于有导出权，无导出权的成员可在线浏览，不能生成文件。

**导出前体检**：点导出后、生成文件前，系统自动过一遍本次组装并逐项列出让导出人确认（可逐项处理或知情继续）：混入了与本次客户上下文不同的其他客户专属页；引用了内容已过期（依据修订落后）的形态；用了锁定版本的条目（提醒不会跟随更新）；所用字体不在公司标准字体清单内、或接收环境可能缺失；含个人占位符但归属人资料缺失（见 4.11）；来源索引已转历史；对外场合用到「AI 译 · 未校对」的页。体检不阻断导出（权限类硬错误除外），但每一项都必须被导出人显式确认，体检结果记入导出记录。

**导出动作本身**：服务端按解析结果生成 PPTX；生成前做个人占位符渲染（见 4.11），并按「添加备注」开关决定是否把讲稿写入备注（见 4.10）；同时完成两件使导出文件「仍连着数据库」的事：在文件内写入清单（新文稿 ID + 每个绑定实例的内容位 / 形态 / 版本），并在服务端登记组装记录与导出记录。导出后这份 PPT 与其他受管理文稿完全同权，走同一套更新逻辑——导出不是一次性快照。

### 4.8 分发台账与消息中心

**分发台账**：服务端凭导出记录与各文稿的更新检查回执形成台账——按索引 / 按文稿查看：这份稿一共导出过多少份、分别在谁手里（归属人）、各自停在哪个索引发布版本 / 索引修订、落后几条更新、有没有人还在用已撤回的版本。维护人 / 管理员可对落后者**一键提醒**（走消息中心）。台账只对有相应管理权的人可见。它是「谁还拿着三个月前的稿子在对外讲」这类事故的治本工具。

**消息中心**：客户端内置，集中承接一切「等某人处理」的事，不只靠打开 PPT 时撞见：

- 给维护人的：我维护的内容有形态过期 / 译文待更新 / 来源块已更新 / 我维护的索引有待审核变更；
- 给持有人的：你导出的稿落后新版本了（来自台账提醒）、你正在用的版本被撤回、你所属索引已转历史并建议迁移；
- 给评审 / 被授权人的：有人请你评审某版本（评论 @）、你的临时授权即将到期；
- 申请公开链路的待审批、通过与驳回同样进消息中心。

一期只做站内消息（客户端 + CLI 可查）；企业微信 / 邮件外发是预留渠道（二期接入同一事件源）。

### 4.9 更新检查与原地替换（硬性要求）

这是整个产品的核心机制，先钉死一条硬性要求：

> **接受更新必须在当前打开的原文件里原地替换——页还是那些位置的页，保存还是原路径。生成一份「更新好的新 PPT」作为交付方式，不可接受。**

**打开检查**：在 PowerPoint 里打开文稿，PowerPoint 侧（一期为客户端内置的 COM 桥）读清单，向主机查询，分三类呈现、不混淆：

- **有更新**：正在用的形态有更新的版本，或该形态所依据的内容修订已落后。候选版本须先过客户标签匹配，与本实例客户上下文不相干的专属版本不进入候选、不提示；
- **可替换形态**：同内容位还有其他形态可选（同线内容、粒度与页数不同），列表标明每个形态的页数、所依据的修订、客户 / 场合标签与适用说明，对方依据的修订更新时标明「含更新的内容」；
- **撤回强提示（最高优先级，单独成栏）**：正在用的某版本已被撤回时，注明撤回原因与指定的替代版本，一键换到替代版本。此栏不提供「本版内不再提醒」——只要还在用被撤回的版本，每次打开都提示，与普通更新的克制策略区别对待，因为这是纠错而非升级。

清单里没有的页、主机上没有的内容位，不提示。若文稿是从某份索引导出的，还要按 4.10 做一次索引差异比对，把结构变更并入同一份更新清单。

**接受更新（原地替换流程）**：对每个被接受的内容位逐个处理（每处理完一个重新核对位置）：从主机取目标版本的页片段 → 记录该内容位在当前文稿中的起始位置与页数 → 把新页插入到该位置 → 核对插入页数无误后删除旧页 → 更新清单（该位置页群改绑目标形态与版本）。全部完成后只提示结果，**不自动保存**，用户检查后自行保存到原路径；中途失败则停下并明示未完成项，用户可撤销或关掉不保存。形态切换复用同一流程，确认界面须显示页数变化（如 3 页 → 1 页）并说明目标形态是更概括还是更展开。整份文稿页数随之增减，后面内容位按绑定 ID 定位，不受页码漂移影响。

**多页组的页级替换**：若新旧版本页数相同、且逐页对位比对显示只有部分页变了，接受更新时只原地替换那几页（删 1 插 1），组内未变的页原封不动——同事对未变页的本地状态完全不受影响。页数不同或几乎整组都变时，退回整组替换。

**本地修改的处理**：打开时对每页算指纹，与所绑版本不符即标「本地已修改」。该内容位有更新时给三个选择：用新版（覆盖本地改动）、保留本地（跳过这次更新）、先预览再定，不静默覆盖。判断细到页：同事只改了组内第 3 页、而更新只动第 2 页时，第 2 页可正常接受，第 3 页保持他的本地状态；只有同一页既被本地改、又被新版改时，才对那一页出三选一。系统不做页内自动合并。

**回退**：任何内容位可切回任一旧版本，走同一原地流程（旧内容以新版本号重新发布，历史不改写，见 4.2）。

**向已有文稿继续插页**：导出之后（以及对任何受管理文稿），可以继续往里插入当初没有选入的页库页面，两个入口做同一件事：文稿在 PowerPoint 里打开时，用 PowerPoint 侧的页库面板浏览最新页，选中后指定插在当前页之前 / 之后，原地插入并新建绑定实例，随后把新组装清单回写服务端组装记录；文稿没打开时，在客户端打开该文稿的组装记录调整清单后对原文件重新落盘——若该文件此刻正被 PowerPoint 打开，客户端须提示改走 PowerPoint 侧入口，不直接改文件。要插入的页还不在页库里时（本地新做的一页），可在 PowerPoint 侧选中该页「导入页库并登记」：指定内容位与形态、发布到主机后，它即成为受管理页并建立绑定。

### 4.10 结构性更新与发布门控

从索引导出的 PPT 分发给同事后，后续更新**以那份索引为基准**计算，而不是只看单个内容位有没有新版本：

- **基准**：导出文件清单记有来源三元组（仓库、分支、导出时的 tag / commit 快照）。该分支发布新标签后，打开文件时把新标签的条目清单与导出快照逐条比对，差异即更新清单。**未打标签的提交不触发**——结构更新是发布门控的：作者改稿过程不打扰同事，打标签发布才对外。锁定条目静默跳过，不进入差异比对。
- **四类变更**：

| 变更类型 | 触发 | 接受后的动作 |
|---|---|---|
| 内容更新 | 条目没变，但所指形态出了新版本 | 按 4.9 原地替换该条目的页 |
| 页数 / 形态变化 | 条目换了形态，或新版本页数不同 | 按 4.9 原地替换（删 N 页插 M 页），确认界面明示页数变化 |
| 新增模块 | 索引里新增了条目 | 在其相邻条目（前一条目之后）的位置原地插入新模块的页，并新建绑定实例 |
| 删除模块 | 索引里删掉了条目 | 原地删除该条目对应的页，并解除其绑定 |

- **审阅方式**：逐条审阅（每条可预览：新页缩略图 / 文字差异；删除类展示将删的页；新增类展示将插入的位置与内容）后单独接受或跳过；或全量更新一次接受全部。两条路都走完后只提示结果、不自动保存，用户检查后存回原路径。
- **顺序与定位**：变更逐个执行，每个变更动手前按绑定实例 ID 重新定位，不依赖页码。新增模块的插入锚点取它在索引里的前一条目；前条目已被本地删掉时锚到再前一个仍存在的条目，都没有则插到后一条目之前。
- **边界规则**：仅作者在自己电脑上删页不触发任何分发，只有索引条目被删除（或内容位被下线）才产生「删除模块」变更；手工组装导出、没有来源索引的文稿不走本节，只走条目级更新。按线隔离：比对永远只针对文稿跟踪的那一条分支。**护栏**：要删的页被本地改过时，删除变更默认不勾选、须单独明确确认；同事跳过某条变更后，同一索引版本内不再提示同一条，来源索引再发布新版本后才重新进入清单；结构更新同样按权限过滤，无权分组的条目不在同事端产生任何提示或动作；作者侧把条目移出索引只影响之后的分发更新，页库里的内容位与历史版本不因此删除，其他引用它的索引 / 文稿不受影响。

### 4.11 个人信息绑定与导出个性化

有些页（如封面、尾页）大部分内容全公司一样，只有少数位置是「谁用就填谁」：汇报人姓名、手机号、微信二维码。这类位置做成**个人占位符**，绑定账户资料，导出时自动替换。

- **账户资料字段**：汇报人姓名、职务、英文名、手机号、邮箱、微信二维码图片（可另加头像）。成员自己维护自己的，管理员可代填 / 代改。
- **占位符类型**：文本占位符（某个文本框或其中一段文字标记为某资料字段）与图片内容块（某个图片框标记为某图片字段，如微信二维码——模板里放通用占位图，导出时按原框尺寸填充、保持比例，换成导出人自己的二维码）。标记在发布 / 导入时完成：选中文本框或图片框一键「绑定为个人字段」并选字段；绑定清单记入版本元数据，与页片段一起版本化，改绑定即发新版本。
- **只存模板态**：存储的片段里该处只存中性占位内容（如 `{{汇报人}}`），**绝不存任何真人的真实号码**——作者标记时若框里是自己的真号码，入库时自动洗成占位符。
- **替换时机（按接收人，不按作者）**：凡是片段要落到某个人手里的环节，都在交付前按那个人的资料渲染一遍——组装 / 索引导出按导出人资料替换，导出记录另记「归属人」（默认即导出人；管理员代他人导出时可指定归属人，按其资料渲染并写明）；更新下发与桥插页按接收文稿的当前账号替换（同事接受封面更新后，封面上的手机号仍是他自己的，不会被作者的覆盖）；客户端预览默认按当前登录人渲染（所见即所得），可切换为「模板态」看占位原样。
- **资料缺失时**：归属人没填手机号 / 没传二维码时，导出前明确列出缺失项，三选：先去补齐资料、留空导出（该处空白 / 保留占位图）、取消。绝不拿模板作者或他人的真实信息顶替。

### 4.12 多语言：逐页绑定、AI 翻译与双语页

**语言绑定**是整稿换语言、AI 翻译与双语页的前提：同一页片子的不同语言版本必须显式知道彼此是「一页」。

- **绑定落到每一页**：同一内容位下、同形态的各语言形态天然成组绑定（中文详细版 ↔ 英文详细版 ↔ 日文详细版）；不只是形态成组，每一页都知道自己对应的英文页（及各语言页）是哪一页——实际使用中默认每页都有英文对应页，缺失的才是例外，进**缺译清单**。内容位详情里按语言并列展示，缺哪种语言一目了然。每个语言版本还记录它的来源（人工制作 / AI 翻译，见下），详情与卡片以徽标区分。
- **页级对齐**：多页形态跨语言时，页与页的对应默认按顺序对齐（中文第 2 页 ↔ 英文第 2 页）；两侧页数不同时可手工指定对齐关系，未对齐的页单独标记。切换语言、双语生成、增量翻译都按这个对齐走。
- **语言绑定工作台**：页级绑定在专门的对照工作台里完成（入口在内容块层级的「语言绑定」区与索引页的「制作 / 管理语言对应版」处）。左右两列并排：左列中文页流、右列英文页流（其他语言同理）。系统先按导入来源、顺序、页位与内容相似度**自动预配**并标置信度，人再确认或修正。主操作是**拖拽**：把一张英文页缩略图拖到某张中文页上松手即绑定（反向亦可）；拖到已绑定页上是改绑，拖回未绑定区是解绑；连续选中多张一起拖，形成 1 对 N 分组绑定（N 对 1 同理）。不便拖拽时用点选配对（先点中文页、再点英文页、点「绑定」），还可框选两侧各一段页序后「按顺序批量绑定」。已绑定的页对带同一编号 / 颜色的绑定徽标，悬停任一侧时另一侧对应页高亮。若拖来的页已绑在别处，系统先提示这是**移动绑定**还是取消，不静默抢绑。没有对应页的一侧可点「标记缺译 / 无对应页」留空位，不硬凑。绑定在工作台内先以待保存状态呈现（可撤销单步、整批确认后生效）；保存后立即作用于整页语言切换、对应索引与 AI 增量翻译。AI 自动翻译出的页天生带绑定（无需人工配对），人工制作的页必须经此工作台（或导入时的自动预配确认）才算绑好。
- **补绑定（事后合并）**：语言版本若被分开导入成了两个内容位（常见情形：英文稿单独导入），可声明「这两个内容位互为语言对应」，系统将其合并为一条内容线：形态与版本各归其位、历史保留、原有两个 ID 建别名不失效。
- **整稿 / 单点换语言**：文稿（或单个绑定实例）可按绑定关系原地换成对应语言形态的最新版（走 4.9 的流程）；无对应语言的条目列入缺译清单并原样保留。索引带语言上下文导出同理，缺译条目逐条报告。
- **译文待更新**：每个内容位设主语言（默认其最初语言）。其他语言形态的最新版所依据的修订落后于主语言最新修订时，标「译文待更新」，出现在页库卡片与发布者待办里；增量重译或人工更新后解除。

**AI 翻译**（接入外部 AI 服务，把每一页翻成多语言）：

- 流程：选源形态（或整份索引）→ 选目标语言 → AI 逐页逐文本框翻译，原样保留版式与格式、只换文字 → 生成目标语言形态的**草稿**版本 → 人工在客户端逐页校对（可改字、可调字号）→ 发布。**AI 译文不经校对不得直接发布**——这是大公司对外材料的硬规矩。
- 术语一致性：服务端维护术语库（产品名、客户名、专有名词的标准译法）与「不译名单」，翻译时一并喂给 AI 并对产出做术语校验，不合术语的段落标出待改。
- 版式风险提示：译文长度与原文差异大时（英文通常更长），可能溢出的文本框逐个标红提示，校对界面可一键缩小字号 / 扩框后再确认。
- 增量翻译：源头出新修订时，只重译发生变化的页与文本段；未变化段落复用已校对通过的译文——靠页级对齐与内容修订对位实现。
- 服务接入：AI 服务商可配置（地址与密钥存在服务端，管理员维护）；这是本系统**唯一需要外网**的能力，无外网时仅此功能不可用，其余功能不受影响。CLI 支持整份索引批量翻译，产物同样是待校对草稿。

**译文来源与人工保护**：每个目标语言版本都记来源并全程可见（卡片 / 详情徽标）：「人工制作」= 人手工做好、经导入与中文页绑定进来；「AI 翻译」= AI 产出（草稿标「待校对」，校对发布后标「AI 译 · 已校对」）。关键规则：**人工制作的译文受保护**——批量翻译与增量重译永不覆盖人工制作的版本；源页更新后，人工英文版只被标「译文待更新」并通知其维护人，由人决定如何改。维护人若想借 AI，AI 生成的只能是并排的对照草稿建议；人采纳并发布后，新版本来源仍记「人工定版」。反之，AI 来源的译文在源更新时自动进入增量重译队列、生成新草稿待校对。来源也是导出体检的一项（见 4.7）。

**双语页**（一页同载两种语言，如中英对照）：形态上是独立的呈现形态——语言维度取值可以是双语对（中+英、中+日、英+日……），在内容位详情、组装选页、原地替换里与单语形态同权，选它即整页替换为双语版。产生方式两种：人工制作后作为双语形态正常导入发布；或系统辅助生成草稿——取绑定的两种单语形态，按对照版式模板（上下对照 / 左右对照）拼成双语草稿，缺一种语言时先走 AI 翻译补齐，再交人工定版。双语形态的过期判断同时看两个来源语言：任一来源的修订更新，双语形态标「待同步」；其版本记录所依据的两个来源修订各是多少。

**整页语言上下文（客户端）**：客户端顶部有全局语言切换（如 中文 / 英文），它决定当前一切视图的解析语言。中文态下只显示中文页（界面干净，不混杂其他语言）；切到英文态，内容页、索引页与成稿解析整页改按英文呈现——有英文版的显示英文页（带来源徽标）；还没有英文版的条目**就地回退显示中文页并标「缺译」**，位置与结构不乱。在英文态点开某页的详情 / 大图时，**内嵌中文原文对照**（源页并排或可切换），供核对译文——即「外面是英文，里面留着中文」。索引总览同理按语境过滤（见 5.5）。

### 4.13 讲稿

每一页除了画面内容，还备好「介绍这一页时要说的话」——讲稿。它是演示质量的一部分，随版本管理：

- **存放**：讲稿挂在版本上、按页存放（多页版本逐页一份），随形态的语言走（中文形态是中文讲稿，英文形态是英文讲稿；AI 翻译形态时讲稿一并翻译成草稿）。
- **来源**：人工在客户端版本详情里逐页写 / 改；也可让 **AI 起草**——按页面文字、内容位描述与适用场合生成口语化讲稿草稿，并按字数估算讲解时长，人工修订后定稿。导入整稿时，原稿自带的 PowerPoint 备注会被读入作为对应版本的初始讲稿，不丢失。
- **修订规则**：只改讲稿**不递增版本号、不算内容修订、不触发**同事端的页面更新提示（画面没变，不值得打扰）；讲稿的每次修改留痕。已分发文稿下次因其他原因接受该页更新时，顺带带上最新讲稿（限当初导出时选了带备注的文稿）。
- **导出开关（自动备注）**：组装 / 索引导出时有「添加备注」开关（工作区可设默认）。开：把每页讲稿写入导出 PPTX 对应页的演讲者备注，导出人拿到的是能直接照着讲的讲者版；某页无讲稿时该页备注留空，并在导出报告中列出缺讲稿的页。关：导出干净稿，备注为空（适合直接发给客户）。
- **其他用法**：客户端浏览成稿时可切换「讲稿视图」逐页对照看稿；CLI 可批量导出整份索引的讲稿为一份文档（Word / Markdown）供打印提词。讲稿数据一份多用，源头只在版本上。

### 4.14 附件（介绍材料）

PPT 之外常有一份配套的介绍材料（Word 说明、PDF 白皮书等），附件就是把这类材料挂在内容上一起管理：

- **挂载对象**：索引文稿（给整份成稿配材料）或内容位（给某个话题配材料）；一份对象可挂多份附件。
- **内容与存储**：任意文件，主用 Word（.docx）与 PDF；原样存入服务端数据目录，记元数据（文件名、类型、大小、上传人、时间、一句说明）。附件本身不做版本线，换文件即新增一份、旧的保留可删（记操作日志）。
- **使用方式（仅 Rust 程序）**：客户端在索引 / 内容位详情里列出附件，PDF 可在客户端内预览，Word 等提供下载 / 用本机程序打开；CLI 同步提供上传、列出、下载。**PowerPoint 侧不做附件**（按需求方明确指示）。
- **权限**：附件跟随其挂载对象的分组权限，有查看权才能看到与下载。
- 附件上传时抽取文字入搜索索引（Word / PDF 解析、图片类附件 OCR），介绍材料可被全文搜索命中；搜索结果同样受权限过滤。
- 附件不进 PPT 导出物；导出时可勾选「同时导出附件」，把附件文件与 PPT 一并落到同一目录。

### 4.15 演示厅

在「拼页做稿」的工作区之外，产品设一个面向「拿现成稿去展示」的板块，定名**演示厅**（不叫「成品」；本板块原工作名为「展厅」，已正式定名「演示厅」，其子区名广场 / 我的库 / 收到的分享 / 群组空间不变）。演示厅里流通的基本单位是**成品条目**：一份可直接对外展示的完整稿——来源是一份索引的某个发布版本解析结果，或一份个人组装记录；条目带封面图（首页缩略图 + 若干页预览）、标题、一句介绍、客户 / 行业 / 场合标签，以及署名信息：维护人是谁、最近由谁修改于何时（卡片与详情都标注，修改历史可展开）。

**广场（组织范围陈列）**：演示厅的公共区，由管理员运营：管理员可把优质成品直接上架、排序、写推荐语、设分类目录。成员自荐不是另一套流程，而是演示厅条目在成员自维护功能（见 2.5）下的「申请公开」：只有在对应组织节点开启该功能后，成员才能把本人维护的条目自荐到广场，按所选公开范围走审批或免审；功能未开启时不显示自荐入口，仍可由管理员直接选品上架。获批条目只对所选组织范围内的账号出现在广场中。广场条目仍受权限约束：底层内容无权的账号在广场也看不到该条目。

**指定分享（三种目标，落点不同）**：不进广场也可分享，分享对象可以是成品条目，也可以是一份索引直接分享。

- **分享给个人**：对方在消息中心 / 演示厅「收到的分享」里看到，点**保存**即收进自己库里指定的目录；不保存则不进库，不强塞。
- **分享给部门**（按部门树选）：该部门（默认含子部门）的成员人人在「收到的分享」里见到，各自决定存到自己哪个目录；它是发给这个组织单元的，之后新加入该部门的人也能看到这份分享。
- **分享给群组**：不走个人保存——索引 / 条目直接进入该群组的共享空间，群组成员打开群组就能看到、使用，随时可再保存进自己的库（见 2.4）。

三种分享的都是引用而非拷贝：源头更新时，收下的人照样收到更新提示（与导出文稿同规则）；分享人可随时撤销分享（群组里的由分享人或群组管理员移除）。

**我的库（个人陈列）**：每个账号有一套个人目录（左目录、右内容的版式与内容页一致）。账号开设时，管理员按「新人基础模板」初始化它：基础目录结构 + 一批官方推荐条目预先放入。此后完全归个人：可自建 / 改名 / 删除目录，可从广场拉入条目、可收下他人分享、可放自己的成品，也可移除（移除只是解除个人引用，不删源头内容）。**拉入 = 引用**：只是在个人目录里建一条指向该条目的引用，条目本身仍由其维护人维护、按其来源的更新线走；想改内容的人走「以此为基础做我的版本」（生成自己的组装 / 索引副本），不直接改动共享条目。

**详情、预览与正式演示（三层分开，不得混称）**：

- **条目详情 / 预览**：单击卡片只选定；双击或点「打开」先进入条目详情，而不是直接放映。详情呈现封面与逐页缩略图、当前解析版本与来源（来源索引及发布版本 / 个人组装记录）、维护人与修改记录、逐页讲稿，并提供拉入我的库、分享、导出 PPTX 与「开始演示」等动作。
- **预览 / 讲稿视图**：整稿页面流只叫「预览 / 讲稿视图」，用于逐页浏览、核对画面与照着讲稿预习；它不是正式放映，任何界面文案不得把滚动缩略图页面流称为「直接演示」。
- **正式演示**：详情中的「开始演示」与卡片上的快捷「直接演示」执行同一动作——先按条目当前解析结果（索引发布版本 / 组装快照，含 4.11 的接收人个性化规则）**物化出一份完整 PPTX**，再进入全屏放映。放映的对象始终是这份当前版本的完整 PPT，而不是客户端拼出的缩略图流。
- **放映由 DeckCraft 承担**：正式放映通过独立的演示适配层调用 DeckCraft 的演示 / 渲染能力；一期在嵌入接口尚不成熟时，可由适配层启动 DeckCraft 打开物化 PPTX 并进入演示。观众屏只显示当前幻灯片、全屏干净放映；演讲者视图在本机或第二屏显示当前页、下一页、该页讲稿、计时与页码 / 总页数；单屏时可切换到演讲者视图，但观众模式不得混入缩略图流、讲稿或管理控件。
- **不可用时明示降级**：DeckCraft 不可用、启动失败或物化稿含其暂不支持的效果时，界面必须明确提示，并由用户选择改用 PowerPoint 放映或静态预览，同时说明动画、切换、音视频等效果可能不同或缺失；不得静默降级并冒充同等效果。DeckCraft 的实际放映保真度以 Phase-0 实测为准（见 8.3）。

**离线缓存（只覆盖我的库，只缓存实际采用的版本）**：

- **边界是「我的库」，不是广场全量**：可进入完整缓存范围的只有已进入本人我的库的条目（从广场拉入的、接受分享保存的、自己创建并已采用的）。只在广场浏览过、未拉入的条目不缓存完整 PPT，最多保留卡片元数据与缩略图，供离线时浏览目录与辨认。
- **缓存单位 = 实际采用的一致快照**：缓存的不是零散页或「最新指针」，而是用户实际采用那一刻解析到的一整套版本组合——按当时的索引发布版 / 各条目版本组合物化，完整保存放映与预览所需的内容（物化 PPTX 或其全部片段、清单、逐页缩略图、讲稿与必要元数据），保证离线打开时整套版本一致，不混进半套新版。
- **触发采用混合策略：一次确认 + 被动缓存**。用户第一次**真正使用**我的库中的条目时——开始演示、导出完整稿、以 DeckCraft / PowerPoint 打开完整 PPTX，或点「离线可用」——客户端只询问一次是否开启「自动缓存我用过的稿件」，三选一：开启自动缓存 / 仅缓存本次 / 不开启。开启后，后续凡是真正用过的条目，系统都在后台被动缓存其当时采用的一致快照（显示进度、可取消），不再逐份询问；**只拉入、只浏览卡片、只打开详情看缩略图，都不触发完整 PPT 缓存**。未开启自动缓存时，只有用户在单条上明确点「缓存到本地」才缓存。每条条目始终保留单条动作：缓存到本地 / 移除缓存 / 常驻本地 / 不要缓存（加入排除名单后，被动缓存也跳过它）。
- **历史版本默认不预缓存**：旧版本、未采用的形态 / 语言一律不预下载。用户在线主动打开某个历史版本时可临时缓存该版，之后按容量策略淘汰。
- **快照替换规则**：采用版被新版取代时，只有联网同步完整成功后才以新快照原子替换旧缓存，替换中途失败继续用旧快照。离线期间一律使用已采用的旧快照，并明确标注「离线缓存 · 版本 X · 尚有新版待联网确认 / 同步」（联网确认前写「待联网确认」），不得把缓存版表述为最新版。
- **离线能做什么**：断网或主机不可达时，我的库仍可打开；已缓存条目可看详情、预览 / 讲稿视图，并可沿正式演示路径用 DeckCraft 放映缓存的完整 PPTX；未缓存条目明确显示「未缓存，不能离线打开」。离线期间的个人目录整理等本地操作可排队，联网后同步；发布、申请公开、审批、分享等涉及服务端的操作仍须联网。
- **状态与容量治理**：卡片与详情显示「已缓存 · 版本 / 大小 / 缓存时间」与「离线可用」徽标。缓存有总容量上限：空间不足时先淘汰最久未用且未常驻的缓存，**不得静默删除常驻项**，淘汰常驻项或空间仍不足时必须提示用户；用户可把常用条目设为「常驻本地」免于淘汰，也可单条移除缓存、在设置中查看 / 调整容量与自动缓存开关。
- **管理员策略优先（更严格者胜）**：管理员可按公司 / 组织节点 / 内容分组设置本地缓存策略——允许被动缓存 / 仅手动缓存 / 禁止本地缓存；客户专属等高敏感内容可被设为仅手动或禁止。用户个人选择与管理员策略冲突时以更严格者为准：策略为「仅手动」时自动缓存开关不可开启，策略为「禁止」时连手动缓存也不可用；策略收紧后，已有不合规缓存在下次联网校验时清除。
- **失效清除与本地安全**：退出登录不自动等于删除缓存；但账号被停用、条目权限被撤销、条目被撤回 / 下架，或用户把条目移出我的库时，客户端在重新联网校验后必须清除对应内容缓存（只保留必要的审计记录）。本地缓存按账号隔离存储，存放在受操作系统用户目录保护的位置，并应支持静态加密；缓存不得被其他账号或未登录状态打开。

### 4.16 索引推送到演示厅

索引详情与总览卡的动作区都有「推送到演示厅」，这是索引进入演示厅的正式通道：

- **推送基准**：以该仓库 **main 分支当前已发布的最新标签**为准；main 尚无任何已发布标签时，动作不可用并提示先打标签发布。
- **同一审核队列**：推送生成一条演示厅待审提交，进入广场上架审核队列——与成员自荐**合并为同一队列**，不另设第二套队列；组织节点开启成员自维护功能时，两者共用同一审批通道与同一状态机（待审 / 通过 / 驳回，**驳回必填理由**）。该节点设为免审公开时，推送按免审规则处理（推送即上架，留痕通知、管理员可下架）。
- **通过**：在演示厅广场上架展示，生成的演示厅条目**绑定该索引**，来源标注为该索引名 + 其目录坐标；条目后续按演示厅既有规则**跟随来源索引的新发布标签解析**（来源打新标签后条目解析随之更新，不需重新推送）。
- **驳回**：索引详情与推送记录处显示驳回理由，并给出「修改后重新推送」入口。
- 来源索引转历史 / 已作废时，其演示厅条目标注来源状态，不静默消失。推送、撤回推送与审核结果均记审计。**推送不改变索引本身的更新线、分支与导出绑定**：导出物仍按三元组走自己的线，演示厅条目只是该索引多了一个展示出口。

## 五、界面与交互规范

### 5.1 顶层导航与页面结构

界面最顶部一级页签固定顺序为 **演示厅 → 内容页 → 索引页 → 设置**，应用打开**默认落在演示厅**，切换即整页替换，各页独立成篇、互不混排。组织管理不是顶层页签，它是设置页内的一个区（见 2.6）。语言切换是全局上下文，对各页同时生效（见 4.12）。

索引页与演示厅采用一致的页面结构与卡片组件：同样的顶部页签下左导航 + 右内容、同样的搜索 / 筛选位置、同样的紧凑卡片网格尺寸与间距、同样的「封面图 + 标题 + 一句介绍 + 维护人 / 最近修改 + 状态徽标」排版、同样的单击选定 / 双击打开。两页的差别只在业务字段与打开落点。

内容页内部，右侧内容区是自上而下**连成一体的一条长卷**——各模块内容依次衔接、页面按顺序连排，模块之间以标题带分隔，不做成互不相连的独立画面；左侧目录树是这条长卷的导航：点击目录平滑滚动定位到该模块段落，滚动长卷时左侧高亮随当前可见模块联动。索引页内部如需按模块分组条目，沿用同样的模块顺序与标题带。

### 5.2 全局交互基线

**单击 = 选定，双击 = 打开，全局统一。** 索引卡片、内容块卡片、页面卡片、缩略图、历史版本条目一律如此：单击只选中（选中的就是卡片当前所示的形态 / 版本，可配合 Ctrl / Shift 多选）；双击才打开——索引卡片的打开 = 进入索引详情 / 编辑，内容块的打开 = 进入下一层级，页面 / 缩略图的打开 = 展开大图预览，历史版本条目的打开 = 展开该版每页。不为不同对象另设打开手势。演示厅条目同理：单击只选定，双击进详情（不是直接放映）。

### 5.3 内容页：只做内容维护

内容页是左右两栏：**左 = 目录树，右 = 当前目录的内容维护区**（平铺该目录下全部内容块的最新页供浏览与维护；右侧顶部同时列出该目录的子文件夹入口，点入即切换）。该目录的「成稿」不在内容页呈现——归索引页（打开主索引即见成稿）。

内容页只有维护动作：浏览、发布、版本、标签、讲稿、语言绑定、附件、嵌套子块、撤回、申请公开。**内容页没有组装托盘、没有拖拽组装、没有导出入口**——组装与导出归索引页的组装工作台。内容页上的单击选定只服务于维护操作。唯一的例外是从索引详情「全面编辑」跳入时出现的选页模式：内容页顶部带上下文条（「为索引 X 选页 · 确认返回」），确认后回索引详情生效——这是索引发起的条目页选定，不常驻于常规维护流。

**内容块详情是页内层级导航（文件管理器式），不是弹窗**：点开一个内容块，当前内容区整层换成该块的下一层——若该块由子块组成，列子块（仍是块，可继续点开下钻）；同时列出当前形态版本的每一页缩略图。一层里可以既有内容块、又有缩略图，逐层下钻直到页。内容区顶部常驻层级面包屑（如 公司介绍 / 合作伙伴介绍 / 渠道伙伴）与返回上一层，点面包屑任意一级直接回到那一层。在下钻状态下点左侧目录，会先退回长卷再定位到对应模块。双击任一缩略图展开大图预览（浮层：整页高清图 + 该页讲稿、版本与标签信息，可前后翻页）；大图与每一层级上都带「编辑」入口（见 4.3）。

**层内布局自上而下分三段**：

1. **顶部推荐区**：系统推荐的本块内容置顶呈现——默认是主索引当前采用的形态与版本（即「优选」），无主索引采用时用该形态的最新发布版；推荐可以不止一组（例如详细版推荐给正式汇报、精简版推荐给简要介绍），每组各带理由标签成组置顶，推荐组有几页就展示几页缩略图。
2. **中部：子块与当前页**——子块入口与（当前所选形态版本的）每页缩略图。每个子块卡片直接展示它自己的推荐组（推荐形态 / 版本的全部页缩略图与推荐理由），用户不必进入子块即可了解与选用其推荐。
3. **下方历史版本**：该块的历史版本**从新到旧**排列，直到第一个版本。呈现与上方完全相同的图形化方式：每个版本是一张紧凑的版本卡片，直接摆出该版全部页面的缩略图（多页版本一排小图）、大号版本号徽标与状态徽标（已撤回等）；发布时间、作者、改动说明只作小字辅助、一行带过。**版本卡片不逐个占满整行**：它们以网格流式并排（一行摆多个版本，从左到右、从新到旧），卡片宽度随本版页数自然伸缩。单击选定某版、双击展开该版每页，并可选用 / 回退。历史按形态（与语言）切换查看，默认停在推荐区所用形态的那条线。

背后的原则：使用者对图形远比对文字敏感，找东西靠认图不靠读字——内容页的一切列表都优先图形化，文字只作辅助。

### 5.4 索引页：两级结构

**第一级：索引总览**（索引页的默认落点，不再默认打开某一份索引）。左侧分区只设三类——**全部索引、按目录（目录树）、我维护的**（开启自维护功能时含待审批状态）；主索引与语言对应不再单设导航分区，只作卡片徽标与工具栏筛选。左侧目录树为常驻导航，总览与详情内都在；列表与计数只含当前账号有权查看的索引。

每张索引卡以图形为主：用该索引当前解析出的前 3–4 页缩略图组成封面拼图，配标题、一句简介、**目录坐标一行（完整路径）与谱系行**、当前发布版本（未发布则明示）、当前解析的条目数 / 总页数、语言、维护人、最近修改与生命周期状态；主索引必须有明确徽标。单击卡片只选定，选中工具栏按权限提供预览成稿、导出、分享、推送到演示厅、建副本等动作，并常驻醒目的「新建索引」；双击卡片或点「打开编辑」才进入第二级。

**第二级：索引详情 / 编辑**。顶部有返回总览的面包屑，并常驻**坐标栏与「归属与谱系」条**（目录坐标、当前分支与分叉点、语言对应入口与状态、「制作英文版」入口；「移动到其他文件夹」在「更多」菜单中）。详情的能力包括条目增删、提交图（分支线与标签徽标画在图上，点任意提交看它的 diff 与快照；分支切换、从此提交拉分支、打标签发布、发起合并都从图上发起）、导出记录与历次导出的版本快照，并可从索引直接再导一份最新版。

### 5.5 索引总览的筛选、分组与视图

- **状态筛选固定三档、顺序不可换：使用中（默认，打开索引页即此档）→ 历史 → 全部（排在最后）**。默认只见使用中的索引；「全部」须用户主动切换才把历史索引一并列出。
- **默认按目录分组陈列**：以文件夹为分组标题（显示完整路径与份数，**份数只计使用中**），组内是紧凑的索引卡片网格，一行多张，**主索引在本组内优先展示**（组内第一张，带主索引徽标）。
- **分组头「历史（N）」按钮**：每个目录分组头在「目录名（N 份索引）」之后另有此按钮（N 为该目录下历史状态索引的份数；没有历史索引时不显示）：点击后在本组之内就地并列加载该目录的历史索引卡（与使用中卡同排呈现，带「历史」徽标、视觉降权如降饱和），再次点击收起；默认不加载历史。此按钮与状态筛选**相互独立**——停留在「使用中」档时，也能临时展开某一组的历史来看，不必切换整页筛选。
- **按派生关系视图**：可切换到仓库分支图（一个仓库一张图，main 在主线、分支按分叉点挂出；独立复制的新索引是另一张图，图间以虚线标注「复制自 X @ V__」）。该视图默认不显示历史索引；切到「历史 / 全部」档时以当前档为准，历史索引在图上降权呈现。
- **视图切换的位置**：「按目录 / 按派生关系」是小尺寸分段控件，置于**右侧内容区顶部工具行的右端**，与左侧目录树在视觉上明确分开——左侧是目录导航（坐标），右上是本区的视图切换，两者不挤在同一列；该切换只作用于右侧内容区，不改变左侧目录树。
- **语言对应不在总览层露出**：中文语境下总览只列中文索引，英文对应索引不作为独立卡片出现，卡面不挂语言对应徽标 / 入口，「按派生关系」视图同样不渲染语言对应；英文语境对称同理。语言对应只在双击打开索引详情之后显示（归属与谱系条里的对应版入口与状态）。内容页同理：列表层不铺对应入口，打开内容块后在语言绑定区显示。

### 5.6 总览陈列与公开范围边框色

我维护的索引与全部索引**同款卡片**（同样的封面、坐标行、谱系行与徽标，不搞特殊样式）。分区只按公开状态分：

- **已公开的索引**（不论谁维护）与大家的索引**混排**在主区（按目录分组 / 按派生关系视图的规则不变）；
- **我维护但尚未公开的**——未申请公开、审批中、被驳回待改——统一沉到总览**最下方**的独立区「**我的未公开**」，同款卡片，带状态小标（未申请 / 待审 / 已驳回）；该区**只对维护人本人可见**，他人（含管理员）视角下不出现任何人的未公开区。

**卡片边框颜色只编码一件事：公开 / 分享到的组织范围**，与申请公开的范围档位一一对应，全产品统一低饱和色板：

| 公开范围 | 边框颜色 |
|---|---|
| 全公司公开 | 蓝色 |
| 上级组织 | 紫色 |
| 本部门及子部门 | 绿色 |
| 仅本部门 | 橙色 |
| 未公开（仅自己） | 灰色（未公开区专用） |

边框色不与状态混用——状态仍走徽标。总览工具行放一个小图例（色点 + 范围名，可悬停展开），不占版面。索引详情的坐标 / 谱系条同步以文字 + 同色标点显示该索引的公开范围，与卡片边框呼应；改投范围获批后，边框色随之变更。

### 5.7 索引详情：五视图按钮与图墙操作

**详情布局定版**：坐标与谱系条之下设一排小尺寸视图切换按钮——**条目图墙（默认）/ 提交图 / 历史版本 / 导出记录 / 派生关系**，同一时刻只显示一个区，点按钮切换主体；详情不再把图墙、提交图、版本带、导出记录纵向全量堆叠。各区内容与功能不减，只是按需切换显示。详情的低频动作（移动到其他文件夹、生命周期变更、删除等）收进一个「更多」菜单，不平铺在页面上。

- **条目图墙**（默认区）：全部条目以图形卡排列——每卡是该内容块当前解析版本的全部页面缩略图（多页成组）、内容块名、形态 / 语言与版本策略徽标（跟随最新 / 锁定），按索引顺序排列，一眼看全这份索引由哪些块组成。
- **提交图**：git log --graph 形态，分支线与标签徽标画在图上。
- **历史版本**：版本带（当前分支的标签从新到旧图形化排列）与点开标签进入的只读老页面（见 3.3）。
- **导出记录**：历次导出的记录与版本快照。
- **派生关系**：显示本仓库的分支图（与总览「按派生关系」视图同一张图），**当前这份索引（当前分支节点）在图中高亮**——节点以强调色描边 / 底色标出并带「当前」小标、自动定位到可见区，其祖先链（从根到它的分叉路径）以强调线连起，其直接派生（子分支）在其下展开；高亮只表定位、不改数据，点击图中其他节点可切换查看该分支。

**图墙上的结构操作**（索引详情的核心交互）：

- **拖拽排序**：拖动条目卡调整顺序（拖拽中显示落点指示），松手生成一个提交（diff 记顺序变化；仍守乐观锁——基于的提交号冲突时拒绝并展示对方 diff）；
- **双击条目卡 = 就地替换内容**：原位打开该内容块的替换选择，图形化列出同一内容块的其他形态与版本（各形态 / 版本的页面缩略图组，与内容页下钻同款呈现），选中即替换——选某形态的最新版，条目保持 / 设为跟随最新；选历史版本，条目自动转为锁定并在卡上标明；多页形态可选摘页（子集），记摘页绑定。替换同样生成提交。双击在此是替换、不是跳转：去内容页维护该内容块本身另有次级入口；单击条目仍只是选定（显示条目信息与版本策略）；
- **条目间插入**：相邻条目卡之间（及首尾）有插入点，点开内容选用器（组装工作台的选用模式）选一个内容块（形态 / 版本，默认跟随最新）即在该位置新增条目，生成提交；
- **全面编辑**：条目卡上的入口，点击后跳转到内容页并直接打开该内容块（带返回上下文：来自索引 X 的条目 Y），在内容块视图里重新选定该条目使用该内容块的哪些页，确认后回索引详情生效（摘页绑定更新）并生成提交。

个人维护中的索引在总览与详情中沿用自维护功能的状态与权限，不因进入总览而变成正式索引。

### 5.8 派生结构速览（悬停预览 + 点击钉住）

索引总览的卡片上另设一个条件按钮——**「派生结构」按钮只在该索引有派生关系时出现**：它有直接 / 间接派生分支，或它本身派生自别人（即在仓库分支图上有父或有子）；完全独立、无派生的索引不显示此按钮，不占卡面。

- **悬停预览**：鼠标悬停在该按钮上（延迟约 300ms 后触发，避免划过误触），页面**最底部升起一块横贯宽度的预览坞**（高度约页面高度的 1/3，坞内图内容可滚动），坞内渲染该索引所在仓库的分支图，且本索引节点高亮（与详情「派生关系」视图同一套高亮规则：强调色描边 / 底色 +「当前」小标、祖先链以强调线连起）；鼠标移开按钮（且没有移入预览坞）时，预览坞收起消失。
- **点击钉住**：点击该按钮，预览坞钉住固定，不再随鼠标移开而消失；此后鼠标可以离开按钮、移进预览坞里慢慢看，并可点坞内节点——点其他节点切换高亮查看其关系（分叉点、提交数随之呈现），点节点上的打开入口可进入该索引详情；坞内另有「打开完整派生关系」入口，跳进当前索引详情的「派生关系」视图（完整版）。解除钉住：再次点击该按钮、点坞上的关闭按钮、或按 Esc。
- **钉住与悬停的叠加规则**：已有钉住内容时，悬停其他卡的「派生结构」按钮只作临时预览——临时覆盖坞内容，鼠标移开后恢复为被钉住的那份；悬停不改变钉住对象，要换钉住对象须点击目标卡的按钮。
- **同图两开法**：速览坞与详情「派生关系」视图是同一张分支图的两种打开方式——速览在总览层看大概、定位来路与下游，完整版在详情里切换查看与发起分支操作；两处的数据与高亮规则全局一致。
- **触摸设备**没有悬停：点按该按钮即按「钉住」打开，再点一次（或点关闭）收起。

### 5.9 界面原则：现代化、克制、简洁

这是全局最高优先级的界面原则。先划清边界：本原则**只针对产品页面设计与界面文案**；规格、功能介绍与本说明属于设计文档，必须把背景、规则、边界、例外、交互与验收写全，不因「简洁」删减文档内容。产品界面严格执行：

1. **页面里不写功能说明书**——删除 / 收起各页面的解释性段落、规则说明、操作教程、重复提示、设计原理文案与大段副标题，用户不需要先读一段话才知道怎么用；
2. **只保留完成任务必需的信息**：标题、图形 / 缩略图、对象名、必要的状态徽标、版本号 / 页数等关键数字、维护人 / 时间等小字元信息、短动作按钮；卡片文案最多保留一行简介，分区头只留标题、数量与动作，不带说明段；
3. **解释按需出现**：次要说明收进 tooltip、帮助入口、首次使用的一次性引导或详情 / 展开层，默认界面不铺开；确认 / 警告 / 错误只保留一句结论 + 必要动作，不写长篇原因；审计、历史等专业信息放在详情或展开层；
4. **视觉同样克制**：现代视觉语言、统一的间距与层级、克制的色彩 / 阴影 / 装饰、少控件堆叠、留白充足、图形优先——不得做成老式、拥挤、装饰过度或层级混乱的页面；
5. **控件尺寸同理克制（紧凑控件）**：按钮、页签、筛选片等控件默认紧凑小尺寸——桌面端高度约 28–30px、移动端不低于 32px 以保证可点；页面面积优先留给封面 / 缩略图与文字说明，按钮不得与内容争空间，工具栏随之变矮；
6. **底线**：极简不得删掉关键状态、风险确认、必要操作与无障碍标签。

设计目标一句话：**看图即懂，点开再看细节**。原型与正式客户端的每一页（含各对话框与横幅）都按此审计。

### 5.10 索引设计四条验收标准

索引是这个产品的核心，其设计单独认四条标准，与 5.9 的界面原则并列，是索引相关一切设计与验收的标尺，每次改版逐项对照，不满足的不得默认通过：

1. **合理**——模型与 Git 心智同构（仓库 / 提交 / 标签 / 分支），一份索引一个仓库、一个坐标；关系靠结构表达，不靠文字解释。
2. **现代化**——图形优先（内容块图墙、提交图、分支图），拖拽等直接操作；禁止老式的「树 + 表格 + 层层弹窗」形态出现在索引页。
3. **易上手**——全站基线不变（单击选定、双击打开）；索引详情的结构操作收敛为三个：**拖拽排序、双击替换、条目间插入**；其余动作（打标签发布、拉分支、合并、锁定、全面编辑、推送到演示厅）都从提交图上或条目卡上的显性入口发起，不藏菜单深处。
4. **易理解**——在索引的任何界面，用户一眼能回答三个问题：**这份索引在哪**（目录坐标常显）、**它从哪来**（分支 / 派生关系在图上）、**它现在是什么状态**（当前分支、当前标签、哪些条目锁定）。

## 六、技术架构与约束

### 6.1 一期两件套

一期只做两件套，不做独立插件：

| 组成 | 形态 | 职责 |
|---|---|---|
| 服务端 | Rust 服务，跑在局域网常开电脑 / NAS | 存全部内容、版本、索引、账号与权限；逐请求校验权限；下发更新；生成导出；备份与恢复 |
| 客户端 | Rust 桌面程序（GUI）+ 同步交付的 CLI，内置 COM 桥 | 浏览、维护、组装、导出、发布、组织管理；COM 桥承担 PowerPoint 侧能力 |
| 核心库 | Rust 库，GUI / CLI / 服务端共用 | 版本、索引解析、组装、导出、权限、更新比对的唯一实现 |

原地替换的本质是操纵 PowerPoint 里正打开的那份文稿；在 Windows 上，独立程序经 COM 自动化从外部连接正在运行的 PowerPoint，同样能插页、删页、导出页，而且免去给每台机器部署加载项、处理信任中心，适用的 PowerPoint 版本面也更宽。独立插件多买到的是 PowerPoint 内的任务窗格体验、文件打开瞬间的事件级提示、Mac / WPS 等没有 COM 的环境——这些放到二期：PowerPoint 操作层做成独立适配层（桥），二期按同一接口补真正的加载项（含 WPS）。规格全文中出现的「插件」均指这项 PowerPoint 侧能力（一期 = COM 桥，二期 = 加载项），职责不变；CLI 经桥同样可触发对已打开文稿的操作。

COM 桥的实现要点：通过运行对象表连接已打开的 PowerPoint 实例（多实例 / 权限级别不一致时给出明确提示）；桥不可用（PowerPoint 未开、非 Windows）时，客户端照常提供库、组装、导出等全部离线功能，只是不提供对已打开文稿的操作。

### 6.2 服务端

- 一个独立服务程序：开发时跑在开发机（本机地址或局域网 IP），上线时跑在常开电脑 / NAS，**不改代码**。
- 数据：一份数据目录 = SQLite（元数据）+ 文件目录（页片段、缩略图、附件）。迁移 = 拷贝整目录 + 客户端改连接地址；账号与授权一并迁移。
- 接口：Axum + Tokio 提供 HTTP API；更新通知用 WebSocket 推送，并保留轮询兜底。
- 发现：mDNS 广播服务，同时支持手动填主机地址 / 主机名，界面展示地址（二维码可选）。
- 职责：版本存储与递增、成员与设备确认、发布与冲突检查、给 PowerPoint 侧下发页片段、客户端更新分发（可选，由主机作镜像分发新版本）。
- 服务端口固定并在界面明示；注意 Windows 防火墙与 NAS 的端口放行。

### 6.3 客户端与界面路线

客户端功能面包括：内容库浏览与内容块下钻、索引总览与详情、组装工作台、导入与拆分工作台、发布管理（含剪贴板发布与编辑回路）、标签管理、附件管理、语言绑定工作台、AI 翻译校对、消息中心、分发台账、演示厅与我的库（含离线缓存治理）、设置与组织管理、主机管理（成员列表、设备确认、数据备份导出）。

界面技术暂定纯 Rust 路线：**egui 倾向已明确**——storytold / Craft 系列的桌面壳就是 eframe / egui（已处理 wgpu 渲染、系统剪贴板含图片、AccessKit 无障碍、原生文件对话框、Windows 图标与版本信息等桌面集成琐事），其界面层被设计为可替换、其下各层不依赖它，与本项目「共用核心逻辑、界面各表」的结构天然合拍；Tauri 只保留为 Phase-0 对比项（各做一个内容库页面原型后最终定，见第九章）。

### 6.4 与 DeckCraft 的兼容要求

除复用 storytold / Craft 系列的 Rust 资产（deckcraft-pptx 解析与导出、deckcraft-render 生成缩略图、craft-update 的局域网镜像分发、craft-i18n 的界面多语言机制等，许可证 MIT OR Apache-2.0，复用时锁定确切版本 / commit 并保留上游声明）外，产品层面还要与 DeckCraft 本身兼容：

- **导入兼容**：在 DeckCraft 里制作 / 编辑并保存的 .pptx，与 PowerPoint 制作的文件同权——可直接导入、拆分、发布、纳入索引，不要求任何格式转换。
- **打开兼容**：本系统导出 / 组装生成的 .pptx 须能在 DeckCraft 中正常打开、编辑、另存，无错误、无可见劣化。
- **清单往返兼容（关键风险点）**：文稿内嵌清单必须经得起 DeckCraft 的「打开—另存」往返而不丢失、不损坏——清单的嵌入位置与格式要选标准 OOXML 扩展点，并在 POC 中实测往返后清单仍可被读出；若实测不保，再评估改用 DeckCraft 会保留的部件形式。
- **放映集成（一期）**：演示厅的正式放映由 DeckCraft 承担，通过独立的演示适配层调用；一期允许外部启动，是否嵌入播放器由 POC 决定（见 4.15）。
- **可选的深度集成（二期候选，一期不做）**：服务端借 deckcraft-render / deckcraft-pdf 生成缩略图与预览；客户端内嵌 DeckCraft 引擎做离线预览 / 轻编辑；把 Craft 的 PPT 编辑器直接内嵌进客户端在内容块详情里就地编辑。是否提前到一期，由 POC 结果决定。

必须正视的风险：DeckCraft 自述仍处 alpha 阶段，其路线图自评对 PowerPoint 的兼容广度约 84%、就绪度约 55%。**不得在未验证前假定其 PPTX 往返无损。** 因此页片段的生成设两条候选路线，POC 后定其一或分工：**路线 A**——用 deckcraft-pptx 导入模型后导出片段；**路线 B**——直接在 OOXML 包层面做手术（复制页部件与关系、其余部件原样保留），DeckCraft 源码作为关系处理的参考实现。跟随上游升级需过保真度测试集。

### 6.5 CLI 全量等价与 AI 接管

CLI 与 GUI 同步交付、功能等价，是硬性要求。架构前提：全部业务逻辑实现在一个核心库里，GUI、CLI、服务端 API 都只是它的前端 / 适配层。

- **覆盖范围（与 GUI 等价，缺一不可）**：登录与主机连接；导入 PPTX 并拆分指认（支持 `--ai-split`、`--quick`、`--dir`、`--owner`）；发布 / 草稿；标签增删与词表维护；目录与索引的增删改、条目调序与版本策略设置（索引域命令按 Git 心智提供等价操作：log / branch / tag / diff / merge / checkout 的语义映射为 JSON 命令）；组装清单的建立、按索引导出、导出记录查询（组装 / 导出命令归索引域，对应索引页的组装工作台；内容域命令只含维护类操作，与内容页只做维护一致）；对指定文稿查更新并输出差异清单（含四类结构变更）；组织管理（部门、账号、分组授权）；设置类命令（按管理层级裁剪，见 2.6）；服务端运维（初始化数据目录、备份、成员设备确认）；附件上传 / 列出 / 下载；AI 翻译批量发起；整份索引讲稿导出；**全量数据导出**——一条命令把全部片段、附件与元数据（JSON）打包导出为开放格式，保证公司资产不被本系统锁死、可迁出自查。
- **AI 友好规范**：全非交互（一切参数走命令行参数 / 选项 / 标准输入的 JSON，绝不中途提问；破坏性操作用显式 `--yes` 确认）；结构化输出（`--json` 输出机器可读结果，对象带稳定 ID；错误输出到 stderr 且带稳定错误码与非零退出码；人读格式只是同一数据的另一渲染）；可脚本化（批量操作支持一次传入多个 ID，长操作输出确定的产物路径与 ID，操作尽量幂等、重复执行不产生重复数据）；`--dry-run` 预演（发布、导出、结构更新类操作先输出将发生的变更清单）。
- **身份与权限**：CLI 以某个账号登录（令牌存放于本机受保护文件 / 环境变量），一切操作同样受权限约束——AI 接管的是「某个账号能做的全部」，不是绕过权限的后门。
- **用途定位**：除 AI 接管外，CLI 同时是验收场景的自动化执行工具——验收要能以脚本形式重跑，而不是靠人手点 GUI。

## 七、非功能需求

### 7.1 权限的服务端强制与不可见不泄露

账号、部门、权限是系统的一等公民，不是后补的设置页。成员只能看到被授权分组内的内容；页库、搜索（含计数与提示）、缩略图与片段下载、组装、PowerPoint 侧面板、更新下发、导出生成、设置页分区，全部按账号权限在服务端过滤——看不见的分组，其内容在任何接口里都不出现，**连「存在」都不泄露**：无权索引不出现在列表与计数中；他人的未公开索引区在任何其他人（含管理员）的视角下都不出现；无权条目混在一份文稿里时，那些页在系统内保持不可见、不可更新（文件本身已在用户手中的不在系统控制范围）。一份文稿里混有无权分组的页，不影响其有权页的正常使用。

### 7.2 备份与恢复（一期必备）

由于系统不存原稿（见 3.7），服务端数据目录是全公司 PPT 资产的唯一副本，因此：服务端按计划**自动定时备份**数据目录，并支持备份到另一台设备 / NAS 路径；提供**一键恢复**（在新机器上还原并自动校验完整性）；管理员可随时手动备份；恢复演练应定期做，备份状态在主机管理页可见。

### 7.3 审计

登录、导出、发布、授权变更、标签变更、索引状态变更与坐标变更、推送与审核、编号重编号、自维护功能的开关 / 模式切换 / 提交 / 审批 / 驳回 / 直接公开 / 下架 / 维护人转交——均记操作日志（谁、何时、对什么、改了什么）。审计信息放在详情或展开层，不铺在默认界面。

### 7.4 存储保留

- 草稿超过工作区设定天数未动自动清理（提前在消息中心提醒作者）；
- 已发布版本永久保留，长期未被引用的可由管理员**归档**（冷存、仍可查可恢复）；
- 页片段内的媒体文件按内容哈希**去重存储**，多片段引用同一份；
- 主机管理页显示数据目录用量与增长，接近阈值时预警。

### 7.5 并发与一致性

- **索引编辑**：索引修订号即乐观锁——提交编辑时若服务端修订已前进（别人在打开后改过），提交被拒并展示对方的新修订差异，由提交人基于最新重新提交，不做自动合并。
- **同内容位并发发布**：版本号由服务端串行递增，两人同时发布同一形态时后到者基于前者结果成为下一个版本，不覆盖、不丢版；发布确认卡提示「刚有人发布了 vX」。
- **同一文稿多端打开**：更新检查相互独立，原地替换只作用于执行它的那个 PowerPoint 实例；清单以服务端为唯一事实源，本地缓存只读降级。
- **离线降级**：主机不可达时，PowerPoint 侧不弹更新提示；客户端只以离线缓存为准提供只读能力（见 4.15）；个人目录整理等纯本地操作可排队待联网同步，发布 / 申请公开 / 审批 / 授权类操作一律不离线执行。联网恢复后先做权限与版本校验；账号被停用、权限被撤销、条目被撤回时，对应缓存按规则清除。

### 7.6 开放格式全量导出

一条 CLI 命令可把全部片段、附件与元数据（JSON）打包导出为开放格式。公司资产不被本系统锁死，可迁出、可自查——这是长期信任的基础设施，不是锦上添花。

## 八、分期与验收

### 8.1 分期总览

- **第 0 期 POC**：先验证最关键的技术风险（见 8.3）。此期不过，不进一期。
- **第 1 期 局域网版**：规格第 1–8 节全部内容。形态为两件套：Rust 客户端（GUI + CLI，内含 PowerPoint COM 桥）+ Rust 服务端。客户端与插件只连局域网、不连外网（AI 翻译是唯一例外）。
- **第 2 期候选**：PowerPoint / WPS 加载项（插件形态）；按部门 / 分组的强制推送策略；多组织与云端 / 跨网；DeckCraft 深度集成（服务端渲染、内嵌编辑器）；企业微信 / 邮件通知打通。

一期明确不做（数据结构可预留，功能不实现）：公网 / 云端同步与跨网络使用；按部门 / 分组的强制推送策略；WPS 插件；自动合并同一页的双方修改。

### 8.2 一期范围要点

一期范围即本文第四章的全部功能：导入与 AI 分割、日常 / 剪贴板发布、编辑回路、标签、搜索、组装与优选推荐、导出与体检、分发台账与消息中心、打开检查与原地替换、结构更新、讲稿、附件、个人绑定、多语言全套（绑定工作台、AI 翻译、双语页、语言语境）、演示厅（广场 / 指定分享 / 我的库 / DeckCraft 演示 / 离线缓存）、索引推送、组织与权限全套（含自定义群组、成员自维护与申请公开、设置分级）、CLI 全量等价、备份与恢复。

### 8.3 Phase 0 POC 五项与保真度门槛

1. **片段生成路线 A / B 对比**：用真实业务文稿对比两条路线的保真度，定其一或分工。
2. **COM 桥原地替换闭环**：在同事实际使用的 PowerPoint 版本上，验证读清单 → 插页 / 删页原地替换的完整闭环（含多实例、权限级别不一致等异常提示）。
3. **最薄链路**：读清单 → 查主机 → 提示更新，三步打通，验证清单格式与查询协议。
4. **DeckCraft 往返与放映实测**：DeckCraft 打开—另存往返后清单存活与内容无劣化；本系统导出稿在 DeckCraft 中打开无劣化；DeckCraft 对真实业务稿的放映保真度（版式、图表、动画、切换、音视频、双屏演讲者视图）实测，据此定嵌入播放器还是外部调用、以及明示降级的口径。
5. **界面路线原型**：egui（与 Tauri 若仍需对比）各做一个内容库页面原型，作为界面路线终审的依据。

**保真度门槛（规格场景 13）**：一批含图表、SmartArt、动画、音视频、备注的真实业务文稿，执行抽页、发布、原地替换、切回旧版全流程，在目标 PowerPoint 版本中打开均无修复提示、版式无可见劣化；同一批文稿另做 DeckCraft 往返，内嵌清单完好、内容无可见劣化，本系统导出的文稿在 DeckCraft 中打开亦然。**此条不通过，不进入一期开发。**

### 8.4 验收场景体系

规格第 9 节共 **50 条验收场景**，覆盖一期全部关键行为，是开发与交付的共同标尺。按域概览：

- **更新与替换**：多内容位精确提示与原地接受（1）、精简 / 详细双向切换（2）、内容修订与形态过期（3）、本地修改三选一（4）、单页更新与页级冲突（26）、版本撤回强提示（27）；

- **标签与权限**：标签闭环（7）、分组权限与停用失效（9）、临时授权到期（30）；
- **索引**：导出即最新与锁定条目（8）、结构更新四类变更闭环（12）、标签与分支隔离（21）、生命周期（22）、Git 式分支与合并（42）、详情图墙与就地替换（43）、条目插入 / 全面编辑 / 锁定（44）、语义版本号与老页面（45）、拖拽插入历史与级联重编号（46）、总览两级结构（37）、坐标常驻与谱系（41）、总览默认档 / 分组历史按钮 / 推送演示厅（47）、总览陈列与范围边框色（49）、派生结构速览（50）；

- **多语言**：语言绑定与换语言（16）、AI 翻译闭环（17）、双语页（18）、译文来源与人工保护（32）、索引语言对应版（33）；

## 九、未决事项

以下事项尚未拍板，如实列出；正文未把任何一项假装已定。

1. **产品命名（暂定）**：产品暂定名「启幕」（2026-11-14 定，明示为暂时名称，后续可更换）；正式定名前商标 / 公众号查重尚未进行。此前讨论过的候选（呈新、日新、同源等）均未采用，留作备选池；「演示厅」只是板块名，不是产品名。
2. **同事的 PowerPoint 版本环境**：具体版本与授权形态（是否支持 PowerPointApi 1.2）、操作系统是否全 Windows——决定 COM 桥的兼容细节与二期加载项路线。一期是否必须在 PowerPoint 内完成发布（选中页直接发布），还是先只在客户端导入发布、桥专心收更新，也与此相关，尚未定。
3. **WPS 使用占比**：决定第二期 WPS 插件（或桥）的优先级与路线。
4. **常开主机形态**：Windows 电脑还是 NAS（品牌 / 系统 / 能否跑 Docker 或原生服务）——决定服务端打包方式。开发期主机不可用，服务端跑在开发机上，上线时整体迁移。
5. **片段生成路线 A / B**：由 Phase-0 保真度 POC 结果决定（见 6.4、8.3）。
6. **客户端界面路线终审**：egui 倾向已明确（证据见 6.3），Tauri 保留为 POC 对比项，各做一个内容库页面原型后最终定。
7. **组织细节默认**：成员可兼属多个部门、部门授权默认向子部门继承——已按此设计，若与公司实际管理习惯不符再改。账号开设方式一期按管理员开设；是否需要「邀请链接 + 自行设密码」再议。
8. **DeckCraft 兼容深度**：一期定为文件级兼容 + 清单往返验证 + 放映集成；服务端渲染缩略图、客户端内嵌 DeckCraft 编辑等深度集成是否提前到一期，看 POC 与实际需要。DeckCraft 当前可调用的演示接口与双屏实现方式，也由 Phase-0 实测决定。
9. **跨块合成提案的整体采纳状态**：规格 3.15 的层级与跨块合成整体标注为「设计提案，待审阅」；其中嵌套块的浏览与调取行为已由需求方另行确认（见 3.5、5.3），其余部分以规格最终审阅结论为准。
